# AR08：首音时延分段定位与优化方案

> 状态：**草案，未实施、未取得新时延样本**；日期：2026-09-09。
> 交付对象：mobile 语音、Planner/Info/LLM Gateway 工程、QA。对应 R11 首音部分。
> 基线与授权见[接续路线](2026-09-09-android-ar06-ar11-execution-roadmap.md)，历史修复见[语音卡顿记录 §6.5](2026-09-05-mobile-voice-broadcast-stutter-plan.md)。

## 1. 要交付的结果

量清楚“用户说完到听见有效答案”花在哪里，只针对当前证据中的主瓶颈优化，并同时验证答案、动作、确认和多段播报。光球反馈、提示音和“正在查询”不能代替有效首音。

历史上队列播放器与 MiniMax 账号级 RPM 周期空白已有独立修复证据。本批保留这些回归，不把历史 12.7s/29s 当成当前包基线，也不重新宣判旧缺陷复发。

## 3. 时间线与指标合同

拟在现有 `mobile/src/core/obs/` 内补有限的轮次计时对象，复用 trace/request/bubble，不另建会话。ASR 开始时可先持有本地 `interaction_id`，拿到主请求 ID 后关联；ASR 取消则保留为独立取消事件，不能伪造一个业务请求。

| 事件 | 定义 | 时钟与证据 |
|---|---|---|
| `input_gesture` / `capture_started` | 用户触发、物理采集开始 | 客户端单调时钟；采集事实来源 |
| `utterance_end` | 用户实际说话结束 | 声学标注；VAD 判断时刻另记 `endpoint_detected` |
| `asr_final` | 客户端收到有效最终转写 | 本地单调时钟，含流式/批处理和终态原因 |
| `request_sent` | 真实 WS 发送，不是入队或点击发送 | 现有 onSent 边界 |
| `server_received` / `plan_ready` / `agent_first_result` | 服务端处理阶段 | 各服务自己的 span/duration 与 trace |
| `first_useful_text` | 到客户端、可作为回答或合法澄清/确认内容的首段文本 | 不计 loading、空白、推理内容、无事实的安慰话术 |
| `tts_text_sent` / `first_pcm_received` | 本段有效文本送合成、首段 PCM 到达 | 本地时间，含 tts_session_id、采样率与实际 provider |
| `play_scheduled` | 首个有效样本排定的时刻 | AudioContext 域，记录 jitter；不称声学首音 |
| `audible_onset` | 扬声器实际发出的有效答案首音 | 独立声学取证或经过验证的原生输出测量；注明误差 |
| `play_ended` / `stopped` | 自然播完/主动停止 | 两种终态独立，含段数、未播段和停止原因 |

主指标：`audible_onset - utterance_end`。辅指标：ASR 定稿、准备/排队、请求至有效文本、文本至 PCM、PCM 至排定/真实出声、整轮播放与段间空白。文本请求用 `request_sent` 为起点另列；PTT 松手与自动端点另列；S2S 自答/移交主链分列。

跨设备和服务端时钟**不能直接相减**。只计算各时钟域内部持续时间，靠 trace 串阶段；并发、重试和缓存有重叠，不能把 span 简单相加伪装端到端。墙钟只用于检索与样本排序。缺事件记 null/NOT_MEASURED，不填 0；旧 `firstAudioMs` 保留原语义和字段说明。

### 3.1 声学校准

正式报告须区分 `acoustic`、`native_output`、`scheduled_proxy`。优先用同一外部时基记录参与者结束说话与手机扬声器首音，使用同意参与的测试语料；不为了测量额外打开产品隐藏麦克风。仪器需验证静音、提示音、无音频包和播放器启动失败不会被判有效首音。

原生/排定代理可做高频定位，但未经声学校准不能签“实际首音 p95”。每个正式主桶每臂的首音样本均需有同口径测量；若只能取得部分声学样本，两种统计分别报告，未测部分不补估为真实结果。

## 4. 语料、冻结条件与建议门槛

先锁 APK/配置、AR07 声学路径、主链与音频 provider/model、TTS voice、云端完整 SHA、网络、缓存策略、并发和配额状态。一个候选只改一个主要瓶颈；新 provider 另开实验轨，禁止全局切换影响别人的真栈会话。

| 正式主桶 | 示例/范围 | 建议端到端目标（p50 / p95） |
|---|---|---|
| L 简短确定回答 | 系统已有事实、日期/时间或短常识；注明实际 T0/T1/S2S 路径 | ≤3s / ≤5s |
| I 常规信息问答 | 有明确城市的天气、真实信息查询/手册；内容与来源有判据 | ≤6s / ≤10s |
| C 长回答/复杂信息 | 长中文解释、受控多域只读任务、mixed/final 一次到齐 | ≤10s / ≤15s |

以上是**本次提议的 PoC 工程门槛**，不是将旧局部“首片/首响 <1.5s”承诺改成达标。旧指标必须单独注明起点；最终采用目标采样前冻结，达不到应出失败与下一轮选择。

辅助建议：`endpoint_detected → asr_final` p95≤1.5s；首有效文本至可听输出 p95≤2s；候选改善瓶颈桶 p95 至少 20%，其他桶不恶化超过 10%。若 A 已达到绝对目标且没有值得承担的改动，可保留 A，不强求改代码凑收益。无自然音频的合法纯卡片轮不算 TTS 故障，但也不进入语音首音成功分母。

样本：每主桶 10 条固定语料 × 3 次/臂，30 条/桶/臂；语料含正反例并先写答案/来源/动作期望。探索集独立，A/B 交错；报告全样本、经验 p50/p95、超时/失败/取消/回退。采用 nearest-rank（排序后第 `ceil(p*n)` 项），脚本与报告注明定义；30 条的 p95 是小样本经验读数，不宣称总体置信区间。

冷启动/首个请求、warm 会话、弱网/配额等待分组；配额用尽不是“污染即可删除”。外部中断可标污染，但保留原尝试与理由。业务失败、超时、无声始终在总分母中，不以只统计成功时延得到漂亮数字。

## 5. 依证据选择优化位置

| 瓶颈证据 | 优先方案 | 必须保住 |
|---|---|---|
| ASR 尾部/回退占主要等待 | 先查本地端点与 server final，再调整一个超时或端点参数；缓存合法能力查询 | 不吞短句/尾字、不重复发请求、不扩大采集窗 |
| 发送前定位/视觉或离线准备 | 消除重复查询与无效等待，复用本轮有效事实 | 权限征询、取消代际、位置/视觉时效与最小化 |
| 规划或上下文准备慢 | 减少重复工作、适用现有 fast 路径、控制上下文；证据支持再评估模型档位 | registry/manifest 权威、安全问句写闸、补槽/确认与真实语义 |
| Info 获取/合成慢 | 使用已有受控并发和流式机制，首段须有可靠内容；长文 progressive 需保真 | 实时来源、provenance、完整回答，不以假数据/提前宣称执行换速度 |
| TTS 首片/RPM 慢 | 按实际文本到达形态检查 pacing 与账号桶等待 | 已修的首片门控/共享配额、mixed 段完整性；不能复活周期空白 |
| PCM 已到但出声慢 | 检查 jitter、线程/重采样与输出路由，再单变量调整缓冲 | 无嗡嗡、underrun、漏段；“只停播”与不误开麦不退化 |

不为了降低首音跳确认、绕权限、让 LLM 直控车或把提示音算答案。若需新增 proto 字段，先改源再 codegen，验证网关和 HMI 兼容；计时信息不能携带原始音频或敏感请求。

## 7. Goal 文本与交接

执行方式以[工程交付与集中验收安排](2026-09-10-android-goal-delivery-and-acceptance-plan.md)为准。下面两种目标在启动时选择；默认采用工程交付目标，本文完整验收矩阵仍保留。

### 工程交付 Goal（默认）

> 按 AR08 方案完成工程交付：建立端到端事件与轮次关联、统计/质量检查和声学校准装置；在现有授权环境取分段基线，修复已证实且可独立验证的瓶颈，完成适用回归与候选构建/发布材料。真实首音依赖的取样、缺少部署的候选 B 和最终盲听集中处理；等待时继续其他工程任务。交付代码、可重算数据和具体后置用例，不以排定回调替代声学首音或声称未部署代码已有生产收益。

### 完整验收 Goal（另行启动）

> 按 AR08 方案建立从说话结束到有效声学首音的可关联计时，冻结 APK、声学路径、云端 SHA、provider/model、语料和目标，取新 A 基线后只优化一个已证实瓶颈。完成本地回归及必要发布授权流程，在固定候选重取 B，逐桶验证 p50/p95、失败与答案/动作质量，保留段链、停播和 RPM 回归。未达到目标或未取得声学证据时不得宣称首音专项通过；把代码产物、原始样本和下一步落盘。

交接给 AR09：选定代码/云端/音频配置、诊断事件合同、负载可比条件。交 AR10：主桶目标与实测、未通过项、完整盲听材料、实际支持场景。实施记录采用[统一证据格式](2026-09-09-android-ar06-ar11-execution-roadmap.md)。
