**目标与现读结论。**

- R03：带 operationId 的确认被 pendingLocationText 截走；本轮离线复现。
- R04：取消只改展示计数，真实 WS 队列仍发送原帧；定位 Promise 在取消后继续派发；本轮两条离线复现。
- R05：“另有 N 个待处理”无回调，v2 又隐藏气泡确认；本轮现读确认。
- 相关事实：gateway/edge/main.go 每连接只保留最新的在飞请求；新请求会抢占上一请求，cancel 帧只取消当前请求。因此客户端不能按 FIFO 头标记另一轮，也不能把离线 cancel 留到重连后误伤新请求。

**最小实施方案。**

1. 明确操作归属：有 operationId 只处理该业务操作，并在点击时校验台账和 TTL；本地定位同意只走本地分支。保持三条挂起容量与服务端权威关闭。
2. 将发送前准备登记在 SessionCore：在定位/视觉异步开始前登记请求和占位，取消/销毁后回调失效；准备中的用户气泡保持可见。视觉物理停止与零落盘仍归 AR02。
3. 扩展共享 WS 的可选发送跟踪：在真实发送时通知，能按 requestId 移除未发帧，取消控制帧只在已连接时发送。默认 send 行为和线上帧结构兼容 HMI。
4. 请求取消按目标身份处理：未发送项撤销队列/准备，已发送项停止本端等待并尝试当前连接的取消；保留已接收动作，不宣称业务回滚。迟到的点名 cancelled/error 不影响其他请求。
5. Dock 的“其它待处理”打开本地可滚动列表，按稳定 id 展示并操作各项；复用现有 G0 卡、倒计时和触控尺寸，不新增样式系统或依赖。

本批不修改 proto、网关执行协议、VAL、数据库、CI/CD、环境或密钥；不启动其它 AR 批次。不推送或部署本批代码，除非用户对本批另行授权。
