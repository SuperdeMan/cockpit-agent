## 1. 测量（只读，2026-10-04）

### 1.1 线上历史（collector 保留约 85 天、1771 次规划，只计数）

### 1.2 能源链（代码，未实测）

- **电量**：云端从验签后的车况视图重建 `vehicle_observation`（含 `observed_at_ms`、`source_kind`、`authenticated`、`expires_at_ms`，
  `orchestrator/cloud/clients.py`），但充电 Agent 只读裸的 `vehicle_battery` 字符串，SDK `ctx.fetch` 也把元数据丢了（`agents/_sdk/base.py:74`）。
  话术「当前电量{X}%（约{Y}公里续航）」与卡片都不带时效、来源。
- **读不到电量就按 50% 算**：充电高德实现、充电 mock、行程规划三处同款兜底（`charging_planner/src/providers/amap.py:103`、`mock.py:55`、
  `trip_planner/src/agent.py:157`、`pipeline.py:742`）——话术因此会说出「当前电量50%（约250公里续航）足够直达」这样**编出来的车况**；
  行程规划写的是 `float(...) or 50.0`，**真实读数 0% 也会被当成 50%**。
- 续航 = 电量 × 满电续航（缺省 500 km），话术里没标「估算」。
- **导航拿不到电量**：导航只声明 `context_scopes: [location]`，`vehicle_battery` 被权限视图滤掉，它的低续航提醒（`_range_advisory`）
  在线上不会触发（单测直接调方法，没走下发链）。
- **充电站**：高德普通 POI 搜索，没有实时空闲 / 营业状态（`available=0,total=0` 占位）；`charging_list` 与低电量提醒卡没有 `_prov`，
  HMI / App 的充电路线卡不显示来源角标。
- **重新规划**：没有任何「站点满了 / 关了 / 换一个」的处理；充电途经点只在动作载荷里，不在路线会话（`_route_session`）里，
  「换一个充电站」找不到它；`charging.plan` 不保存方案。
- **可追溯**：选站理由、保留余量规则（首段 85%、之后每段 65%、尾段 20 km）、到达电量都不进数据 / 卡片 / trace；没有「最低到达电量」等约束槽。

### 1.3 健康链（代码，未实测）

- **胎压**：「胎压正常吗」「胎压报警了吗」在端侧本地答，VAL 模拟分支直接套成功话术「当前四轮胎压正常」——**背后没有任何胎压数据**
  （模拟车 27 个信号里没有胎压、告警灯、故障码、里程、保养状态）。这是第二处编出来的车况。
- **告警解释**：手册来源护栏只登记了一条（胎压告警，第 245/256/257 页），且只在命中告警关键词时才走（「低了」「黄色感叹号」都不命中），
  其余是检索 + 模型生成；证据可用的分支没有「不能据此判断已排除」这句（只有证据不可用分支有）。
- **「已排除」**：系统模板与提示里没有声称故障已排除的话；但用户一句「已经恢复正常了」就会清掉会话告警（只按用户原话），清掉后道路安全建议可能回到
  「天气良好，适合出行」。没有任何判据拦「故障已排除」类声称。
- **预约**：没有任何预约 / 联系 4S 店能力；服务建议只是文字（「前往就近服务点检查」）。唯一带「预约」形态的写能力是 `nearby.order`（餐厅、确认闸、接入中桩）。
- **可追溯**：手册卡带页码、章节与指纹；话术只说章节名不说页码；没有任何健康答复带车况信号来源。

## 3. 分片建议

- **S1 车况不编、带时效与来源**（判据①，含胎压固定答「正常」）：读不到电量就如实说、不判断「够不够」；0% 是合法读数；续航标「估算」；
  SDK 读车况保留时效与来源；充电 / 低电量卡带 `_prov`；导航补 `vehicle_state` 上下文范围让低续航提醒真能触发；端侧胎压没有读数时如实说读不到
  （端侧能力五段链与门禁照流程跑）。
- **S2 告警解释不越界**（判据③）：手册护栏不止认关键词；证据分支补「不能据此判断已排除」；「故障已排除 / 恢复正常」类声称只认车况来源，不认用户一句话；
  道路安全在告警清除后不回落成「适合出行」。
- **S3 站点可重规划与约束可追溯**（判据②与可追溯）：充电途经点进路线会话、「换一个充电站」可重规划、方案带选站理由与到达电量；
  实时空闲 / 营业状态要有 Provider，没有就如实说「状态未知」。

## 5. S1：车况不编、带时效与来源（已部署 `48e35f83`）

### 5.1 判据

- **读不到就是读不到**：车况读数只认编排下发、验签且未过期的信号；没读到（没权限 / 没信号 / 过期）是 `None`——不是 0，也不是任何缺省值。
  0% 是合法读数。
- **说出口的读数带来源**：卡片与数据一律带来源类型、观测时间（业务时区）、读数年龄；话术只在来自非实车（模拟车 / 沙箱）或读数超过 60 秒时点明
  （「（模拟车读数）」「（约2分钟前的读数）」）。
- **估算要标估算**：续航 = 电量 × 满电续航假设，话术写「估算约 N 公里续航」。
- **没有读数不下结论**：电量读不到时充电规划不判断够不够、不建议补几次，只列沿途充电站作参考；行程规划不按编出来的电量排补电点、说明原因；
  端侧胎压没有读数时不说「正常」。

### 5.2 实现

- 判据一份 `runtime/vehicle_reading.py`（`Reading.percent / note / spoken_note / card_fields`，`from_projection` / `from_view`），
  云端 Agent、低电量提醒与端侧共用；SDK 新增 `Context.vehicle_reading(key)`（同样受 `vehicle_state` 读权限约束，`fetch` 照旧只给裸值）。
- 充电：`_resolve_soc` 返回 `Reading`（验签读数优先，裸 `vehicle_battery` 只作测试 / 旧通道兜底）；provider `plan_route(soc: int | None, soc_note=...)`，
  高德与 mock 删掉 50% 兜底，未知电量只列沿途充电站（间隔按一段舒适续航）；卡片 `soc` 只在读到时给（客户端据此画电量条），另带 `soc_source` / `soc_note`；
  `charging_list` 补 `_prov`；查电量读不到时如实说。
- 低电量主动提醒改用车况仓库的 `view()`（同一份车况连同每个信号的来源与时间），话术带来源说明，站点卡盖 `_prov`。

  原想补 `vehicle_state`，但导航的 9 个能力是冻结的旧接口（`additional_parameters: legacy`），上下文范围进 ABI 指纹，改了就对不上冻结清单、

  「暂时读不到胎压数据，没法判断胎压是否正常」，只有读数明确说 normal 才说正常；电量查询读不到回 None（状态闸本就先拦），读到的话术点明「模拟车读数」。

## 6. S2：告警解释不越界（已部署 `85d3353e`）

> 用户 2026-10-04 指示后续按推荐推进；以下口径为推荐项，理由随条写明。

### 6.1 判据

- **解释告警 ≠ 宣布已排除**：系统手里没有能证明故障已排除的车况来源（模拟车没有告警灯 / 故障码信号），所以凡是告警类回答
  （手册证据分支、生成分支、零命中、非权威来源、数值弃权、图标目录）一律以「不能据此判断故障已排除」收尾，已说过不重复。
- **用户说「灭了 / 处理好了」**：保留 QA T47 裁决 A（用户的话可以撤掉会话里的告警约束、这一轮不再按旧告警答），
  但会话里确有那条告警时，系统据此只说「不等于故障已经排除、建议尽快检查」，不回落成「天气状况良好，适合出行」。
  会话里没有告警时（「车没故障，今天适合出行吗」）照旧走一般建议。
- **识别补齐**：仪表上的「感叹号」图标只用于警示（制动 / 胎压 / 通用警告），没有一盏功能灯长这样，收进告警灯名；
  胎压异常的自述只收完成 / 状态形态（「胎压低了」「偏低」「过低」「不足」），问阈值的「胎压低于多少要充气」不收——
  与判据模块里「宁可漏一个告警，也不要对着一盏正常的灯劝人停车」同一取舍。

### 6.2 实现

- 措辞一份：`runtime/safety_signal.py` 新增 `NOT_RESOLVED_NOTE` / `with_not_resolved()` / `user_cleared_reply()`；告警词表新增词同步进道路安全那条告警续问路由提示（正则是词表镜像，对账测试当场抓到没跟）；
  手册问答 6 处告警拼接收成 `_alert_answer()`（处置前置、正文、收尾句）；道路安全在「用户解除 + 会话确有告警」时返回 `user_cleared_reply`。
- 变异 7 条全部被测试抓住。

发布证据：全量 10924 通过（另 2 条是告警词表与路由提示的对账测试，补齐后 4935 条相关集复跑通过），四门禁通过；变异 7 条全部判红；status 5/5，verify `20261003T190623Z-85d3353.json`；真栈只读探针：「胎压报警灯亮了是什么意思」手册原文逐字后以「不能据此判断故障已排除」收尾，「机油灯亮了」给立即停车处置，同会话「机油灯灭了，现在还能继续开吗」→「机油灯不再提示，不等于故障已经排除…建议尽快到服务点检查」（不再是「适合出行」），S1 三句复核仍通过；固定语料 20×3：60/60、100 轮，证据错误 0、open operations 0，217 次 LLM 全为 minimax/MiniMax-M3，零动作、零车态变化，p50/p95/p99 5937/12031/25031 ms；业务红 3 条均为既有手册路由签名（V211 r1 只规划了道路安全，r2/r3 手册 + 安全并行通过）。

### 6.3 登记、未在本片做

- 兜底谈话 / 聚合层没有通用的「故障已排除」声称闸：本片只修了查到的两条路径（手册回答、道路安全回落）。

## 7. S3：选站可追溯、路线会话对齐（已部署 `aef9537a`）

> 按用户「都按你建议的来」推进。判据②「站点变化可重规划」的触发只能来自用户（高德没有实时空闲 / 营业状态），
> 本片先把重规划需要的地基与可追溯做实；「换一个 = 充电挑下一个 + 导航改路线」的规划编排与带导航动作的真栈验证登记另做。

### 7.1 判据

- **路线会话与实际下发一致**：聚合器把别的步声明的途经点（如充电站）并进导航动作，活动路线（`focus.active_route`）也记同一份——
  合并规则只有一份 `orchestrator/cloud/waypoints.merged_waypoints`；此前会话只记导航步自己盖的章，「换掉 / 不去那个充电站」时路线里根本没有它。
- **选站可追溯**：规划的每个补电点带「到站估算电量 + 为什么在这补」，全程带到达估算电量（都是估算、话术写估算）；目的地附近选站带理由，
  高德基础 POI 没有实时空闲时如实标「空闲状态未知」。理由只进 `data` 与卡片，不往途经点里加字段（途经点会原样进导航动作载荷）。
- **不对没发生的导航说「已加入途经」**：单独问「X附近有充电站吗」时没有导航步、没有路线，此前却答「已为前往X的路线加入途经充电站」；
  充电这一步自己不发导航，话术只说推荐。

### 9.2 判据

- **换站由导航一步做完**：路线上的充电站换成原站附近的另一家（高德按距离排），排除原站与路线上已有的点，原位替换，目的地 / 时限 / 策略 / 其余途经点不动，

  不用两步编排：改路线那一步不知道新站，话术与全程里程会是旧的；新站坐标也没法经字符串槽交给导航，只能按名字重搜，可能搜到别处的同名站。
- **规划选哪个都一样**：充电识别出换站说法、且活动路线上有途经点时，零播报改派给导航改路线（`_escalate`，每轮一跳）；规划直接选导航改路线也走同一段。
  说法判据只有一份：`runtime/charger_swap`（导航与充电共用）。
- **改派出的步拿同一份焦点**：改派与主计划同一轮执行，活动路线、目的地坐标、候选集按同一个 `_apply_focus_meta` 下发（仍只给声明了对应范围的步，权限投影不变）。
- **认不准就问、换不成就说**：路线上几个充电站又没点名 ⇒ 反问换哪个；只有一个途经点、名字认不出是充电站 ⇒ 用原站附近的充电站搜索结果核实，核实不了不换；
  附近没别的站 / 路线上没有充电站 ⇒ 如实说，不动路线、不发导航。
- **提示本身能用**：手机端把追问提示整句做成 chip、点按原样发出，用户也会照着引号里那句说——提示改成「想换一个充电站，说『换一个充电站』就行」，两种都认得出。
- **并进路线由系统说**（§7.3 第二条）：别的步声明、被并进本轮导航动作的途经点，聚合器确定性附一句「已把X加入导航途经点」；导航步自己的途经点它自己会说，
