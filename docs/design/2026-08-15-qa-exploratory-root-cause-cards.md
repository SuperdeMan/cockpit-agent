## 3. 逐卡

### Q1 · 确认/挂起/取消状态机（T1）

**覆盖**：I-013 全局确认命中旧请求 / I-046 取消后仍长期待确认 / I-051 商户补槽跨域劫持 / I-037① 无订单却进退款确认

**机制（已定位到行）**：

1. **HMI 侧确认是一个布尔 + 一个字符串槽**。`hmi/src/App.tsx:73` `awaitConfirm` 是全局布尔；`confirm()`（:794）在没有 `pendingLocationText` 时直接 `dispatch(reply, true)`，**只发「确认」二字，不带任何 operation_id / trace**。谁最后置位 `awaitConfirm`，这一下就打给谁。
2. **云侧挂起也是单槽**。`session.py:123` `_session_key(owner, session_id)` 一个 key 一条 `SessionState`，`_suspend` 覆盖旧挂起（engine.py:228 注释已自认「确认条 UI 也只有一个，语义一致」）。**这个语义在两个并行任务下就不成立了。**
3. **取消判据两条分支不对称**——本卡最关键的一处。`wait_confirm` 分支（engine.py:234）用 `_confirm_reply`，其「词占据整句」规则是 `len(t) <= len(k) + 3`；`wait_slot` 分支（engine.py:255）有 `_SLOT_CANCEL_RE` 子串匹配 **+ 复合取消余量 ≥6 续处理**（§37 那批的产物）。
   于是 **「取消刚才解锁」6 字 > 2+3，在 `wait_confirm` 下判不出取消**，落进「插话保留挂起」，pending 一直活着——正是 I-046 的原文现象（第三次单独说「取消」才清除）。
   > 判据：**§37 的复合取消修法只落了一半**。同一件事的两条分支，修了 `wait_slot` 没修 `wait_confirm`——「同一件事有两份实现，迟早有一份是错的」在**分支**上的形态。

**修法方向**（未拍板）：
- **A（必做）**：把 `wait_slot` 的取消判据（子串 + 复合余量续处理）**下沉成两条分支共用的唯一实现**，`wait_confirm` 改为调用它。同 B5 `stream_state.py`「判定抄两份正是 B1 那个 bug 的成因」。
- **B（必做）**：确认帧带 `operation_id`。`_suspend` 生成 id → 随确认卡下发 → HMI `confirm()` 原样回传 → engine 校验不匹配就诚实拒绝（「这条确认对应的操作已经不在了」），**不静默打给当前挂起**。
- **C（✅ 泓舟 2026-08-15 已拍板做）**：单槽 → 小容量挂起表（≤3，LRU 淘汰最旧）。HMI 确认条相应支持同时显示多条。**实施顺序：先 B 再 C**——`operation_id` 是挂起表的寻址键，没有它多槽根本没法定位；先做 C 会得到一个「有三个槽但仍然靠猜」的状态机。⚠ 淘汰要有话术（「刚才那条解锁确认已过期」），**静默丢弃就是 B3 那条「认不出就用默认值」的确认版**。

**验收**：确认 / 取消 / 重复取消 / 超时后取消 / 换话题后取消五组；跨任务串扰一组（旧导航挂起 + 新 scene 确认）；**每组两档各跑一次**。

### Q2 · 焦点与候选集：来源、版本、时效、结构化事实（T2，问题数最多）

**覆盖**：I-018 已有营业时间却答未查到 / I-023 已知两价不算合计 / I-030 跨商户序数比较失败 / I-011 失败搜索清空候选 / I-019 详情焦点粘滞 / I-052① 无候选编造 / I-042 取消不存在的任务 / I-017 取消后卡片残留 / I-035 取消的行程仍 active / I-009① 提醒焦点错位 / I-026① 「刚才订单」错绑 / I-032② 地点焦点切换

**机制**：

1. **`Focus` 是一组扁平单槽，每轮从当前 plan 重建**（`context.py:229` / `extract_focus:545`）。粘性接力**只有两格**：`last_places` 与 `active_route`（`update_focus:700-712`）——这两格是前两次被真栈烧到才加的。`last_choices` / `last_poi` / `last_destination` / `last_choice_purpose` 仍然每轮重建，**任何一轮不产生候选就把上一份抹平**。这就是 I-019。
   ⚠ **I-011 的根因经阶段 0.2 取证后改写**（§3.5-N5）：那次「失败的重搜」**根本没失败**——泛化兜底搜出了 10 家「美食」，于是它**合法地**覆盖了上一份川菜候选。所以要修的不是「失败不覆盖成功」，而是「**兜底/降级产生的候选集不得顶替用户点名的那份**」（候选集要带 `is_fallback` 之类的来源标记，序数解析优先绑定非兜底的最近一组）。
2. **候选集只存名字**。`last_choices` 是 `list[str]`（最多 5 条）、`last_places` 只留 `name/lng/lat` **三个标量**。于是卡片上明明渲染了营业时间、评分、电话、价格，**下一轮的上下文里一个字都没有**——I-018「称全部未查到营业时间」、I-023「不肯算 26.5+9.5」由此而来。
   > 判据：**卡片是终点**。结构化结果一旦渲染成卡片就不再是可消费的事实，后续比较/合计/序数只能交给 LLM 从话术里回忆——而它没有那些数。
3. **候选集没有来源与版本**。一个 `last_choices` 同时被 nearby POI 列表、商户菜单、途经点候选、充电目的地候选共用（App.tsx 侧同样是四个并列的 `lastXxxRef`）。跨域「第二个」于是无从判断问的是哪一份——I-030、I-025①、I-053②。

**修法方向**：把「候选集」升格成**一等对象**——`CandidateSet{source_intent, agent_id, version/ts, items:[{id, name, 结构化属性}]}`，Focus 持有**最近 N 组**而不是一格；序数解析显式绑定某一组；失败轮不覆盖成功轮（沿用 `last_places` 已经验证过的粘性纪律 + 限龄不续期）。

⚠ **先做 §5 的取证**：本卡最容易走成「给每个字段都加粘性接力」——那是打补丁，不是修根因，且第三次、第四次仍会漏。

**刻意不做**：不把候选集渲染进 prompt（`last_places` 那条注释已经写明：让模型看见只会诱导它自己编）。**它是给确定性消费方用的结构化事实。**

### Q3 · HMI 响应归属与并发（T1）

**覆盖**：I-048 上一轮生成中继续发送→响应错挂 / I-053① speech 与卡片不同家 / I-022 营养查询显示订单卡 / I-010 主动卡按钮未关卡片 / I-031 按钮回发反被拒识

**机制**：

1. **WS result 帧不带 request id**，归属靠 `pendingIdsRef` FIFO + 一条注释里的假设：「网关 WS 串行（一轮事件流 drain 到 EOF 才读下一条），故 fifo[0] 恒为当前正在收流的轮」（App.tsx:89-91）。**这个假设在用户抢发时不成立**：端侧快路径可以秒回，云侧还在流——两条流交错，FIFO 头就不是正在收流的那轮。
2. **看门狗只有一个计时器**。`armWatchdog`（:575）开头就 `clearTimeout(watchdogRef.current)` ——第二个请求一来，第一个请求的超时保护**被清掉了**。这解释了报告里「下一轮长期正在思考，需要同标签页刷新」：那轮既没有 final，也没有人再去救它。
3. **按钮 send_text 与后端状态解耦**：卡片按钮发的是一句自然语言，后端按新请求处理，与产生这张卡的那次操作没有任何绑定——I-010（点「不用提醒」→ 后端说没有待确认操作）、I-031（按钮句被判拒识）。

**修法方向**：result/action/stream 各帧回带 `request_id`（网关已有 trace 语境，属加字段不属改协议）；看门狗改**每轮一只**（`Map<id, timer>`）；发送期间要么禁用输入、要么明确支持并发并按 id 归属——**两者选一，不能靠 FIFO 猜**。

**验收**（照抄报告 §I-048，它列得对）：三请求快速连发 / 第一轮流式+第二轮 action+第三轮超时 / 中间取消一轮 / 每个用户气泡只接收自己 trace 的帧。**必须 CDP 真浏览器**。

### Q4 · HMI 位置前置闸（T1，改动面最小、收益最直接）

**覆盖**：I-007（整句被拦，含车控、取消、显式城市）/ I-032①（AQI 被拦）

**机制**（`hmi/src/location.mjs:22-31`，`App.tsx:773`）：

```js
LOCATION_DEPENDENT_TERMS = /(导航|带我去|…|充电站|停车场|…|充电|补电|续航|…)/
isLocationDependent = LOCATION_DEPENDENT_TERMS.test(t) || (WEATHER_TERMS && !EXPLICIT_PLACE)
```

四个各自独立的缺陷叠在一起：

1. **子串匹配没有意图概念**：「打开**充电**口」命中 `充电`、「**取消**当前**导航**」命中 `导航`、「别开始**导航**」命中 `导航`。
2. **`EXPLICIT_PLACE` 只对天气那半边生效**：「查深圳欢乐海岸周边停车场」显式给了地点，仍被 `周边|停车场` 直接判定为依赖当前定位。
3. **没有否定/取消排除**：闸只看「提没提到位置类词」，不看这句是要**开始**还是**停止**。
4. **闸在 `send()` 里、`dispatch()` 之前，拦的是整句**：多意图句里的天气/股票/车控全部陪葬。

> 判据：**客户端不该做意图判定**。这道闸真正要问的是「本轮**执行**是否需要当前坐标」，那个答案只有编排侧知道。

**修法方向**：闸降级为「**没有任何显式地点线索 + 命中位置依赖词 + 不是否定/取消句**」三条同时成立；否定/取消/车控对象走白名单；更彻底的方向是**后端在需要坐标时回一个 `need_location` 帧**由 HMI 弹授权——闸从「事前猜」变成「事后要」。⚠ 后者改动跨端云，二期评估。

**验收**：显式城市 / 当前位置 / 取消 / 否定 / `charging_port` / `charging_station` 六组双向；多意图句「关空调 + 查深圳天气 + 看股票」不得整句被拦。

### Q5 · 身份、作用域与记忆写入约束（T2，本批最深的一处）

- **写入闸**：自环拒绝、主宾角色校验（人→地点方向固定）、`(subject, rel)` 单值 supersede、置信度低于阈值不落库。**沿用 E5 的定式：归一表 + prompt 收敛源头，两头都做。**

- **产品口径**：「进行中的任务」默认限**本会话 + 未来 N 天**，跨会话结果必须显式说明。

⚠ **数据清洗需泓舟单独授权**（红线：数据迁移）。清洗前先修入口，否则清完再跑一轮又脏——§40 已经证明过一次。

### Q6 · 执行事实账本与审计出口（T2）

### Q7 · 端侧语义维度：极性 / 顺序 / 省略（T2）

**覆盖**：I-039 否定反向执行 / I-040 同对象顺序动作只执行第一步 / I-006 刚操作完「关掉」仍问对象 / I-003「再展开」指代到天窗 / I-005 前后风挡丢一项 / I-001 云边重复执行

**机制**：`fast_intent.split_and_classify*`（:1691/:1730）把整句按连词切段，**每段独立丢给 `classify_structured`**。这条链上：

- **没有极性维度**：「车窗别开」切出来就是「车窗别开」，对象词 `车窗` + 动作词 `开` 命中正向规则 → `window.open`。**「别」不是任何判据的输入。**
- **没有顺序维度**：返回的是一个 list，执行是并行聚合；「打开然后立刻关掉」即使切对了也表达不了「先 A 后 B」。
- **没有跨段省略消解**：「把空调打开**然后立刻关掉**」的第二段没有对象，`classify_structured` 判不出 → 整段标 `_needs_cloud` 上云 → 云侧拿到一个无对象的碎片「立刻关掉」。**第一步执行了，第二步蒸发了。**
- **I-001 是同一条链的云侧半边**：`route.mixed` 把「有点冷」当独立云侧片段规划成 `hvac.inc`，而端侧已经按 26 度执行过——**已被 local_actions 满足的语义跨度没有被剔除**。

> 这三条缺的都是**同一个东西**：端侧分类器是「对象 × 动作」的**正向、无序、无上下文**匹配。加规则治不了，因为极性和顺序不是「再多几条规则」，是**多一个维度**。

**修法方向**：分段时**先抽极性**（否定词 → 段级 polarity 标记），极性为负时映射到反向意图或**诚实上云**（宁可慢一点，不要按反）；同对象多段保序（复用云侧 `depends_on` 的表达，别在端侧发明第二套）；跨段省略先在**段内**回填对象（上一段的对象是最强候选），跨轮省略走 Q2 的焦点。

**验收**：正反两向 × 三个对象 × 并列句 × 纠正句；**必须做反向突变验证**（注入缺陷要红——§4.3「恒绿的断言比没有更糟」）；`test/eval_corpus/intent_adversarial/negation` 族同步补覆盖（⚠ 语料唯一输入 591/上界 591，**余量为 0**，加语料前先按 §4.1 的规矩说明占用理由）。

### Q9 · 安全与真实性：prompt 不是护栏（**T0**）

**覆盖**：I-036 胎压(P0) / I-054 红色机油灯(P0) / I-043② 疲劳与障碍物(P0) / I-055 资讯站冒充手册 / I-034 无来源精确数字 / I-033 失败不披露 provider / I-052② 编造营业时间 / I-057 静默降级(P3)

**机制（四条，逐条有码）**：

1. **`manual_rag` 的「不要编造」只是 system prompt 的一句话**（`agent.py:15`）。代码不检查 `chunks` 是否为空、不检查答案里的数字是否出自 chunks、零命中不短路——**照样把 LLM 输出当手册结论播出去**。
2. **mock 知识库与真手册在消费面不可区分**（重判 2）。`mock.py:6` 的胎压条目带着 `source="第3章·轮胎保养"`，一路传到 `ui_card.sources`，用户看到的就是「手册第 3 章」。同一会话里追问章节时因为关键词不再命中而回到诚实兜底——**两句自相矛盾的答案，是同一条检索链的两次不同命中**。
3. **`_prov` 真实性标记覆盖面漏了正好这三个 agent**：实测 `info` 7 处、`nearby`/`navigation`/`trip_planner`/`charging_planner`/`parking_payment` 各 2 处，而 **`manual_rag` 0、`road_safety` 0、`chitchat` 0**。
   > 判据：**数据真实性治理覆盖了「取回外部数据」的 Agent，唯独漏了「答案本身就是内容」的 Agent**——而后者恰恰是最不该没有出处的那类。
4. **安全域没有「不可让步的结论」这一层**：`road-safety` 的能力面只有天气/路况三条，`fallback: chitchat`；疲劳驾驶、警告灯分级**根本没有能力面**（Q8 同源）。于是红色机油灯的安全约束不跨轮保持，被下一轮的普通驾驶建议覆盖；用户说「别提醒我，继续开」时没有任何东西挡住「好的，安心开」。

**修法方向**（本卡是 T0，先做前两条）：
- **零命中短路**：`chunks` 为空或最高分低于阈值 → **不调 LLM**，直接诚实弃权。这是确定性判据，不是 prompt。
- **来源类型随资料一起传**：chunk 带 `source_type`（`manual` / `web` / `mock`），生成层与话术层都必须体现；**`mock` 类型在非 dev profile 下不得作为结论来源**（接 B3 的 `DEPLOY_PROFILE` 三档闸）。
- **补 `_prov`**：manual-rag / road-safety / chitchat 三个 agent 接入既有 `agents/_sdk/provenance.py`。
- **安全焦点跨轮保持**：红色警告一旦出现，本会话内的驾驶建议必须先过安全约束（Focus 加一格安全态，归 Q2 的结构一起做）。
- **安全能力面**：疲劳/警告灯分级建能力（Q8），**在它建起来之前，安全类问题不得由 chitchat 兜底**。
- I-057 降级 P3：只补 HMI 展示实际 provider（obs 已有数据）。

**验收**：车型未知/已知 × 黄灯/红灯/快速掉压/高速 五组对照；**用户拒绝、改口、无视觉、连续第三轮**四种对抗（报告这条要求是对的，照做）；红色机油灯/水温/制动三类各三轮拒绝对抗。

### Q12 · 槽值保真：转述丢限定词（T2）

**覆盖**：I-008「下午三点半」→ 03:30 / I-041 英文 tomorrow 当 current / I-029 出发地被当目的地 / I-025② 规格「少冰」丢失 /（I-012 城市丢失，已有卡）

**机制**：planner 产出的槽值是**自由文本**，转述时会丢限定词，而下游拿到的是一个看起来合法的值，**没有任何东西能发现它比原话少了信息**：

| 丢的是 | 表现 | 问题 |
|---|---|---|
| 时段词（下午） | 「明天下午四点……三点半再提醒」→ 第二条槽值只剩「三点半」→ 03:30 | I-008 |
| 城市（深圳市） | 「南山实验小学」→ 全国检索命中济南 | I-012 |
| 语言（英文时间词） | `tomorrow` 未进时间归一 → 返回当前天气 | I-041 |
| 角色（从 X 出发） | origin 被填进 destination | I-029 |
| 规格（少冰） | 未进结构化规格校验 | I-025② |

> 这是既有判据「**planner 改写 query 是不可信指代通道，指代解析只信 raw**」（sports 批）的第 N 次复发。也说明：**槽值校验不能只校「有没有」，要校「比原话少了什么」**。

**⚠ 同时暴露的第三份实现**：中文时段词解析现在有**两份**——`agents/reminder/src/timeparse.py:66` 与 `agents/_sdk/timewindow.py:26`（E1 从 navigation 提出来的那份）。§4.3「同一件事有三份各自正确的实现，就迟早会有第四份是错的」刚在时区上应验过一次，**这里是同一条规则的下一个候选**。修 I-008 时顺手收敛到唯一实现，别再加第三份。

**修法方向**：关键槽（时间/地点/角色/规格）在执行前做**原话回查**——槽值里的限定词若原话有而槽值无，回填或追问；时段词/城市/极性优先走确定性回填而不是让 planner 重说一遍。

### Q13 · 两个分类出口对同一段文本产出不同意图名（**阶段 0.2 探针翻出，不在报告 58 条里**）

**性质**：Q7 与 Q8 的**共同上游**。它不产生「答错」，产生的是「走错路」——所以 QA 用黑盒方式看不见它，只有对着分类器两个出口逐字比对才会显形。

**机制**：端侧有两个把结构化意图翻成意图名的出口，**它们不一致**：

| 文本 | `classify()`（单句路径） | `_to_legacy_name()`（分段路径） | `is_local` |
|---|---|---|---|
| 音乐别停 / 停止音乐 / 暂停音乐 / 音乐停 | `music.pause` | `media.pause` | **False vs True** |
| 播放音乐 | `music.play` | `media.play` | **False vs True** |
| 下一首 / 上一首 | `media.next` / `media.prev` | `media.switch` | **True vs False** |
| 打开双闪 | `warning_light.open` | **None** | False vs — |
| 打开前/后除雾 | `front_defogger.open` / `rear_defogger.open` | **None** | True vs — |
| 打开氛围灯 / 大灯 / 座椅加热 / 座椅通风 | `*.open` | `*.on` | True vs True |

**实测 13/33 处不一致**（33 条覆盖全部端侧对象族的探针，脚本见本卡取证附件）。三类后果：

1. **媒体域的端侧快路径在单句形态下根本没生效**。`classify("暂停音乐")` → `music.pause` → **不在 `LOCAL_INTENTS`** → `is_local=False` → 整句上云。而同一句话出现在复合句里，走 `_to_legacy_name()` → `media.pause` → 本地秒回。
   > 架构文档写的是「端侧快系统处理高频/确定/安全敏感指令（车控、**媒体**）」。**媒体这半边在最常见的单句形态下一直在绕云。**
2. **「下一首」方向相反**：单句本地、复合句上云。同一个指令，句形不同走不同的路。
3. **`_to_legacy_name()` 返回 `None` 的三个对象**（双闪、前/后除雾）在复合句里必然被判「不能本地处理」→ 整组上云。

**这条链解释了报告里三个原本各自独立的问题**：
- **I-005 前后风挡丢一项**：`_split_parts("前后风挡除雾都打开")` **压根没拆**（实测 parts 只有一段），走单句 `classify()` 命中 `rear_defogger.open`，前风挡从头到尾没被表达过。**不是「拆了丢一项」，是没拆 + 单句只认一个对象。**
- **I-050 双闪→大灯**：端侧认得 `warning_light` 但判成非本地 → 上云 → **云侧能力面没有 hazard light** → planner 就近挑了 `headlight`。Q8「能力缺席→就近误执行」的完整因果链在这里闭合。
- **I-049 静音→`volume.dec`**：同族，待按同一方法逐条验。

**⚠ 这条判据代码里已经写过一次，当时只修了一处**：`fast_intent.py:1788-1794`（2026-08-04）——
> 「同一个『aircon 对象 + inc/dec』在两个命名点各产一个名字……判据（第二次适用）：**发现根因时要问「同一形态还有几处」**——『改遍了』和『发现了』是两件事。」

那次修了 aircon，**没有问「还有几处」**。今天的答案是 13 处。**这条注释是它自己的反例**，也是本卡存在的全部理由。

**修法方向**：两个出口收敛成**唯一实现**（同 B5 `stream_state.py`、E1 `timewindow.py` 的先例）——`classify()` 应当直接调用 `_to_legacy_name()`，不再维护第二份 if-else。收敛后必然暴露一批「名字变了」的连带（`LOCAL_INTENTS` 里同时收着两个名字的死条目、`VEHICLE_INTENTS` 派生面、对抗语料的期望值），**那些暴露正是收益**。

**⚠ 收敛前必须先建断言**：一条从 `commands.yaml` 派生的源码级守卫——**对每个对象族，两个出口必须产出同一个名字**（同 B6「反例从被测系统自己的知识库派生」）。先让它红，再修，别反过来。

**归档在哪一档**：Q13 是 Q7/Q8 的上游，**排在阶段 3 的最前面**（Q7 之前）。在它收敛之前修 Q7 的极性维度，会在两条不一致的路径上各修一遍。

2. **单次取样不能当基线**。SF4/CD1/CD2 在两次跑批之间**完全翻面**。加 `--repeat` 后 SF4 实测 **0/3**（稳定红，上一次的 PASS 是少数情况），AU2 **1/3**（真方差面）——**差一点就因为一次 PASS 把稳定红降级成方差**。定基线一律 `--repeat >= 3`，报告里按「n/N + 方差标记」读，不报单次结论。

### 两处教训

1. **dry-run 当场劝退了我一条判据**（E5 那条的第二例）。③ 首版判据是「同 `(subject, rel)` 多个不同 object 即冲突」，于是把 `爸妈 --family--> 爸爸` 和 `爸妈 --family--> 妈妈` 判成冲突，**并准备把「妈妈」标成失效——直接丢掉一个真实的人**。修法：③ 只对**单值语义**谓词生效（`works_at`/`lives_at`/`place_of`），`family`/`owns`/`prefers_brand` 天然一对多，排除在外。

#### 实施中途翻出的两件事（都不在原计划里）

#### 实施期的三处判断

**① 「收敛」不是把一条抄给另一条，是把两条的并集写成一份。** 直接让 `wait_confirm`
复用 `wait_slot` 那套会**换一个洞**：`不订/不付/先不/不了` 只在前者词表里、
`不要了/别提醒了` 只在后者词表里。所以按**歧义度**分了 STRONG（子串安全）与
WEAK（只在占据整句时算）两层——WEAK 那条「词占据整句」规则不是删掉，是**作用域收窄到
它真正该防的那半**（「第二天不要去长城」含「不要」、「我吃不了这么多」含「不了」）。

**② `closed_operation_ids` 是被逼出来的第三个字段。** 最初只打算加 `operation_id`，
但 HMI 拿到一条普通 final 时无从判断「刚才那条挂起是不是被这一轮消费掉了」——
猜错就是一条已作废的确认条继续挂在屏幕上等人点（I-017 同族）。**服务端知道，
那就让服务端说**，别让前端推断。同「系统持有的事实绝不让 LLM 答」的形态。

**③ CF5 的尺子改过一次，留痕。** 原期望是第四轮说「已失效/过期/取消了」——那是
**为单槽写的**期望（旧挂起注定被丢弃，至少要说一声）。挂起表落地后旧挂起根本没被丢，
再要求系统说「已过期」就是要求它说一件不真的事。新考点换成结构判据（带 T1 的
`operation_id` 回来 → 先来那条仍可执行 + `closed_operation_ids` 点名关掉它），
比话术判据硬。**这不违反「不为某个模型的问题改案例集」**：那条针对被测对象做不到，
这里是**契约变了、旧期望描述的行为已经不该存在**。

## 5. 动手前的取证清单（每卡通用）

1. **先建红绿迷你集再动码**——接地卡 R1 二期的做法，本批沿用。
2. **两档各跑一次**：两档相反 = 模型方差（档案化、不加 hint）；两档逐字同错 = 系统缺陷（立刻能修）。
