# Android AR06～AR11：工程交付 Goal 与集中验收安排

> 状态：2026-09-10 根据用户“希望 Goal 完成时绝大部分任务已完成”的要求调整执行方案；**尚未启动实施 Goal；本文不授予后续工程的红线操作权限**。
> 关联：[六批总入口](2026-09-09-android-ar06-ar11-execution-roadmap.md)及其中六份详细方案。
> 本文调整任务划分和依赖，不降低原验收条件，不修改 [AGENTS.md](../../AGENTS.md) 的授权规则。本批文档的提交与推送已由用户在 2026-09-10 单独授权，不扩展为后续工程发布授权。

## 1. 采用的执行方式

**默认先设“工程交付 Goal”，集中完成代码、必要回归、工具、候选包和可自动执行的验证；真人与最终发布放到集中验收阶段。** 完整验收另设明确目标。

原方案 `AR06 → AR07 → AR08 → AR09 → AR10 → AR11` 适合表达最终签收依赖，不适合把所有工程任务串成一条等待链。AR07 缺真人不应阻止 AR08 计时、AR09 诊断/渲染修复、AR10 材料和 AR11 规划。

以下两种“前置”必须区分：

- **授权前置**：批准必须早于相应操作；不意味着整个 Goal 开始前就要批准所有后续动作。没获准时先准备具体产物，继续其他工作。
- **技术前置**：例如真实 KWS 基线决定怎样调参。可以先做其他模块，但不能没有数据就把优化结论写完。

用户后续明确要求“实施这些方案”即覆盖方案内普通工程工作的授权，不再每个文件、每次本地测试重新确认。已有明确授权在约定范围内持续有效；不重复询问。涉及红线时只请求尚未覆盖的具体动作，不请求未知 SHA、未知迁移或任意设备操作的空白授权。

## 2. 哪些授权要早准备，哪些可以后置

| 事项 | 当前规则/限制 | 处理时机 | 等待时继续完成什么 |
|---|---|---|---|
| 方案内源码、测试、文档、隔离 checkout、本地提交 | 不属于项目列出的红线；只提交本任务文件 | 后续实施 Goal 明确范围后自主执行 | 无需增加独立审批 |
| 项目依赖与工具 | 项目内依赖可按必要性处理；全局安装/系统配置须授权 | 先核现有工具；优先已有或便携、限定目录方式。确需全局变更时先给版本/路径/用途 | 静态检查、脚本、测试与文档；不能将便携工具误报已验证可用 |
| Android 原生构建 | 现有脚本包含 `/MIR` 删除镜像多余文件，以及 `gradlew --stop` | **首次构建前**核对并一次明确镜像同步范围和资源占用；后续同范围不反复问 | 代码与本地回归、构建材料先完成；不清缓存碰运气 |
| OPPO 验包与普通 App 操作 | 测试机工作需要明确纳入执行范围；同签名安装可保留数据 | 建议开工就明确测试窗口、候选包安装、正常 UI 操作和测试语料范围 | 没有设备时先完成工具/离线验证；设备空闲后自动执行已授权范围 |
| 字号/网络/权限/省电等系统设置、IME/driver 安装 | 系统变更或新安装按项目规则；不能误操作对照机 | 首次需要时合并成一份具体设备操作清单，附原值回读和恢复办法 | 正常设置下的 UI/生命周期测试继续；特殊格暂留未验 |
| 受限 token、`.env`/密钥、数据库 schema/迁移 | 必须具体授权，不能由普通 Goal 隐含放行 | 可后置到实际真栈负例/生产化实施；如果本次目标包含该负例，就应早准备条件 | 离线真实契约反例、代码修复、迁移草案与验收脚本 |
| CI/CD | 必须具体授权 | **本地检查已通过、确切 diff 和成本可审查后**集中处理 | 先交完整本地门禁和 CI 候选补丁/说明，不提前修改 workflow |
| `git push` | 必须单独授权，展示完整 `origin/main..HEAD` | 候选冻结后集中处理；不提前批准未知提交集 | 本地代码、提交、测试、APK/报告 |
| 生产部署 | clean、已提交、main 可达 SHA；dry-run 后授权 apply | 候选及 dry-run 就绪后；可以是工程 Goal 末尾的发布关口 | 未发布代码的离线验证与发布材料；不宣称 B 已在生产通过 |
| 真实车控/商户写/支付、远端数据删除/受控故障 | 通用部署/E2E 授权不覆盖 | 默认排除普通体验测量；必要时精确到用例、对象和清理方案 | 只读场景、隔离假通道、无副作用的契约检查 |
| Xiaomi 对照、真实参与者招募/发消息 | 用户主用设备和对外沟通不由 OPPO 工作自动授权 | 集中验收时安排；邀请文本可提前准备 | OPPO 主验、脚本、计分表与参与者材料 |

上述是安排，不是本轮已经取得的授权。若用户在后续 Goal 启动时明确批准了其中具体范围，按该范围执行，无须到每一步再问一次。

### 2.1 构建授权中容易漏掉的动作

[build_mobile.ps1](../../scripts/build_mobile.ps1) 当前的镜像目标是：

- `D:\Android\builds\xiaozhou-mobile`：mobile 构建镜像；脚本排除其中生成的 Android/.expo 目录。
- `D:\Android\builds\hmi\src`：共享源码镜像。

`robocopy /MIR` 包含目标镜像内的删除，不能只说“构建是可逆的”就跳过用户的删除红线。首次执行前列出这些已解析绝对路径、源目录、排除项和将受影响的文件；取得限定镜像同步授权。该授权不包含仓库源文件、APK 证据、签名材料、共享 CXX 缓存或整目录清空。

构建还必须确认没有其他会话在用同一镜像/Gradle。即使镜像同步已获授权，也不能停止其他 Agent 的进程。需要调整脚本时先做限定自有资源的实现，不把“换 worktree”误当构建资源已隔离。

### 2.2 一次授权的记录方式

记录：用户原话、适用任务、具体路径/设备/用例、允许的动作、明确排除项、恢复要求。后续步骤先查该记录，只有新增动作超出范围才再次提问。不要从“尽量自主完成”推导出凭证、生产部署或系统设置授权。

不需要在写计划阶段收集真实 token、密钥或开通账号；批准材料应先做到可审查，再把批准作为对应操作的最后一步。

## 3. 人工确认与验证能否后置

| 人工事项 | 能否后置 | 原因与安排 |
|---|---|---|
| 常规代码评审、实现细节选择 | 可以集中；普通工程选择无需逐项问 | Agent 先实现/自审/测试，交完整差异 |
| 中文输入通道 | 工程可先做；大量设备自动化之前必须解决 | AR06 先验证已装工具，不能把安装 Maestro 当成中文输入成功；必要时一次人工初始化，之后复用 |
| KWS 真人基线/候选比较 | **不能全部留到优化结束之后** | 阈值选择依赖真实输入；装置就绪后安排一次集中取样。已有同意留存的固定素材可辅助自动重放，但不替代真人/主麦声学路径 |
| 首音声学校准 | **不能在声学时延结论之后补** | 软件排定回调不等于出声；先校准测量装置。独立服务器/客户端分段定位可提前完成 |
| 混合段盲听、最终音质确认 | 可集中到候选稳定后 | 先完成段完整性、队列、停播的自动检查；人耳结果单列 |
| 五名外部用户任务 | 可以后置 | AR10 脚本/材料/计分工具和自动矩阵提前做；Agent 不代填真人数据 |
| TalkBack、系统 200% 字号、真平板与 Xiaomi 对照 | 可集中到后段；已有设备/工具能自动做的先做 | 不可因后置把缺失格记 PASS；同包版本和真实系统条件保持 |
| KWS 生产默认、支持范围、隐私承诺的改变 | 影响实现的决策在实际改变前；不影响部分继续 | 无实验依据时保留默认 A；不静默缩支持范围或改数据留存承诺 |
| AM5 账号/推送/签名供应商与商业条件 | AR11 规划阶段可后置为明确进入条件 | 本轮 AR11 交技术规划；实际接入前才必须落实，不提前实现未知供应商 |

建议把人工参与集中到三个窗口：**开工的必要工具/设备授权；实验装置就绪后的声学取样/校准；候选稳定后的集中验收与发布关口**。这不是保证只发生三次交互：出现新的实测失败，仍可能需要一轮有针对性的取样或决策。

最不合适的做法是先“优化完成”，最后才第一次让真人说话。那会把可能推翻参数和测量方法的证据放到最晚，反而增加返工。

| 批次 | 工程交付必须尽量闭合 | 可以集中到验收阶段的部分 | 不能提前宣称 |

| AR07 | 实验参数入口、真实链路计数/回读、单例/取消回归、统计器、语料协议、候选装置；有有效声学数据就继续完整调参 | 补充说话人、长时负例、最终 prod 选值确认 | 无真实数据时已提高唤醒率；仅做仪器不等于 AR07 完整关闭 |

| AR10 | 入场条件、自动矩阵与脚本、可执行子集及失败修复回流、全部真人任务材料、逐格报告骨架 | 五人执行、缺设备/特殊权限格、最终总体判定 | 材料准备或模拟用户等于外部 UX 验收 |
| AR11 | AM5 五包完整技术草案、依赖/角色/接口/DoD/估算依据、授权与发布/回退材料 | AR10 最终基线校准、人员与供应商落实、业务范围裁决 | Android M5 已实现或已具备正式上线证据 |

AR09 可先在**当时固定的实际默认语音实现**上定位和修复；若 AR07/08 最终选择改变负载，补受影响场景，不把全部 UI 工作重做，也不借用旧包数据。AR11 可以完成技术规划主体，定稿仍需回填 AR10 的实际结论。

## 5. 工程目标的完成判据

工程 Goal 完成时交付完整的候选，而非一张“待人工确认”的任务清单：

1. 已授权、无需外部输入且能够独立完成的实现和必要检查全部结束；不能因为一个人工项等待就提前收工。
2. 代码自审、适用测试/静态检查通过；已有可复现失败要修复或准确说明独立阻塞，不能悄悄归入人工验收。
3. 构建条件/资源/镜像同步已具备授权时，交实际 APK 和 hash/验包结果；缺条件时交可直接执行的构建入口、完整预检结果及所缺的具体条件，不能只说“待打包”。
4. 现有设备和授权可完成的自动用例实际执行；可执行的测试不能为了让等待清单整齐而全部拖到最后。
5. 每项后置工作均给出：case_id、阻塞原因、为何无法自动完成、所需人/设备/授权、已准备产物、直接执行步骤、成功判据、预计操作量与失败后的接续位置。
6. 后置集合冻结并明确标记；区分“实现完成”“自动验证完成”“人工/外部未验”“发布未执行”，不合成一个虚假的完成率。

不承诺未经估算的“完成 90%”。合理目标是**把所有可自动完成的工程项做完，只留下确实依赖真人、特定设备或红线授权的最后几类工作**。AR07/08 的核心改善若缺真实数据，仍属未验证/待决，不能通过更改任务分母把它算成已优化。

若用户设定的是“AR06～AR11 全部通过”的 Goal，就不能按本节的工程就绪判据将它标完成。应在创建 Goal 时明确采用哪种目标，不能执行失败后才悄悄缩范围。

## 6. 推荐的连续 Goal 文本

> 按六份方案和《Android AR06～AR11：工程交付 Goal 与集中验收安排》，执行工程交付阶段。持续完成方案范围内所有已授权、无需外部输入且可独立完成的代码、必要测试、工具、候选构建和自动验证；AR10 完成验收准备及可自动执行子集，AR11 完成生产化技术规划主体。普通实现选择按项目原则自主处理，不逐项重复确认。
>
> 真正等待人工/设备/红线授权的事项先准备成可直接检查和执行的产物，列入集中处理表，然后继续其他独立工作。KWS 与真实首音优化依赖的取样/校准在装置就绪后集中安排；未得到证据前保持生产默认，不编造改善。只有具体动作超出已有授权时才询问，已有授权不重复询问。
>
> 完成时交付代码与适用检查结果、已具备条件的 APK/设备证据、六批逐项状态、发布候选材料，以及最小人工/外部剩余清单。工程目标完成不表示六批完整签收；保留原正式验收矩阵，后续集中验收再关闭相应项目。

这一模板没有授权 push、生产部署、凭证/数据库/CI/系统修改或任意删除。若要把相关操作纳入同一个 Goal，先准备精确范围并取得明确授权，随后在授权范围内继续推进即可。
