# cockpit-agent：落域、拒识、上下文与长会话深度评审及优化方案

**评审日期：2026-09-19｜代码基线：`2f3c574dbbd077437c75c766a340d5afc1b99c5f`**

## 0. 结论与证据边界

我的判断：目前的主要矛盾不是“少了几个 Agent”，也不只是模型不够强，而是**已经有较丰富的能力与安全执行基础，但用户的目标、指代、临时约束、任务状态和真实结果，还没有在所有路径中形成一致的对话状态模型**。因此局部路由、回归用例和业务执行可以分别正确，连续交互仍然不像一个知道前因后果的助手。

应保留现有 manifest / Registry、请求级 capability_ref 白名单、Skill / exemplar、DAG / T2、VAL、执行核验、候选集、Memory、Task Ledger 与测试资产；在它们之间补齐统一契约，而不是重写项目、另造一个万能 Agent，或者把所有问题都交给一个更长的 prompt。

### 本轮做了什么

读取了上述固定提交中的 README、Planner、Engine、ContextManager、SessionStore、T2 Loop、端侧 fast_intent、chitchat、会话约束抽取、reminder manifest、Memory 与评测说明、9 月 19 日 QA 收口记录。另对五组提取后的纯函数/谓词做了本地逻辑复算，文件见 `local_logic_probes.py` 与结果 JSON。

**本轮没有连接用户的生产服务，没有运行完整仓库 pytest，没有真实调用地图/商户/车辆，也没有在 Android 真机采集语音。**本文区分：

- **代码事实**：从指定提交可直接验证。
- **局部复算**：只验证抽出的逻辑，不等于全调用链复现。
- **待真栈验证风险**：代码存在触发条件，是否在实际部署达到该条件仍需检查。
- **目标设计**：建议实现的产品与工程行为，不是对现状的描述。

源码默认值不等于实际部署配置。特别是上下文预算、模型、功能开关与超时，验收必须记录生效配置。

### 不能重复报旧问题

9 月 19 日的代码已经包含告警解除、补槽期间安全陈述让路、规划提前结束时登记输入事实等修复。`technical_failure` 也已经有诚实失败终态；不应再写成“所有规划失败都会伪装成闲聊成功”。候选集、执行账本、数据源事实、操作 ID 寻址、插话保留挂起、同一逻辑覆盖流式与非流式等也都已存在。[S1–S6]

这些是值得沿用的基础。下面关注的是修完具体 badcase 后仍存在的机制边界。

## 1. 当前交互链路与真正的断点

```text
用户文字 / PTT / 免唤醒语音 / HMI操作
  → 端侧确定性识别与端云分流
  → 挂起任务取消 / 确认 / 补槽分支
  → ContextManager：历史 + 记忆 + Focus + 能力目录
  → 候选集 / 执行史 / 来源等确定性事实回答
  → Planner：Skill与范例 + capability_ref受限规划 + 有界重试
  → route_hints及安全终结器
  → 单步流式 / DAG / 有界T2重规划
  → Agent业务结果与执行核验
  → 聚合回答、卡片、动作事实与Focus更新
```

断点并不是“没有上下文”，而是以下几种状态不能等价：

**用户说过什么 ≠ 当前任务是什么 ≠ 上次落到什么 intent ≠ 屏幕上看见什么 ≠ 已经执行了什么 ≠ 现在现实世界是什么状态。**

单个 `last_intent` 和最近几条消息不足以代表这六种东西；扩大它们的存活时间，也不等于解决指代和任务切换。

## 2. 核心发现

### F01｜P0：确认的肯定谓词仍会接受问句形态

**证据**：`engine.py::_confirm_reply` 使用 `k in t and len(t) <= len(k)+2`，词表含“确认、可以、行、嗯”等；`wait_confirm` 分支在云端 `addressed` 判定之前处理。[S3]

局部复算：`确认吗`、`可以吗`、`行吗`都满足该肯定谓词。本轮未执行其前置取消识别与整条语音链，不能据此宣称已在生产造成错误执行，但该谓词确实没有把询问与授权分开。

**修复**：确认应绑定 `operation_id + plan_revision + confirmation_nonce + 已展示的动作摘要`。HMI 点击使用精确寻址；语音“确认”必须对应当前明确展示/播报过的唯一操作。对“可以吗”等可解释为询问的输入，先解释而不执行。乘客短应答、TTS 回声、陈述里的引用不得充当授权。声纹仅辅助对话归属，不替代账号权限与 VAL。

多条挂起并存时，裸“确认”不能静默选择后创建的任务；问一次“确认导航，还是提交订单？”。确认后若门店、金额、目标或关键动作发生改变，旧授权作废并重新确认。

### F02｜P1：Planner 的历史视窗短，而且预算并非硬约束

**证据**：`_CTX_BUDGET` 源码默认 1400 字符；焦点、长期记忆与历史共用该额度。`_render_history` 只取 `history[-4:]`，即 4 条消息，通常约 2 次问答；当剩 1 条时，即使超预算仍整体返回。chitchat 则独立取 8 条消息。[S2,S7]

局部复算：剩余预算为 0，最后一条助手消息 2000 字符，历史渲染仍输出 **2019 字符**。

**影响**：路由模型看不见用户四五轮前的约束，业务 Agent 可能又看到另一段历史；“模型上下文窗口很大”不能弥补装配层根本没传进去的信息。长回答还可能挤占本应保留的任务事实。

**修复**：按完整 exchange 裁剪；为当前目标、未完成义务、用户否定、金额/地点/时间、实体引用与安全状态设受保护结构区。历史摘要与原始消息分开预算。不能为了硬截断而把“不吃花生”切成半句话；超预算保留完整必要事实并删除可再取的内容，必要时诚实澄清。

建议把 2K/4K/8K token 的任务上下文作为实验档位，而不是无证据统一改为某个大窗口。数字不包含独立记录的 system/catalog/tool schema 开销，须按实际模型 tokenizer 或保守估计记账。

### F03｜P1：同类列表的新检索会替换旧列表

**证据**：候选集并非只有名字数组，已有结构化台账；但 `update_focus` 合并键是 `(source_intent, purpose, is_fallback)`，不含查询、任务或稳定列表 ID。同键新组替代旧组。[S2]

例如先搜 A 地附近餐厅，再搜 B 地附近餐厅，两次均为 `nearby.search`。用户问“刚才 A 那批第二家”时，旧组可能已不在结构化候选台账。不同 Agent 菜单共存的修复不等于同能力不同查询也能共存。

**修复**：给每次展示建立 `candidate_set_id / task_id / query_signature / revision / item_id / displayed_at`。HMI 绑定具体展示版本，语音回指结合称谓、时间、任务与明确地点选择；不能只绑定当前最新组。新搜索产生新集合，“换一批”产生相关的新版本，不覆盖仍可引用的旧事实；过期后可说明需重新查询，禁止悄悄换成另一家。

### F04｜P1：焦点、活动路线、安全与临时约束共用短生命周期

**证据**：SessionStore 中 `_FOCUS_TTL=300`。活动路线、候选、session_constraints、安全告警一起保存在 Focus；安全告警虽另有 7200 秒总龄检查，仍依赖先读得到 Focus。[S2,S4]

这意味着 Focus 副本可能在沉默 5 分钟后消失。不能据此断言底层导航一定停止，但“上次还在说的事”与实际正在运行的导航/任务可能脱节。

**修复**：拆开生命周期：短时会话焦点可分钟级；活动任务到完成/取消/业务期限；路线从导航权威状态同步；安全事项按来源与解除事件管理；长期偏好继续由 Memory 管。缓存超时不是事实解除。安全状态需要区分用户自述与真实车端信号，用户一句话不得清除仍然有效的硬件告警。

### F05｜P1：临时约束只是少量布尔值，改口、时间和主体不完整

**证据**：`runtime/session_constraints.py` 只提取 `no_spicy` 与 `no_queue`。前者全句否定优先，后者只有 `True` 写入，没有“可以排队”的 `False/撤销` 通道。[S8]

局部复算：先“我不想排队”，再“今天可以排队，等一会儿没关系”，结果仍 `no_queue=True`；“之前不吃辣，今天想吃辣”被提取为 `no_spicy=True`。

**修复**：将临时约束表示为带 `subject / predicate / value / scope / valid_time / source_turn / supersedes` 的原子事实。不吃辣、不要太辣、不吃川菜不应压成一个语义；“我不吃辣”和“同行的人想吃辣”不能互相覆盖。先保证会话事实同步生效，不能等待异步长期记忆抽取。

### F06｜P1：补槽是保守修补过的启发式，仍非统一的对话行为解析

**证据**：Engine 已有 `slot_shapes`、换题判断和两次补槽重试止损，值得保留。但形状没意见时，仍依赖动作词、问句后缀、搜索/安全词等判据；进入补槽后，对所有 missing slots 使用同一句文本作为值，除 `order_id` 外 `_slot_answer` 不做细分抽取。[S3]

**影响**：“明天早上八点，提醒我拿文件”可能同时包含补充与纠正；“还是后天吧，目的地不变”不是整个新任务；“别买了，先导航去那家”是取消一个动作、保留同一门店实体、开始另一个动作。仅分“槽值/换题”不足。

**修复**：识别 `answer_slot / correct / select / confirm / cancel / pause / resume / new_goal / ask_explanation`，允许一轮多个行为。字段 patch 只更新有证据的字段；补完信息不代表确认执行。提示用户补某个槽时，必须引用任务与问题 ID；新请求不应自动取消旧任务。

### F07｜P1：多诉求完整性仍缺少强结果账本

**证据**：已有窄型多动作漏步重试；`_clause_uncovered` 与 `_goal_value_dropped`明确只做观测。前者按槽位字符串与分句子串比对，零槽动作、改写、隐含条件都可能使其失真。[S1,S3]

**修复**：每个肯定目标有 `goal_id`，计划步骤和回答证据都指回目标。每个目标必须落到“完成 / 澄清中 / 等确认 / 部分完成 / 受限 / 不支持 / 已取消 / 待异步完成”之一。禁止用一个成功的查询覆盖整句尚未完成的提醒、导航或下单需求。安全敏感多步仍按依赖和独立性决定是否先完成部分，不能盲目追求“能做的全做”。

### F08｜P1：T2 用 capability/intent 级别判重，粒度过粗

**证据**：`_completed_observation_steps` 按成功 observation 的 intent 记已完成；未声明 `retry_same_intent=True` 时，`_drop_completed_replan_steps` 移除同 intent 新步骤，即使新参数不同。Loop 的 observation 默认只在 Agent data 声明该值时传播例外。[S1,S9]

局部复算：已成功查询深圳天气，后续广州天气仍被标为重复。是否出现在具体产品旅程取决于该旅程是否经过 T2 以及 Agent 是否声明例外。

**修复**：读取复用键至少包含 capability、规范化参数、相关实体/状态版本和 freshness；不同地点/时间/查询不是重复。写操作必须单独使用服务端任务动作 ID 与幂等键，不能简单“去掉去重”。请求结果不确定时先对账再决定重试。

此外 `loop.summarize` 只保留前 12 个 data 字段、speech 前 160 字符，属于按位置压缩而非按决策价值压缩。应改为 capability 声明的决策投影，保留关键事实、单位、来源、时间和下一步所需字段；大对象按引用再取。[S9]

### F09｜P1：受话、理解、支持性和执行失败仍需更清晰分账

**证据**：`ptt` 被 `is_voice_input_source` 纳入语音静默拒识面；显式输入虽有一次重试，最终仍可输出空 speech 的 rejected。确认/补槽先于这一受话闸。另一方面，技术失败、无授权与取消未匹配已分成不同终态，不能抹掉这些进展。[S1,S3]

**修复**：明确五个不同问题：是否对助手说；听清了什么；想做什么；当前设备/账号/供应商是否支持；执行后发生了什么。PTT 的按下不自动构成动作授权，但主动交互后不应无解释消失；明显背景噪声可不播报，界面应有可理解状态。免唤醒才把“不打扰人”作为主要默认。

### F10｜P2：能力目录、route_hints 与上下文相关性仍耦合

**证据**：`_always_include`保留 fallback、有 hints、core 的 Agent；保护项可超过 catalog 预算；默认 top_k=20 在当前规模通常不触发筛选。sticky places 是否让路与 clause-scope hint 命中有关。Skill 与 exemplar 的检索主要用当前原话。[S1,S2]

**修复**：先统一 capability 的适用条件、效果、排除条件和所需上下文，并把 hint 扫描与 prompt 候选目录分离；再测试能力级检索，而不是当前 14 个 Agent 先粗暴裁成 3 个。候选集需按每个目标分别召回并合并，显式保留当前挂起任务、对象引用、安全与兜底。上下文“是否相关”不应由“恰好有哪条规则命中”决定。

### F11｜P2：长期记忆基础存在，缺口更多在读取与会话连接

**证据**：Memory 已有 semantic/episodic/procedural、时序替代与 OwnerKey；Planner `_recall` 仍是 top_k=3，episodic 仅在若干历史指代正则下开启；renderer 最大 5 条不意味着实际召回 5 条。chitchat 又独立召回 4 条。[S2,S7,S10]

**修复**：不要再建第二个向量记忆库。现有 Memory 增强成任务/实体/时间感知检索，按需二次召回；读取返回“找到 / 无结果 / 后端不可用”三态。显式当前约束优先于历史推断偏好；用户纠正需可追踪替代。关闭长期个性化记忆，与当次会话的必要任务状态应有独立产品开关；当前 `mem_on`会同时影响历史/焦点装配，需核对 UI 对用户的实际承诺。[S2]

### F12｜P2：评测资产很多，但不能用旧模型全绿证明当前体验

**证据**：正式对抗基线说明明确写着 2026-08-09、`f0af9c0`、DeepSeek 147/147；同 SHA MiniMax 为 141/147、eligible=false。这些是 `case@layer`证据单元，不能理解为今天的 147 个独立真实会话。仓库也明确提示 canonical 自污染、域分布偏斜及排除分母问题。[S11]

**修复**：以当前生产模型、当前代码与配置重建统一基线；路由、任务、语音和长会话分层统计。对正确性的主裁决改为满足约束的真实结果；多个 Agent 路径都能正确完成时，不应强行只有一个金标域。

## 3. 建议的目标架构：在现有编排中增加统一对话契约

不新增一个串行必经的“超级对话 Agent”。先用现有 Planner 的一次结构化生成同时产出语义解释与计划，只有对象确实缺失、歧义较大或校验失败时追加一次有界读取/修正。确定性明确车控仍走低延迟通道。

```text
输入证据 InputEnvelope
  ├─ 文字 / PTT / 免唤醒 / UI操作 / S2S
  ├─ 认证主体、会话、设备、时间、当前展示对象
  └─ ASR/说话人/声学证据（可缺失；缺失不伪造）
          ↓
对话行为与目标 DialogueDecision
  ├─ addressed / audio_uncertain / background
  ├─ new_goal / answer / correct / select / confirm / cancel / resume
  └─ 多个 goal、限定词、否定、条件、引用与来源原文
          ↓
上下文与对象绑定 ContextCapsule
  ├─ 本轮事实 + 活动任务 TaskFrame
  ├─ 候选集合 Entity/CandidateStore + 展示版本
  ├─ 车端/供应商权威状态 + 时间戳
  └─ 必要历史摘要 + 按需 Memory 召回
          ↓
现有能力规划 capability_ref → DAG / Skill / 有界T2
          ↓
契约校验、scope、安全、确认、幂等与VAL
          ↓
现有Agent执行 / 任务服务受理 / 查询真实结果
          ↓
GoalOutcome 与 AnswerContract
  └─ 每个诉求有结局，每个执行性表述有证据
          ↓
事件化更新TaskFrame、候选引用、短期状态与Memory
```

### 3.1 统一对话决策的最小字段

```yaml
# 提议的数据契约，并非当前仓库已有字段。
dialogue_decision:
  turn_id: server_turn_id
  acts: [correct, new_goal]
  addressed_state: addressed
  task_ref: task_123
  base_revision: 4
  goals:
    - goal_id: g1
      action: modify_route
      target_ref: route_1
      source_span: "先不去机场了，改去酒店"
      constraints:
        - predicate: arrive_before
          value: "19:00"
          source_turn_id: previous_user_turn
          scope: this_task
    - goal_id: g2
      action: find_charging
      source_span: "看看酒店附近能不能充电"
      depends_on_goals: [g1]
  unresolved_refs: []
  proposed_patches: []
```

schema 限定输出形状，不代表语义一定正确。仍须检查引用是否存在且属于当前认证会话、变更是否允许、旧约束是否被显式推翻。模型只能提出 patch，服务端负责验证与落账。对跨设备、重复请求、过期 UI、并发回复使用 revision/CAS；不能 last-write-wins 覆盖另一条有效更改。

### 3.2 “主意变了”应修改对象，而不是重做任务

推荐规则：

- “改成周日”只 patch 日期，其余约束继承。
- “不，是副驾”修正目标音区/座位，不修改温度与原始动作方向；已执行错的动作是否恢复须按策略和实际状态判断。
- “这家不要了，换刚才第二家”变更门店后，商品可迁移部分与不可迁移部分分开；重新查菜单和价格，旧预览/确认失效。
- “先别下单，导航过去”阻止订单写操作，保留门店实体并创建导航目标。
- “算了”仅在唯一显著任务明确时撤销该任务；多条同等显著任务时澄清，不替用户猜取消哪条。

### 3.3 把“请求去重”与“动作幂等”分开

读请求的复用应建立在：

```text
capability + normalized_args + entity/state_revision + freshness_policy
```

写请求应建立在：

```text
server_task_id + action_id + authorized_plan_revision + idempotency_key
```

用户主动“再买一杯”是一笔新动作，不可被旧 action 去重；网络重发同一个 action 则不能再创建一单。订单状态未知先查询；已知失败可按合同重试；已完成不可重复。不同城市天气、不同时间预测与同一门店的新菜单版本也不能按 intent 一概拦掉。

## 4. 当前已接入能力的语义分工与优化重点

以下能力依据仓库 README 与对应接口描述整理；“期望”是建议统一的产品行为，不代表每个例子已通过真栈测试。[S6,S12,S13]

| 能力 | 应承担的角色 | 重点边界与对话优化 |
|---|---|---|
| edge vehicle / media | 确定性车控、媒体操作 | 先分执行、状态查询、原理询问、引用和条件；明确位置与相对量。“刚才那个再高一点”需对象证据；“这首歌叫什么”不是播放命令。 |
| navigation | 从明确实体发起、修改、取消路线 | 找地点与启动导航分开；路线实体、目的地、途经点、策略及到达时限独立更新；GPS、POI与关系地点有明确优先级。 |
| nearby | 搜索、筛选、比较地点候选 | 保留每批候选与原始查询；约束能力不足要说清，比如无法验证实时排队；不能用“推荐得像”代替可验证筛选。 |
| trip-planner | 行程规划与结构性修改 | “第二天改成室内”只改相关日程；单次改路优先活动导航，除非用户修改的是旅行计划；时间冲突和约束保留可解释。 |
| charging-planner | 沿途或目的地补能 | 复用活动路线与电量事实，区分距离最近、绕路最少、能否到达及有无实时状态；不能默认导航到第一个站。 |
| info | 有时效的天气、新闻、行情、赛事、联网检索 | “明天呢”要绑定正确专题；日期和数据时点写清；“那边”绑定目的地而非随机历史城市；财经/比赛不是天气追问。 |
| deep-research | 用户明确需要的多来源深度任务 | 异步任务 ID、主题修订、取消、进度、完成后追问绑定报告；普通一句知识问答不应自动升级成长任务。 |
| reminder | 提醒/待办的创建、查询、变更、完成、取消 | 现有时间、位置、重复与待办能力保留；按标题引用先取真实对象；赛事提醒消费真实赛程时间。未接入的任意外部触发不能承诺“已持续监控”。 |
| scene-orchestrator | 场景定义、激活、修改、退出及恢复 | “创建一个模式”不等于立即激活；只修改指定参数；退出模式需读取实际状态，不能覆盖用户期间手动改变的设置。 |
| road-safety | 驾驶状态与车辆异常的安全建议 | 安全前提不能被聊天遗忘，但也不必每轮长篇重复；对查询停车点/求助等有益请求继续完成，而非全局阻断。 |
| manual-rag | 车型限定的说明、规格与操作指导 | 区分当前读数、推荐值与告警处置；车型/版本/配置不适用时不得用另一车说明书强答；引用证据与“不知道”可见。 |
| parking-payment | 停车费用与确认后的支付入口 | 账单、停车会话、金额与确认版本绑定；二维码展示不代表已支付；以可信支付状态回执确认完成。 |
| mcp-bridge | 准入工具，含现有麦当劳/瑞幸真实商户链路 | 门店→菜单/规格→确定性价格预览→确认→未支付订单→付款入口各有对象状态；地图 POI 不是商户内部门店 ID；各供应商取消能力不对称时如实处理。 |
| vision | 当前授权图像的感知与相关问答 | 没有有效画面就不能猜“这个灯”；引用帧版本，过期需重拍。结合 manual/safety 可回答，但图片文字不能变成工具指令。 |
| chitchat | 社交、情感、稳定知识、解释与诚实兜底 | 不伪装成已执行，不从两轮文本推断不存在的任务；系统事实继续走既有确定性读出口，按需读取任务上下文再解释。 |

### 边界测试不应只做单一金标路由

“机油灯亮了还能开吗”可有不同内部路径：先安全建议后手册，或者手册 Agent 内先走同一确定性安全出口。只要车型适用、结论与证据正确、没有错误动作，不能仅因为 agent_id 不同就判失败。

“前往 A 附近找能停车的餐厅，先别导航”即使选对 nearby，也可能因为擅自启动导航而失败。**路由路径是诊断维度，目标完成与约束遵守才是最终结果。**

### 最容易混淆的表达，应做最小对比对

| 表达 A | 表达 B | 必須区分 |
|---|---|---|
| 打开空调 | 空调怎么打开 | 执行 vs 指导 |
| 帮我把窗关上好吗 | 关窗会影响通风吗 | 礼貌请求 vs 效果询问，不能只看问号 |
| 导航到第二家 | 第二家离这里多远 | 写动作 vs 读事实 |
| 取消订单 | 订单取消了吗 | 变更 vs 状态查询 |
| 记住我喜欢清淡 | 今天吃清淡一点 | 稳定偏好 vs 本次约束 |
| 周五去广州 | 改成周五去 | 新任务 vs 更新旧任务 |
| 现在查明天是否下雨，再建提醒 | 之后一旦下雨就通知我 | 即时条件计划 vs 持久事件订阅 |
| 创建午休模式 | 开启午休模式 | 定义 vs 激活 |
| 这家不要了，换第二家 | 不要换第二家 | 局部取消/替换 vs 禁止变更 |
| 你说“确认”是什么意思 | 确认提交这笔订单 | 引用/解释 vs 授权 |

## 5. 拒识与澄清：把“不打扰”和“不装懂”分开

### 5.1 终态建议

| 终态 | 实际含义 | 推荐反馈 |
|---|---|---|
| background / not_addressed | 不是在对助手说 | 免唤醒默认无播报；PTT界面可说明未识别到对助手的请求 |
| audio_uncertain | 转写质量不足 | 只针对听不清部分重问，不让用户重讲整段 |
| ambiguous_goal / unresolved_reference | 听清了，但有两个合理目标或不知指谁 | 明确列出区别最大的一两个选项 |
| unsupported | 理解目标，但当前能力不支持 | 说明边界，提供真实可用替代，不凭空建立后台任务 |
| permission_missing | 已接入但当前主体无权限 | 指向正确的能力授权，不让用户去开无关系统权限 |
| policy_blocked / precondition_failed | 安全或业务前置不满足 | 解释原因，并继续可安全完成的独立子目标 |
| dependency_unavailable / planner_failure | 服务或规划失败 | 保留原请求与有效参数，提供重试，不归咎用户没说清楚 |
| partial / pending / uncertain / completed | 不同业务进度 | 与真实动作/任务状态一致，不把“受理”说成“完成” |

终态应扩展当前 `contracts` 与 issue/recovery 体系，而不是新建一套与客户端不兼容的错误字典。

### 5.2 输入源差异

文字提交与 UI 操作表示明确的交互意图，但不授权任意动作。PTT 表示主动采集交互，可能有背景音，适合低打扰的可见反馈，不宜全部静默。免唤醒/全双工需融合可用的声学与文本证据：回声相关、唤醒窗、说话人状态、轮次连续性、转写稳定性；这些信息没有就标 unknown，不能用一个自报置信度替代。

不能把“知识问答超出车控范围”当拒识，因为 chitchat/info 已承担开放域能力。也不能把“句子里有指令词”当受话证据：乘客或电台同样可能说“打开空调”。

### 5.3 澄清应有对象、进展与有效期

当前 `clarify_resume=1` 与空计划转 talk 能避免重复澄清，却不能确保用户回答真的完成了消歧。[S1,S3]

建议澄清卡携带 `clarification_id / task_id / target_field / candidate_refs / expires_at`；点击的是选择结果而不是仅发回一段由模型生成的自然语言，再让 Planner 从零猜。

限制的应是“对同一个问题没有进展的重复追问”，不是全任务总共只能问一次。缺日期、补完日期后缺门店，是不同问题；每次都问“你到底想干什么”才应止损。

## 6. 上下文与长会话

### 6.1 四层状态，复用而不推倒已有 Memory

| 层 | 保存什么 | 生命周期与权威 |
|---|---|---|
| Turn Evidence | 本轮原话、输入源、引用、修正、ASR证据 | 本轮；原始输入与解析结果分离 |
| Active Dialogue / Task | 用户目标、参数、未完成义务、挂起与澄清、展示候选 | 到任务结束/显式取消/业务失效；不是随聊天沉默整体清空 |
| Session Episodes | 已结束话题的摘要与事实索引 | 按会话策略；保留原始轮次链接，不让摘要覆盖事实 |
| Long-term Memory | 跨会话偏好、实体、关系、常用行为 | 沿用现有隐私、OwnerKey、时序替代与删除治理 |

车辆、导航、商户订单的当前状态仍由各自权威系统持有；以上层保存的是引用与最近观测，不是擅自成为第二套业务数据库。

### 6.2 ContextCapsule 的读取策略

默认传当前明确目标、活跃任务的最小快照、最近完整问答、相关实体引用与必要约束。出现“刚才另一批”“上周那次”“恢复出发前设置”才有界读取相应索引。不同 Agent 取得同一快照的授权投影，而不是各自重新猜历史。

优先级建议：当前用户明确要求 > 当前任务明确约束与更正 > 有效业务状态 > 与当前任务有关的历史事实 > 长期明确偏好 > 低证据推断。安全和权限是另一条硬约束轴，不作为普通偏好参与加权；来源有冲突时保留冲突与依据，不以“最近一句”自动覆盖传感器。

### 6.3 摘要不能改变授权和事实

摘要仅是导航索引/辅助阅读。关键数值、单位、否定、主体、时区、日期、订单/门店/路线引用、待确认动作与执行回执应结构化保留。摘要生成必须给出源 turn_id；更新摘要时验证这些受保护字段不丢失、不变号、不把“未执行”改为“已执行”。摘要与原始事实冲突时回读原文，不让摘要决定写动作。

### 6.4 真正的长会话验收

同一认证会话完成 50/100 个用户轮次，穿插不同 Agent、插话、拒识、失败、菜单刷新、手动改车态和较长沉默；再问旧任务、旧候选与修正后的约束。不只测“最后还能聊”，而要测“旧对象还找得到、已取消的不会复活、未完成的不会失踪、旧价格不会被当最新、别人的偏好不会串给我”。

断线重连、应用恢复与会话跨端迁移分开测试。HMI 与 Android 默认独立会话不能强行共享所有焦点；只有明确恢复同一个 conversation/task 时迁移必要状态，并按新设备重新校验能力和权限。

### 6.5 一条代表性长会话

初始：去广州某酒店，19:00前到，途中找能充电且可吃晚饭的地方，暂不启动导航。随后查询天气，讨论歌单，筛选两批餐厅，补充“今天不吃辣、预算人均80”，切到手册问答，再说“上一批第二家，排队可以，晚到十分钟也行”。

正确结果应能区分：哪一批候选；“排队可以”撤销哪条约束；到达期限改为19:10但目的地不变；选店不自动下单；天气与手册话题没有覆盖活动出行任务。沉默十分钟再说“继续刚才的行程”时，应重新校验车端位置、电量、路线与商户事实，继承仍有效的用户目标，而不是盲信旧缓存。

## 7. 回答一致性：避免“落对域但答非所问”

`AnswerContract`建议包括：本轮要回答的问题、每个 goal 的状态、可引用 evidence_ref、允许的执行性表述、不可核实的字段、需要用户补充的唯一关键点。

一个合格回答不一定长。例如：“已找到两处顺路充电站；其中A多绕3分钟。你说不想排队，但我拿不到实时等位数据。还没有开始导航。”胜过三段泛泛建议。

目标相关性校验不应每轮串联另一个大模型重写。先用确定性判据：实体是否对应、单位/金额是否来自结果、状态是否允许说已完成、所有 goal 是否都有终态。只有复杂多结果聚合或明显冲突时，才在一次已有合成中增加受限检查；不能静默把错误行动通过润色变成成功。

`issued / accepted / observed_success / observed_failure / unknown` 分开记录。现有执行核验和审计出口要复用；本方案不是声称仓库没有它们，而是要求新的对话状态与所有答复路径消费同一份事实。

## 8. 分阶段实施计划

以下是实施顺序与验收门，不是工期承诺。先把兼容的修复放回现有模块，再逐步引入数据契约；每一步都保留独立开关、旧 schema 读兼容和可回滚版本。

### P0：先修会误确认、丢真值和错误复用的窄问题

| 工作包 | 建议修改位置 | 交付与验收 |
|---|---|---|
| W01 确认歧义修复 | `engine.py::_confirm_reply`、pending入口、客户端确认契约 | 问句/引用/背景应答不授权；多pending裸确认不误选；确认与补槽不混；安全/幂等旧测试不回退 |
| W02 上下文预算保真 | `context.py::_render_history/_render_memory` | 完整exchange；预算0/长消息边界；受保护事实完整；按实际请求记录渲染规模 |
| W03 约束改口 | `runtime/session_constraints.py`及消费方 | 支持撤销、不适用、主体与时间；“之前不吃、今天想吃”不被旧否定锁住；模型抽取异常不覆盖旧真值 |
| W04 读复用与写幂等分离 | `planning.py`、`loop.py`与既有Executor/ledger接口 | 同intent不同参数允许；同写动作重发仅执行一次；结果未知先对账 |
| W05 当前生产基线 | 现有eval、journey及观测链 | 固定SHA、配置、主模型、embedding与工具版本；保存逐轮输入、实际状态与结局，报告不把基础设施失败从分母里悄悄删除 |

P0退出条件：上述局部复算用例变为符合期望；对应真实输入路径通过；没有确认、权限、重复副作用回退。零次危险错误是该测试样本上的门槛，不是对所有未来输入的零风险保证。

### P1：建立统一任务与引用状态，主攻连续体验

| 工作包 | 建议修改位置 | 交付与验收 |
|---|---|---|
| W06 DialogueDecision | 扩展 `models.py` / Planner输出，新增薄解析与校验模块（提议） | new/answer/correct/select/confirm/cancel/resume 分开；必要时多行为同轮；普通车控不多一次云模型调用 |
| W07 TaskFrame | 扩展现有SessionStore及Task Ledger对接，不另立业务订单库 | 任务、目标、待解决问题、plan_revision、明确终态；多pending合理寻址；并发变更CAS可测 |
| W08 候选集合版本 | `context.py`、`candidate_query`、客户端选择载荷 | 同intent多批候选共存；旧卡点击定位旧对象并检查时效；无证据不选最新冒充 |
| W09 生命周期拆分 | Focus存储及活动任务/导航/安全状态适配 | 沉默10分钟不丢任务；过期缓存会重新验证；结束/取消不可复活；安全解除按来源处理 |
| W10 澄清续接 | 现有clarify结构、`engine.py`、HMI/Android消息契约 | 系统给的选项可直接消费；不重复猜自然语言；同一问题无进展才止损 |

P1退出条件：跨域插话、同域多列表、纠正、取消/恢复、10分钟静默的核心旅程全覆盖；已有实体/任务不是靠LLM编ID。每个新字段都必须有生产者、持久化、消费者、测试四项，不能只有prompt看得见。

### P2：统一能力语义与回答质量

| 工作包 | 建议修改位置 | 交付与验收 |
|---|---|---|
| W11 Capability Contract | 各Agent manifest / SDK / Registry schema | 定义效果、适用前提、读取/写入、所需上下文、数据有效期与结果投影；不是把全部内部工具暴露给Planner |
| W12 多目标闭环 | Planner、DAG/T2、Aggregator | 每个goal都有结果或明确阻塞；同一句已完成与未完成分别答；schema正确不能掩盖漏目标 |
| W13 受话与失败分类 | Edge/Cloud入口、现有contracts与UI | PTT/免唤醒/文字分别验收；ASR失败、理解歧义、不支持、无权限、工具失败分账；挂起分支覆盖同一受话边界 |
| W14 AnswerContract | AgentResult/StepResult与聚合器 | 实体、时间、金额、来源和执行结论可回指；系统不因流式提前说话而宣告未验证结果 |
| W15 hint与目录解耦 | `route_hints`、`context.py`、现有skill/exemplar评测 | 不因规则退役而改变能力可见性；每条hint有收益/副作用证据；优先迁移会话相关规则而非一次删光 |

P2退出条件：14类Agent边界矩阵和最小对比对通过；多步完成率和语义保持率提升，同时不增加危险误执行。允许多个内部路径达成正确结果；延迟与成本必须单列。

### P3：长会话、跨端恢复与迭代优化

| 工作包 | 建议修改位置 | 交付与验收 |
|---|---|---|
| W16 ContextCapsule | ContextManager与SDK读取门面 | Planner与Agent消费同一任务快照的授权投影，必要时按引用读取；子模块不能各自编造历史 |
| W17 摘要/Memory检索 | 现有Memory、会话索引与摘要模块（提议） | 摘要保真、时间感知、事实纠正、无结果/不可用区分；不另建第二套记忆平台 |
| W18 长会话与恢复 | 现有journey runner、客户端恢复协议 | 50/100用户轮次；静默、断网重连、恢复、人物切换、旧卡/旧确认、工具状态变化；隔离不同会话 |
| W19 模型与检索消融 | 现有模型pin、eval、观测与灰度 | 单变量比较主模型、上下文、hint、范例、检索；按风险分层选择，不凭公开排行榜换模型 |

### 工程实施纪律

每个工作包先增加能复现原问题的失败测试，明确历史兼容窗口，再做小提交；每次变更只推进一个行为面。老的单步流式、DAG、T2、确认恢复、补槽恢复、端云混合、S2S escalate 都必须覆盖，避免“只修 handle，不修 handle_stream”的重复问题。复杂性的预算应写进设计：不要为普通一句车控串行增加“域分类→上下文重写→二次规划→模型审查”四次LLM。

## 9. 评测与指标

### 9.1 建议四层评测

1. **纯契约/确定性测试**：预算、约束patch、TTL、候选版本、确认寻址、revision冲突、幂等、时间/单位。绝大部分无需LLM。
2. **固定状态的语义测试**：正确域/允许域集合、目标、槽、否定、条件、对象绑定、澄清与拒识。每个核心领域含口语、难负例与最小对比对。
3. **状态驱动的多轮旅程**：真实业务fixture和用户干预；目标最终状态可判定；不能只用另一个LLM判断“回答听起来不错”。
4. **真栈/真语音验收**：锁定配置，真实ASR、PTT/免唤醒/S2S、噪声/TTS回声/打断、移动/位置变化、供应商延迟与失败；高风险动作使用安全沙箱、干跑或可控测试设备。

新增语料先进入独立留出集，不立刻同时写入exemplar。训练/检索资产、修复集、留出集、线上回放应分开记录；同一个语义模板的改写不能一半进训练、一半冒充泛化测试。

### 9.2 指标不要只看一个“落域准确率”

| 指标 | 分母与观察点 |
|---|---|
| Goal completion | 可支持且允许执行的用户目标；同时单列unsupported，不能随意删除难例 |
| Whole-turn completion | 所有必要子目标均有正确结果/正确阻塞的轮次，不能靠只完成一半算成功 |
| Constraint fidelity | 有明确约束的目标；禁止、主体、地点、时间、数量、金额与单位逐项核对 |
| Reference resolution | 有回指的轮次；正确绑定set/item/task版本 |
| Clarification utility | 澄清后确实获得必要信息并推进的比例；重复问同一件事单列 |
| False reject / false accept | PTT、免唤醒、文字、UI分开；非受话与不支持也分开 |
| False confirmation / wrong side effect | 全部待确认与写操作；样本中任何严重错误都阻断发布 |
| Grounded answer | 实体、时点、数值、来源、执行事实是否有证据；流式已播内容也计算 |
| Long-session retention | 在第10/30/50/100用户轮次、沉默和恢复后的约束、对象与任务保持 |
| Recovery success | 服务失败/过期/断线后能否恢复同一目标，而不是靠用户重新重述全部参数 |
| Latency / cost | 有效首反馈、完成P50/P95、模型调用次数、token、工具调用；按任务档位分层 |
| Stability | 同一语义在重复采样、独立进程、生产配置下的波动，不只选最好的一次 |

推荐初始建设量：300–500个有明确结果判据的语义场景，另配20–30条跨域长旅程。它们是规划量，不是已有基线数量。先保证危险边界与高频问题覆盖，不为凑数量复制模板。

可把核心受支持任务的目标完成率≥95%、实体绑定正确率≥98%作为讨论起点，但必须先取得真实分布基线再冻结；不同任务难度、ASR条件和能力边界不能混为同一个指标。任何比例都应带样本数和置信区间，不把这些建议目标说成当前水平或承诺收益。

### 9.3 如何定位究竟是哪层错

对同一badcase做四组对照：

- 实际ASR文本 vs 人工校正文本：隔离语音转写损失。
- 实际上下文 vs 人工补齐的正确ContextCapsule：隔离装配/召回缺口。
- 实际Planner输出 vs 人工正确计划：隔离语义规划问题与业务Agent问题。
- 实际工具结果 vs 固定可信fixture：隔离外部数据与供应商波动。

再对候选路径、模型与hint做单变量消融。只有“人工补齐上下文仍明显失败”才适合主要归因模型理解；只有“正确计划也回答错”才应主要修Agent或聚合器。

### 9.4 外部方法参考及适用范围

Anthropic的context engineering实践强调高信号上下文、按需读取、结构化笔记和压缩，而不是无限扩窗口；本方案采用这些原则，但不照搬其编码Agent工作流。[E1]

LongMemEval提供信息抽取、多会话推理、时间推理、知识更新与弃答五个维度，可作为本项目Memory验收分类；论文的数值结果不能外推为本仓库现状。[E2]

τ²-bench强调用户也能改变共享世界状态。本项目应因此加入用户手动调车态、改导航、完成支付、供应商菜单变化等干预场景，而非只让模拟用户连续发送静态文字。[E3]

## 10. 最终建议

先做 W01–W05，然后以 W06–W10 为本轮主干。对用户体验收益最大的变化是：

**同一件事有稳定对象，改口能精确修改，插话不丢主任务，确认不靠猜，已做/未做/做不了各有准确结局。**

在此基础上，再做能力契约、按需检索与模型优化。不要先训练一个更大的落域分类器，也不要把每个badcase都变成一个新route_hint；同样不必一次性删除现有规则与安全闸。让系统先持续知道“正在为谁处理哪件事、用户改了什么、证据是什么”，模型能力才能转化为连续体验。
