## 二、优先修复清单

这里的 **P1** 表示建议下一轮优先修复的正确性或隐私边界问题；**P2** 表示条件性故障、异常恢复或长期稳定性问题。不是在宣称这些问题已经在实车造成事故。

### F01：VAD 缺少异步推理的代际隔离

**位置：** `mobile/src/core/voice/vad.ts`，重点是 `start()`、`accept()`、`infer()`、`stop()`。

当前 `infer()` 在调用 `await this.session.run(...)` 之前检查 `running`，但返回以后直接更新 `h/c`、更新端点状态并读取当前 `this.cb`。与此同时，`stop()` 只是清空状态和重新赋值 `chain`，并没有让旧的 Promise 链失效。

由此可以出现：

```text
旧一轮 VAD 推理尚未返回
→ stop()
→ start()，建立新状态和新回调
→ 旧推理返回
→ 覆盖新一轮 h/c，并调用新一轮回调
```

**本次复现结果：旧推理触发了 1 次新生命周期的回调，并覆盖了新建状态。**

外层 `HandsFreeController` 已经有 epoch，但不能完全挡住这个问题：旧推理读取的是 VAD 对象里**后来替换的新回调**，新回调自身的 epoch 检查可以成立。当前免唤醒关闭时调用的是 `vad.stop()`，后续开启还会使用这个 VAD 实例。

**建议修复：** 给 VAD 自身增加 generation；入队时捕获 generation，推理前后均复查。不能仅把 `chain` 换成一个新的 Promise。`dispose()` 还需要明确在途推理与 session 释放的顺序。

**验收要求：** 用延迟返回的原生推理替身，覆盖 `stop→start`、连续开关、`dispose` 中推理返回，证明旧结果既不能改新状态，也不能触发新回调。

### F02：系统音频中断绕开了已经建立的统一停播语义

**位置：** `core/voice/audioFocus.ts`、`stopPlayback.ts`、`handsFree.ts`、`useHandsFree.ts`。

当前系统 interruption 开始、旧音频设备不可用等处理，核心动作是：

```ts
speechController().stop()
```

但是，你自己的 `stopPlayback.ts` 已明确解决过一个更复杂的问题：**必须先处理 HandsFree，再停止 SpeechController**。否则 SpeechController 收尾触发 `onSpeechEnded → ttsEnd()`，可能把免唤醒状态推进 FOLLOWUP，打开续问窗口。

另外，**S2S 的播放器不经过 SpeechController**，这一点在 `handsFree.ts` 中有独立的播放事实包装和停止路径。只停止主 TTS，不能证明 S2S 播放、在途音频和回路状态也已停止。

因此这里不是“没有监听音频焦点”，而是：

> **界面停止按钮已经使用统一停播语义，系统音频事件却还在走单一路径。**

Android 对焦点丢失后的播放行为有明确要求，但系统可能自动静音，并不等于应用内部的回路状态、网络接收和续问窗口也自动正确收尾。这里需要验证的是应用状态，而不能只凭“听起来停了”判断通过。

**建议修复：** 将系统音频中断接入应用级统一入口，区分“自然播完”“用户停止”“系统抢占”。系统抢占时，统一处理主 TTS、S2S、续问窗口及采集策略；恢复焦点也不应无条件恢复旧内容。

**验收要求：** 分别在主 TTS、S2S、LISTENING、FOLLOWUP 状态下制造焦点丢失、耳机断开和系统中断，检查声音、播放器、FSM、采集与上行五个维度，而不只检查一个 `speaking=false`。

### F03：服务器配置的双存储写入不是原子操作

**位置：** `mobile/src/core/config/storage.ts`。

现在的保存顺序是先写 SecureStore 中的 token，再写 AsyncStorage 中的服务器配置；加载时则分别读取后组合，没有共同版本或提交标记。

假设原配置是：

```text
服务器 A ＋ token A
```

切换到 B 时：

```text
token B 写入成功
→ 服务器 B 写入失败，或中途进程终止
→ 下次加载得到服务器 A ＋ token B
```

**本次通过注入第二次写入失败，复现了这个混配结果。**

这不一定表现为“保存失败”那么简单：新凭据可能被发送到旧地址。实际风险大小取决于旧、新服务的归属及 token 权限，但地址与凭据不能失去绑定。

**建议修复：** 配置体积较小时，优先考虑一个安全存储中的规范化配置对象；保留双存储时，需要共同 revision、提交标记、串行写入及加载时一致性校验。状态只能是“完整旧配置”“完整新配置”或“未配置”，不能是混合配置。

**验收要求：** 对每个写入点注入失败、中断和并发保存，验证恢复结果；不要只测全部存储操作成功的路径。

### F04：定位关闭没有贯穿在途请求的撤销边界

**位置：** `mobile/src/core/location/appLocation.ts::refreshMeta()`，以及 SessionCore 的请求准备和发送阶段。

`refreshMeta()` 在开始时检查定位开关，但等待权限、等待坐标结束后，没有重新检查开关或授权代际，直接返回位置元数据。

本次复现的是：

```text
定位开关开启，开始取坐标
→ 等待过程中用户关闭定位
→ 坐标返回
→ refreshMeta 仍返回非空位置元数据
```

**这证明了定位桥接层的撤销缺口，不是一次真实网络泄露的抓包证据。**

进一步看发送侧，异步准备返回后主要检查请求是否仍存在；队列发送前检查请求有效性和 operation 有效性，没有在这条路径上重新验证位置授权。

这里可以参考你已经做好的视觉链路：视觉存在 capability signal、请求 signal、取消边界及上传后的有效性复查。

**建议修复：** 定位也使用授权代际或 capability signal，至少覆盖“开始取值、取值返回、进入发送、离线队列补发”四个时点。撤销后，尚未发送的位置数据应被移除，或让依赖该位置的请求明确失败。

**边界要写清：** 已经发送给服务端的数据不能声称撤回；尚未发送的数据则不能因为“取值时曾经授权”而无限期继续发送。

### F05：录音重启后可能跳过重采样

**位置：** `mobile/src/core/voice/recorder.ts::startNative()`。

每次启动录音都会把 `resampler` 设为 `null`，但 `_deviceRate` 保留上一轮值。首帧只有在采样率与 `_deviceRate` 不同时才重新创建重采样器。

因此，当两次录音回调都返回同一个非 16 kHz 采样率时：

```text
第一次 48 kHz：创建重采样器，正常输出 16 kHz
停止
第二次 48 kHz：重采样器被清空，但采样率没有“变化”
→ 不再创建重采样器，原始数据直接向下游传递
```

**本次模拟 48 kHz、100 ms 输入：第一轮输出 1,600 个样本，第二轮输出 4,800 个样本。**

需要强调：当前 `onAudioReady` 已请求 16 kHz，**本次没有证明你的某款手机实际会返回 48 kHz**。这是非目标采样率兼容分支中的确定缺陷，不是“所有手机第二次录音都会坏”。

**建议修复：** 每次启动重置输入采样率状态，或按“实际采样率＋当前重采样器是否匹配”决定是否重建。

**验收要求：** 覆盖 16k、48k、44.1k 的重复启停及路由切换，检查输出样本数、时间连续性与识别音频时长。

### F06：WebSocket 补发异常后，队列可能失去恢复和顺序保证

**位置：** `hmi/src/ws.mjs`，这是 Android 复用的传输层。

当前 `_flush()` 遇到发送异常时，把当前请求放回队首后退出；没有在此路径启动恢复。而 `send()` 只要看到 socket 为 OPEN，就直接发送新请求，不检查是否还有旧队列。

本次模拟结果：

```text
A、B 离线入队
→ 连接打开，补发 A 时 send 抛错，但 socket 仍显示 OPEN
→ A、B 留在队列
→ 用户再发 C
→ C 发出，A、B 仍滞留
```

这属于**注入发送异常后的逻辑复现**，不是对 React Native 原生 WebSocket 出错频率的判断。

**建议修复：** 明确 flush 失败后的传输状态和恢复动作；存在未处理队列时，新请求不能无解释地越过旧请求。对于“是否已写出无法确定”的情况，也不能仅为了保持补发就盲目重试有副作用的命令。

**验收要求：** 增加“补发失败后连接不关闭”“失败后再次发送”“失败与取消同时发生”的顺序测试。

### F07：KWS 线程退出超时后，不能继续把全局 running 当作同一生命周期

**位置：** `mobile/modules/kws/android/src/main/java/com/xiaozhou/kws/KwsModule.kt`。

当前实现比早期版本更稳：解码线程在锁内重新读取原生对象，释放时也尝试 join。但 join 超过 1 秒后只是记日志，后续仍可能重新加载并把共享 `running` 设为 true。

条件性风险是：旧线程尚未真正退出，却在新加载之后读到 `running=true`，从而继续消费新队列。与此同时，join 后仍要进入同一把锁，因此 **1 秒 join 超时不等于整个 release 最多阻塞 1 秒**。

**建议修复：** worker 使用独立的停止标记或 generation；旧 worker 未确认退出时，不允许开始下一次加载。超时应进入明确的不可用状态，而不是只留日志后继续。

**验收要求：** 用可控的慢解码/阻塞替身和原生压力测试覆盖加载、释放、重复启停。这里不能只靠 JS 层单测签收。

## 三、架构评审：主方向正确，问题在边界没有完全统一

### 1. 值得保留的设计

**应用级单一宿主是正确的。** `AssistantProvider` 持有会话和语音运行时，页面主要负责展示；`InteractionScope` 统一记录路由、前台、焦点等事实。这比每个页面各自开一套录音、WebSocket 和语音控制器更可控。

**麦克风租约设计值得保留。** `micBus` 把共享录音设备和使用者生命周期分开，避免 PTT 停止时顺带关掉免唤醒所使用的麦克风。底层 recorder 也已经处理了权限等待期间的代际取消，不能把这一部分笼统评价为“生命周期没做”。

**请求身份先于异步准备建立，也是正确的。** 定位、视觉准备前就登记请求，取消时可以撤回；离线补发前通过 `canSend` 再检查有效性，确认操作还会校验是否已关闭或过期。

**S2S 与执行主链的边界没有被混在一起。** 当前 S2S 自答有自己的气泡和播放生命周期，需要执行时回到正常主链，而不是在 S2S 会话内直接增加执行通道。这个方向应继续保持。

### 2. 当前架构的核心缺口

现在不是“缺少状态机”，而是**不同资源的撤销和结束语义还不一致**：

| 资源或事件 | 当前较好的部分 | 仍需统一的部分 |
|---|---|---|
| 主会话请求 | 身份登记、取消、排队有效性复查 | 普通离线请求的时效与副作用策略 |
| 视觉 | capability、AbortSignal、迟到结果处理 | 完整设备并发矩阵 |
| 录音 | 租约、启动取消、真实采集状态 | 重启采样率边界 |
| VAD | 串行推理、共享端点判据 | 在途推理的生命周期隔离 |
| 播放 | 用户停播入口统一处理两路声音 | 系统抢占仍绕过统一入口 |
| 定位 | 预算、缓存年龄、来源记录 | 授权撤销与迟到结果隔离 |

这些差异可以直接从相关实现之间看出来。修复方向应是补齐现有边界，而不是再叠加一套平行框架。

### 3. 共享代码需要逐步脱离 HMI 目录，但不是本轮第一优先级

Android 的 `@shared/*` 当前直接指向 `../hmi/src/*`。复用协议、请求归属、端点与语音回路判据是好事，但“共享核心归在某个客户端目录里”，会让依赖关系与实际所有权不一致。

我的建议是：**先修正确性，再逐步抽出平台无关的协议、状态机和纯判据。** 不需要现在一次性迁移所有共享模块，更不需要为了目录整齐改动一批已经稳定的行为。

## 四、语音体验评审：链路完整度不错，声学结论仍不能由代码替代

### 1. 现有语音链路已经做了不少有效防护

PTT/ASR 已经考虑了录音先行、握手前音频缓冲、单 final 守卫、备用模型、批处理超时、快速按下松开、取消和迟到回调。PTT 的 final/error 路径也会释放本轮会话，因此不能只看到 ASR 内部某个 cleanup 没有直接停麦，就判定一定泄漏。

但下一阶段应把关注点从“有没有兜底”转向：

> **这次走了哪条兜底、用户等了多久、是否多上传了音频，以及最终是否只产生一次有效输入。**

### 2. 不能把文本回声过滤等同于声学验收

当前代码已经有播报参照和疑似回声转为草稿核对等防护；仓库待办也明确把乘客闲聊、新闻播报、本 App 播报时按住说话等，列为需要真人和背景声源的验收场景。

我的判断是：**这部分仍是产品可用性的关键门槛，不能用文字注入测试或几次安静环境演示替代。**

建议固定包后分别记录：

| 维度 | 应记录的结果 |
|---|---|
| 唤醒 | 漏唤醒与单位背景时长误唤醒分别统计 |
| 自身播报回灌 | 误采纳次数、重复发送次数、误开启续问窗口次数 |
| 插话 | 从用户开口到真正停止输出的时间、误打断次数 |
| ASR | 主模型成功率、备用模型触发率、最终失败率 |
| 恢复 | 电话、耳机切换、退后台返回后的首次录音成功情况 |

这些是建议采用的验收指标，不是本次已经测得的数据。

### 3. 首音指标必须区分软件时间点与真实声学时间点

`first_pcm`、`play_scheduled` 很有诊断价值，但不等于扬声器已经出声。仓库待办仍把外部时基下的首音声学校准列为需要真人与设备的事项。

建议同时保留三种时间：用户动作/端点到发送、发送到首片 PCM、用户说完到扬声器首音。否则优化了一个软件打点，未必改善用户听到的等待。

## 五、UI、交互与长期性能评审

### 1. 不建议继续大改整体视觉结构

当前 ChatScreen 已是独立移动端呈现层，包含聊天记录、语音层、FocusDock、舞台、紧凑欢迎态、字号与动效策略；用户自己发送后的跟底、读取历史时不被强拉回等，也已有专门处理。

**本次没有对当前 APK 做截图逐屏检查，所以我不对光球质感、模糊效果或动画流畅度给分。** 接下来比重画界面更有价值的是验证几个任务是否真正清楚：

- 用户能否区分“停止播报”“取消任务”“结束收音”。
- 网络中断后，能否理解“尚未发送”与“发送结果未知”。
- 待确认、待补槽、位置授权同时出现时，能否理解自己正在回应哪件事。

这些应进入固定包用户验收，而不是仅由开发者观察界面是否“看起来合理”。

### 2. 行车档需要约束操作风险，而不只是放大按钮

当前代码已经区分行车与泊车状态下的目标尺寸和呈现方式。下一步应该继续检查任务层面的负担：错误恢复是否需要长时间读屏、是否出现多处竞争焦点、重要确认是否会被聊天与语音层重复表达。

这不是要求现在就把手机客户端按量产车机标准重做，而是避免把“行车档 UI”误认为已经完成驾驶场景验证。

### 3. 长会话性能仍需要单独验证

`AssistantProvider` 使用整份 store 订阅；持久化虽然只保留最近 50 条消息，但这不限制当前内存会话长度，`confirmLog` 快照也不是按这 50 条消息直接裁剪。

不过，**我不建议立刻做一轮全面 memo 化。** 仓库已经把渲染放大列为已知工程项，并提醒 React Compiler 可能覆盖部分情况，应先测再改。

建议先建立 50、200、500 条消息的稳定压测数据，同时记录 JS 更新、掉帧、内存与输入响应；有证据后，再拆分热状态订阅、稳定列表依赖和裁剪关联表。

此外，VAD 目前通过 Promise 链不断排入推理任务，没有像 KWS 那样显式设置积压上限。建议至少暴露积压长度和处理延迟，并定义落后过多时的处理方式，而不是让音频处理延迟无声增长。

## 六、定位、隐私与执行安全

### 1. 定位来源和等待预算的改进是有效方向

当前定位已经优先使用系统 LocationManager 各 provider 的结果，旧 APK 再回落到 Expo/GMS；策略上区分缓存、新取值和陈旧回落，并记录来源、年龄和等待时间。这样能把“回答慢”和“位置错”追到具体取值路径，而不是笼统归咎于导航或模型。

但是，陈旧坐标仍可能携带年龄上行，把能否用于“此刻位置”的判断交给服务端。**天气、附近搜索和导航起点，不应默认使用同一个可接受年龄。** 建议把位置新鲜度要求写成任务契约，尤其是在接入真实导航执行前。

### 2. 视觉隐私实现比“卸载组件就算关闭”更扎实

视觉模块区分准备、相机实际采集、上传等事实；原生相机活动由独立观察报告，不把组件卸载直接当作硬件关闭；取消后也会阻止依赖该结果的请求继续走。

这套模式值得用于修复定位撤销，也适合作为其他敏感能力的参考。但它还需要完成设备上的异常矩阵，尤其是视觉与免唤醒、S2S 并发、权限拒绝和进程中断。当前待办表也保留了这些格子。

### 3. “未知执行结果”不能只靠手动重发解决

你已经正确地区分了断线前已发送的请求和断线期间排队的请求，也避免自动重发已发送、结果未知的轮次。

但接入有副作用的实际操作后，还需要进一步区分：

| 请求类型 | 建议的未知结果处理 |
|---|---|
| 天气、搜索等只读请求 | 可以明确提示后重试 |
| 设定某个绝对目标值 | 先确认操作的幂等语义 |
| 相对调整、支付、开关执行等有副作用请求 | 优先查询状态或核实结果，再决定重试 |

当前普通离线请求没有像确认 operation 那样的业务有效期检查；“还能发送”不一定等于“现在仍该执行”。这应作为连接真实车控前的设计门槛，而不是把所有离线补发都判为错误。

### 4. 历史记录清除应有可验证结果

当前聊天快照以 JSON 形式写入 AsyncStorage，`clearHistory()` 会吞掉删除异常。不能因此断言已经发生数据泄露，但**“界面记录清空”和“持久化数据删除成功”是两件事**。正式分发前，应明确历史保留、账号切换、清除失败和重新启动后的表现。

## 七、构建与发布评审：工程包和正式产品包还需要明确分界

### 1. `prod`、`release`、正式签名是三个不同维度

当前构建脚本明确记录：release 仍沿用模板 `debug.keystore`，正式签名留给 M5；`-Release` 与 `-Variant prod` 也是独立参数。

这在受控工程验证阶段可以是明确的阶段性选择，但**不能把“prod release APK”直接等同于可正式对外分发的包**。Android 官方也明确区分调试签名和正式发布签名，调试证书不适合作为正式发布凭据。

建议将正式分发入口单独固化，至少校验最终 APK 的签名、非调试属性、variant、代码 SHA、网络策略和诊断能力，而不是只看文件名。

### 2. 诊断入口已经做了隔离，不应重复报旧问题

当前操作型诊断要求显式 dev 变体；生产包开发者选项解锁只开放只读取证能力。`voice-spike` 也已加变体检查，参数只作为预填，操作需要按钮触发。

这里的后续重点是**最终产物回读验证**，不是再提出“所有调试深链都能直接录音”的过时结论。

### 3. 当前 APK CI 不能承担完整发布门禁

`mobile-apk.yml` 是手动触发的 debug APK 构建；模拟器离线冒烟默认关闭，而且明确只证明启动、路由和本地卡片渲染，不证明真实后端整链。这个范围划分是诚实的，但正式发布需要在它之外增加固定候选包的验收。

另外，原生插件只打包 ARM ABI，而 CI 冒烟配置是 x86_64 模拟器。这需要明确验证所选镜像的 ABI 与转译能力，**不能简单断言必定装不上，也不能默认必定兼容**；Android 的部分官方镜像确实支持 ARM 转译。

## 八、测试评审：现在需要补的是故障交叉覆盖和固定包证据

仓库中的历史记录已经有较大规模的测试通过结果，例如 9 月 14 日记录的 mobile **97 suites / 1,020 passed**。但那是特定旧基线的记录，**不是本次对当前 HEAD 的复跑结果**。

下一轮不应只追求测试数量继续增长，而应补齐以下类型：

| 测试层 | 优先补什么 | 通过应证明什么 |
|---|---|---|
| 模块单测 | F01、F03、F04、F05、F06 的故障注入 | 异步迟到、写入失败和异常补发不破坏不变量 |
| 原生与桥接测试 | KWS 慢解码、录音启停、推理释放 | 不产生跨代 worker、迟到采集或资源状态失配 |
| 系统事件测试 | 焦点抢占、耳机切换、后台返回 | 两路播放与语音回路一致收尾 |
| 会话集成测试 | 取消、补槽、确认、断网、重连的组合 | 不串请求、不误确认、不隐式重放副作用 |
| 固定包声学测试 | 唤醒、插话、回声、拒识、首音 | 用户实际听到和感受到的体验成立 |
| 固定包 UX 测试 | 多页面、折叠姿态、长错误、字号、外部 App 返回 | 状态可理解、关键操作可达、不会误操作 |

当前基线保留的待办总表中，仍能看到 KWS 真人 A/B、首音声学校准、ASR/S2S 回退听音、视觉并发、部分权限与横屏验证，以及 AR10 固定包用户验收。应该用对应证据逐项销账，而不是仅凭“AR01～AR09 工程批完成”判定整体验收完成。

特别建议把每次验收固定为同一组身份：

**客户端源码 SHA＋APK 哈希＋构建变体＋原生模型版本＋服务端 release＋设备/系统版本。**

这样才能区分“同一 APK 的后端行为变了”“原生能力没随 JS 更新”和“测试装置自身失败”。

## 九、建议的下一轮推进顺序

| 批次 | 重点 | 完成标准 |
|---|---|---|
| **第一批：正确性修复** | F01～F04 优先，F05～F07 随后；不夹带 UI 大改 | 原仓库真实模块测试补齐；对应故障注入由失败转为安全结果 |
| **第二批：固定包验收** | 系统音频、声学、视觉并发、长会话与关键 UX | 同一候选包取得可回读的设备与用户验收证据 |
| **第三批：按分发目标生产化** | 正式签名、账号/服务授权、隐私生命周期、发布流水线 | 明确工程验证包与正式分发包的边界，产物可验证、可升级 |

我不建议现在把以下工作放到第一优先级：重写 Kotlin 客户端、全面搬迁共享目录、再增加一套语音状态机，或重新设计光球视觉。它们都不能直接解决本次发现的核心问题。

**最终评价：当前 Android App 的架构基础是可以继续投入的，真正需要提升的是“状态变化后，旧事情是否还能继续生效”的控制能力。先把旧推理、旧授权、旧配置、旧队列和旧线程这几类边界收紧，再用固定包完成系统与声学验收，比继续增加功能更能提高它的实际可靠性。**
