# demo-dqt1fu：麦当劳选门店成了死循环

- 状态：已落地（2026-10-17，线上 `663ab0ee`，落地记录见 §5）。用户：「demo-dqt1fu 这一轮的会话有问题，你要修复其中的问题」。提交、推送、
  部署与真栈验证沿用既有授权；真栈验证只走只读菜单（`mcd.menu` / `luckin.menu`），不建单。
- 证据：云端 collector 只读拉取的 8 轮（`/api/sessions/demo-dqt1fu/turns` + 每轮 `/api/turns/{trace}`），存在本机暂存目录，不进仓库（含用户原话）。

## 1. 现象（2026-10-16 22:58–23:00，线上 `252cab57`）

| 轮 | 用户 | 系统 |
|---|---|---|
| 1 | 帮我查一下我附近的麦当劳有什么可以点单的？ | 周边搜索 + `mcd.menu`：「找到多家可用的麦当劳门店，请选择一家。」（选店卡，挂起补 `store_hint`） |
| 2 | 第一个。 | 同一句追问 |
| 3 | 选择麦当劳门店：麦当劳深圳前海科兴天地餐厅（点按钮） | 同一句追问 |
| 4 | 麦当劳深圳前海科兴科学园店。 | 追问两次没接上被放弃（C3-D），重新规划 `mcd.menu`，又是同一句追问 |
| 5 | 选择麦当劳门店：麦当劳深圳前海科兴天地餐厅（点按钮） | 同一句追问 |
| 6 | 帮我查看离我最近那家麦当劳的菜单。 | 换题、重新规划，又是同一句追问 |

| 8 | 瑞幸咖啡(前海科兴7栋店)这家瑞幸咖啡，我要看看菜单 | **被还挂着的麦当劳选店追问吞掉**，又问了一遍选麦当劳门店 |

用户自始至终没看到麦当劳的菜单。

## 2. 根因

1. **门店线索拿错了店**（第 1 轮）：执行器 `_hint_store_from_plan` 从本轮周边搜索取 `items[0]` 当 `store_hint`，日志
   「store_hint 取自本轮 nearby.search（沙县精品小吃(老兵大厦店)）」——搜「麦当劳」的第一项是一家沙县小吃。官方门店检索按这个词查不到，
   退回默认门店列表，于是出选店卡。周边结果里本来带着这次搜的是什么（`_candidate_label` = 麦当劳），执行器没看。
2. **麦当劳的选店没有续跑**（第 2 / 3 / 5 轮）：瑞幸出选店卡时把候选门店（官方 `deptId`）存成服务端草稿，用户回答时从草稿里挑、按身份续跑
   （`luckin._store_choices` / `_resume_store_choice`）。麦当劳只出卡、要一个 `store_hint`，回答之后拿名字重新查官方门店、按子串匹配：
   - 「第一个。」：桥的候选集解析把它解析成「麦当劳深圳前海科兴天地餐厅」，却写进了这条能力的 `candidate_slot`（`item_query`，**商品**查询槽）——
     选店卡与菜单共用 `mcd.menu` 这个来源，桥分不清这份候选是门店还是商品；`store_hint` 里还是「第一个。」，查门店又是多家；
   - 按钮「选择麦当劳门店：X」：剥前缀后按子串在官方门店里匹配，仍然出多家（门店名互为子串时，比如正店与同名甜品站，子串匹配同时命中）。
   选店卡明明带着门店身份（`storeCode`），解析却只比名字。
3. **换题判据漏了这一句**（第 8 轮）：`store_hint` 没有声明槽值形状，「瑞幸咖啡(前海科兴7栋店)这家瑞幸咖啡，我要看看菜单」不以动作动词开头、
   不是问句，于是被当成麦当劳门店的答案。请求在逗号后的第二个分句里。

## 3. 改动

1. **执行器**：给商户补门店线索时，只取名字里带这次周边搜索词（结果自带的 `_candidate_label`）的那一项；一项都对不上就不补，不拿别家冒充。
   没有搜索词时保持原行为（第一项）。城市照旧补。
2. **麦当劳选店续跑**（与瑞幸同构）：出选店卡时把展示的那几家官方门店存成草稿（`select_store`，带原请求的槽）；`menu` / `prepare` 解析门店之前
   先试续跑——回答（剥掉按钮前缀）按 `candidate_ref` 同一份判据（全等 → 序号 → 唯一包含）在草稿的候选里挑，挑中就按这家门店继续，
   请求槽从草稿恢复（桥误写进 `item_query` 的店名随之作废、误带的候选 id 清掉）；挑不中就丢掉草稿、照常按名字解析（用户可能说了另一家）。
   `candidate_ref` 补一个直接吃候选列表的入口（`resolve_items`），判据不复制。
3. **槽值形状 `place_name`**（零领域词，`slot_shape.py`）：门店 / 地点名是一个名词短语，不是一句话——剥掉句末句号 / 感叹号后，含分句符、疑问词、
   新检索词或超长 ⇒ 判换题；序号与店名都不定案、交回通用判据。长度上限 32：要装得下按钮那句「选择麦当劳门店：麦当劳深圳前海科兴天地餐厅」
   （21 字）与带分店注记的长店名。**按槽名兜底**（`DEFAULT_SHAPE_BY_SLOT`：`store_hint` / `store_name` → `place_name`），不在 `servers.yaml`
   逐条声明：`slot_shapes` 算在能力 ABI 里，四条商户能力还是旧契约，逐条声明会让冻结迁移清单对不上（第一版就这样撞了契约测试）；这两个槽名只在
   商户能力里出现、到哪都是「一个门店名」，兜底与声明等价。
4. **瑞幸选店续跑同一根因**（这次会话没走到，顺手收口）：裸「第一个」回答瑞幸选店卡时，桥同样把它当错位槽挪进 `item_query`、清掉 `store_name`，
   而瑞幸的续跑只认店名全等。改为与麦当劳同一份判据（全等优先，再序号 / 唯一部分名）；回答被挪进 `item_query` 时只认全等，对不上就把草稿原样放回。

不做：瑞幸门店打烊时的话术（第 7 轮如实）。「周边搜『麦当劳』为什么第一家是沙县小吃」起初当成高德排序记在这里，复测查明是周边 Agent 把
「麦当劳」换成了「美食」，见 §5.3。

## 4. 验证

- 单测：执行器按搜索词挑线索（第一项不是该品牌 / 都不是 / 没有搜索词）；麦当劳续跑（序号带句号、按钮、店名全等、唯一包含、挑不中照常解析、
  草稿属于别的操作要放回、`item_query` 被桥误写时恢复）；`place_name` 形状正反例（四句真实原话）；换题判据接上形状。
- 变异：去掉按搜索词挑、续跑不恢复请求槽、形状不剥句末标点、形状不判分句符。
- 真栈（只读）：同一串原话在新会话里重放，要求第 1 / 2 轮就看到菜单、按钮选店一次成功、第 8 轮的瑞幸请求不被麦当劳挂起吞掉。
