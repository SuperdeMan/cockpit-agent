### 5.2.3 槽值保真：下发前的原话回查（v1.28，QA 卡 Q12）

规划/执行分离解决的是「谁有权产生副作用」；它不解决**「产生副作用时用的那个值对不对」**。
planner 产出的槽值是**自由文本的转述**，而转述会丢限定词——下游拿到的是一个
**看起来完全合法**的值，没有任何东西能发现它比原话少了信息。真栈原样：
「明天下午四点提醒我开会，**三点半**再提醒我一次」→ `time_text="明天三点半"`
（日留下了、段位丢了）→ 落成**次日 03:30**，而话术说的是「下午 15:30」。

- **判据是「比原话少了什么」，不是「有没有值」**。落点 `runtime/slot_fidelity.py`
  （唯一实现），在 `executor._resolve_slot_refs` 里接线——那是**下发前的最后一道**，
  三条执行路径（executor 尾链 / engine D0 / loop T2）都经过它。
- **逐维补，不是整值判**。要求「整个槽值是裸时刻」的首版对 `明天三点半` 直接放行
  ——**防御要一路防到真正会被拿去用的那个维度**（CLAUDE.md §6 的时间版）。
- **三道闸任一不成立就原样返回**：值必须是可解析的时间短语形态；它必须能在原话里
  **唯一定位**；限定词只能取自紧邻或同句更早的一个**带时刻的**时间短语
  （「早上跑完步，提醒我三点半吃药」里的「早上」修饰的是跑步，不继承）。
  贴着 `周三`/`15号` 这类本机制不解析的日期词时**整体让路**——回填错等于系统替用户
  改了他说的话，比不回填糟得多。
- **服务端权威解析出来的槽位（`_trusted_slot_refs`）跳过**：那些值不是转述，
  拿原话覆盖它们等于取消 provenance。

同批把 §5.2.2 第 3 条「一切旁路路径与主路径同闸」补成第三次应验，且形态是新的：
`loop.py` **传了函数却漏了 `ctx`**——跨轮门店锚定、城市补全、本机制在 T2 单步流式
那条路上**静默不生效**。**「挂点被调用了」和「挂点拿到了它要的东西」是两件事**，
症状完全相同（无日志、无报错、只是不发生）。修法照旧不是「下次记得」，
是把覆盖面变成断言：每个 `_resolve_slot_refs` 调用点必须三个参数，注入验红过。

配套一并收敛的是**中文时间词的三份实现**（reminder `timeparse` / `_sdk timewindow` /
info `weather`），唯一声明落 `runtime/cntime.py`。收敛当场照出三个活缺陷：
`早晨八点` 在一份里是 08:00、另一份是 **20:00**；`晚上12点` 在一份里是次日零点、
另一份留在**中午**；`晚上12:00` 与 `晚上12点` 在**同一份实现里**给两个答案。
英文日词（`tomorrow`）进同一张表，`weather.py` 因此不再把「扫不到日词」与
「说的是今天」合成一个 `return 0`——那是 I-041 的完整根因。

### 5.2.4 省略式开关的确定性消解（v1.29，QA 卡 Q7）

「打开天窗」之后说「不用了，关掉」——**这一句要做什么，完全由「上一个对象 × 这个动作」
决定，没有任何需要模型判断的东西**。交给 LLM 只是引入方差：同一句话三次取样给出三种结果，
其中一次是**声称「好的，已为您关闭天窗」而 action 为空**（说了没做）、一次**反向执行**。

- **事实源是执行账本，不是新存储**（`conventions.md` §9.24）。
  （⚠ 2026-08-19 校正：原文还写着「§5.2.5」，而当时**根本没有 §5.2.5 这一节**——执行账本只在版本记录 v1.27 里。悬空编号的代价在下一人占用它时才兑现：v1.30 新增的 **§5.2.5 是候选集聚合问答**，读者点过去会看到另一件事。**判据：引用一个还不存在的编号 = 给未来埋一条错引用；新增编号前先搜它被引用过没有。**）焦点态
  （`update_focus`）**只由云侧规划轮构建**，端侧本地快路径那 40% 的车控动作一个都不在里面
  ——所以「从焦点取对象」这条路对最常见的车控轮次天然失效。真正的事实源是 Q6 已经落库的
  轮次 `actions`；缺的只是**读侧**（同一个 proto 的两份客户端实现，一份读了一份没读）。
- **同轮那半走端云 meta**。混合路径下端侧先执行本地那半、把剩下的碎片上云，而碎片可能
  **没有对象**（「关闭空调然后打开，按顺序执行」上云的是「打开，按顺序执行」——对象在
  同一轮的**另一个组**里）。端侧把本轮真执行掉的动作名随请求带上；**入口每轮先剥同名键**，
  它是执行器签发的内部事实，不是客户端输入。
- **确定性消费方是一条计划出口**（`plan_mode=focus_deterministic`），零 LLM。
  三样东西各有确定来源、缺一即 fail-open 回正常规划：**对象**来自执行账本、
  **操作**来自本轮原话的显式开关词、**能力**来自权限过滤后的 catalog 且必须唯一。
  产出的是普通 `Plan`，照常过步骤校验 / Executor / VAL / `require_confirm`
  ——**不是绕过执行链，是不让模型参与一个它无从判断的选择**。

> **判据：「把事实写进 prompt」和「让事实决定结果」是两件事。** 中途取过一次干净读数
> ——只补事实源、不做确定性接管时，跨轮那条已经稳定正确，而同轮那条**仍然 0/3**，
> 且失败形态从「我不能帮你执行操作」变成「您想把空调温度设成多少？」：
> **模型确实看见对象了，但动作没落对。**

边界与代价：判据是 `fullmatch` 且**不含任何对象词/领域词**——放宽后「打开周杰伦的歌」
会被上一轮车控焦点劫持成另一个对象的动作。焦点采用**「刷新」而非「填空」**语义
（最近执行事实赢，并清掉账本证不了的位置/agent 字段）：只填空会把「取不到对象」变成
**「稳定用陈旧对象」**，那更糟。契约 `docs/conventions.md` §9.26。

### 5.2.5 候选集上的聚合问答（v1.30，QA 卡 Q2）

用户看过一份候选列表之后问「哪家最晚关门」「这两个一共多少钱」——**答案已经在系统
手里**（`Focus.candidate_sets` 的结构化 items），需要的是**算**，不是想。

**它不该落给任何 Agent，因为落到哪个都是错的**：产出那份列表的 Agent（`nearby.search`）
会重搜一遍、答的是**新一批**；详情能力（`nearby.detail`）只看得见一个；兜底闲聊手里
根本没有那些数，只能编。**这不是路由问题**——没有任何一个 Agent 站在能回答它的位置上。

⇒ 判定与回答都放在**编排层、plan 构建之前**（`orchestrator/cloud/candidate_query.py`，
确定性纯函数、零 LLM、零网络）。它与既有的「零候选时确定性弃权」守卫**方向相反、
判据同源**，构成同一个判据面的正反两半：

| 方向 | 条件 | 结果 |
|---|---|---|
| 负 | 引用了候选，**而一份都没有** | 诚实弃权（防编造） |
| 正 | 引用了候选，**而候选就在手里** | 确定性回答（防瞎猜） |

**判据必须三段同时成立**，因为这条短路看见的是全部流量、命中即整轮不进 Planner：
① 在引用当前候选（词表通道**或**「句中点到 ≥2 个候选项名字」的名字通道——后者从候选集
派生，不是又一张词表）；② 算子与维度**一起**匹配（分开匹会让「附近最近的加油站」这种
新检索命中「距离/最小」）；③ 不是新检索。没有指示词的说法（「最晚关门的呢」）**刻意
不劫持**——宁可漏说法，不误伤。

**数据不全时仍由它确定性回答**（「这份列表没带营业时间」），不回落 LLM：回落等于把
一个「我没有数据」的问题交回去让它编，而那正是要消灭的形态。覆盖不全时把覆盖度一起
说出来（「9/10 家带营业时间」），别让部分读起来像全部。

**算子有三种，第三种是两条守卫之间的缝补上的**（v1.32）：最值、合计、**序数取值**
（「第 N 个多少钱」）。前两种只认聚合，而零候选那条弃权守卫只在**一份都没有**时触发
——于是「**有候选的单项查询**」两头都不管。真栈实证：菜单卡就在上一轮，
「第七个多少钱」落到兜底闲聊，**商品名和价格都被编了出来**。
⇒ **凡是「系统持有的事实」，判据面就得是闭合的**；留一条缝，模型就会从那条缝里
编一个出来。第三种算子唯一的收窄手段是**序数与维度问句必须紧邻**
（「第二天第一个**景点**多少钱」问的是行程内部，序数后是实质名词就放行）
——同一条「算子与维度一起匹配」的纪律，只是这次用在序数上。

**两条支撑性纪律**（它们是这一节真正的前提，缺一条能力就是空的）：

1. **候选项白名单是与产生方的契约，字段名不许猜。** 白名单里每个键都必须是某个产生方
   真的产出的名字，否则「声明留住了营业时间」而实际一个字都没留——**而这种缺陷会被
   测试自己的 fixture 掩盖**（fixture 一起用了那个不存在的字段名，断言当然过）。
2. **可被指代的候选必须进 `data`，不能只进 `ui_card`。** `ui_card` 是给人看的终点，
   `data` 是给下游消费的结构化事实。只进前者 = 这份候选对系统不存在。

契约与逐条判据：`docs/conventions.md` §9.1b / **§9.27**。

### 5.2.6 候选集下发面：文本入口与按钮入口收敛（v1.31，QA 卡 Q10）

§5.2.5 处理的是「对这份候选做聚合」——那类问题**没有 Agent 站在能回答它的位置上**，
所以拦在编排层。本节处理的是另一半：「我要这份候选里的**那一项**」——这类问题
**必须**落到 Agent（下单要过商户的选品、核价、规格链），编排能给的是**指到哪一项**。

**真栈把立卡时的说法改了两处，两处都改变了该做什么**：

1. 卡上写「按钮路径带结构化引用」——**并没有**。按钮送出的也只是一句中文；
   v1.31 时是 `在<门店>点一份<商品全名>`，v1.37 起菜单选项带上可读序号
   `在<门店>点第 N 个：<商品全名>`，仍不是客户端 product_code。
2. 卡上写「文本路径靠 LLM 从原话解析」而实测**它经常是对的**——焦点块早就把
   `最新候选=1:甲/2:乙…` 渲染进 prompt。但那里只有 **5** 项而菜单有 20 款：
   「第七个」在 prompt 里根本不存在，真栈稳定 0/3。

⇒ 判据由此确定：**序数落到哪一项是系统持有的事实，不该让 LLM 数**——
与「墙钟不让 LLM 答」「执行账本不让 LLM 重构」同一条。

机制是一条**按 `context_scopes` 门控的下发通道**（与 G8 活动路线同款）：编排把最新
那一组候选的**最小投影**注入声明了 `candidates` scope 的步，Agent 侧做确定性翻译，
**之后按钮与语音都先闭合到同一个候选项，再进入同一条商户链**。

三条纪律，每条都有它挡住的具体事故：

1. **默认投影只留序号与名字，菜单可额外留有界商品 id。**「哪些事实值得跨轮留住」与「哪些字段可以离开编排」是
   两个问题——桥是第三方信任级、连位置 scope 都没有，候选集不能成为绕过那条声明的
   第二条路；而营业时间/价格那些字段的消费方在编排自己这一侧。
   `*.menu` 是唯一例外：真栈证明同一官方菜单可以有两项**展示名逐字相同**，名字已不
   是身份；nearby/POI 仍不下发 id，位置权限边界逐字不变。
2. **id 只能由服务端候选铸造，且必须对新鲜菜单再校验。** Agent 入口先删除 planner/
   客户端同名保留槽，确定性消解后才写入；工作流重新读取当前门店菜单，只在其中按
   code 精确匹配。过期、换店或伪造 id 一律不命中。
3. **翻不准就不翻。** 命中多项且原话没有唯一序数时仍交回商户既有的追问链。
   **一个算错的确定性答案比不答更糟**——它没有 LLM 那种不确定信号，用户会照着付钱。
4. **归属只认产出这份候选的域。** 否则「先查附近的瑞幸」之后一句「点第一个」
   会把一个地图 POI 名当成商品名——那是**用户从没说过的商品**。

哪个槽吃候选集由能力声明（`servers.yaml` 的 `candidate_slot`）——加一家商户改表不改
主循环。挂点在能力分发的**唯一入口**，且只对「选品/看菜单」生效：确认与取消靠草稿
token 寻址，那条路上的商品早已核价定死。

契约与逐条判据：`docs/conventions.md` **§9.28**。

### 5.3 为什么"规划/执行分离"是 P0 安全要求
让 LLM 直接调用车控接口（function calling 直连车身）在量产不可接受：幻觉、注入攻击会变成真实的车辆动作。本设计中 LLM 的输出永远是"计划/意图"，所有副作用动作（尤其 `vehicle.control`）都要经过确定性的、可审计的 Executor + VAL 权限层（见 §9）。

### 5.2.7 能力缺席：从「声明了」到「可达」是一条五段链（v1.33，QA 卡 Q8）

前面几节讲的是**有能力但答错**；这一节讲的是**能力面上根本没有那一侧**时会发生什么。

#### 就近误执行，以及它的签名

Planner 只能在**当前能力清单**里选工具。清单上没有对应能力时，它不会说「我不会」，
而是挑一个最近的：真栈实测「从深圳市民中心到深圳北站开车多远多久」被挑成
`navigation.navigate_to` 并**真的开始导航**；「静音」被挑成 `volume.dec`；
「打开双闪」三次取样分别落 `power_mode.set`、`lane_assistance.close`、**`hvac.off`**。

⇒ **方差本身就是能力缺席的签名。** 同一句话每次落到**不同**的错误工具，说明它不是
某个工具描述写得像，而是根本没有正确答案可选——这与「模型抖动」在读数上长得一样，
但处置完全不同：前者要补能力，后者归档案化。判据：**看它错得一不一致**。

#### 五段链：任何一段断了，用户看到的都是「不支持」或答非所问

端侧车控从声明到可达要同时成立五件事：

| 段 | 断了会怎样 | 真实事故 |
|---|---|---|
| ① 知识库有这个**对象** | 规则认得出名字，但对象不存在 ⇒ 名字进不了本地意图集 ⇒ 整句上云 ⇒ 就近误执行 | 双闪：生成器 family 表把 `warning_light` 并进了 `headlight` |
| ② 对象声明了这条 **intent**（`edge_intents`）| 能力不可达且**无任何报错** | 除雾能力那次（B4 的立项理由） |
| ③ 端侧规则产得出**结构化命令** | 单句/复合句走不同的路 | Q13 两个分类出口不一致 |
| ④ 那条命令过得了 VAL **校验** | 端侧秒回「暂不支持哦」 | 方向盘加热：规则产 `operate=open`，而对象的 `operates` 是 `[set,inc,dec]` |
| ⑤ 有专属**状态键与话术** | 执行了但对不上账 / 用户听不出做了什么 | 方向盘加热关闭答「开了」 |

**B4 的能力完整性门禁覆盖 ①②⑤，不覆盖 ③④。** 它逐条跑的是
`edge_call.decode_intent`（云侧计划面）那一个产出方，而且直接调 `_simulate`、
**跳过校验**。于是「声明齐全、名字也对、就是过不了校验」这一族对门禁完全不可见——
方向盘加热在这条缝里活了很久。

⇒ 通用判据：**门禁走的是执行流水线的一段，不是整条。写完一道门禁要问的不是
「它查得对不对」，而是「真实那条路上，它没走到的是哪几段」。**

#### 两条与它成对的纪律

- **「有几个产出方」和「校验走了哪一个」是两个问题。** 同一个 intent 由两处产出
  结构化命令时，门禁只走其中一条就等于另一条没被守。修法不是要求两个产出方逐字
  相同（实测大量良性差异），而是要求**每一个产出方的产出都过同一道校验**。
- **放开一条被误吞的路，必须同时给它落点。** 「取消导航」原本被前置取消闸吞成
  「当前没有待确认的操作」；把判据收窄让它能进规划之后，如果能力面上仍没有
  `navigation.cancel`，它就会掉进就近误执行——**把一个错换成另一个错**。

### 5.2.8 指代到人：占位与具名是同一个实体，救济路径要闭合（v1.34，person-pickup 卡）

前一节讲能力面上**没有**那一侧；这一节讲能力面上**有**、判据面也有，
但它们**各自只覆盖自己那条路**时会发生什么——真栈症状是「接孩子」把车导去了
1582km 外的同名小学，而系统全程没有一句不确定。

#### 一、匿名占位与具名是同一个人

关系图谱里「无名的人」以称谓自身作实体名（`女儿--family-->女儿`）。用户后来说
「我女儿叫小雨」，于是又有了 `小雨--family-->女儿`。**同一个人在库里有两个 subject**，
而一跳解析按「命中几个实体」判歧义 ⇒ 数成两个人 ⇒ 从此对这个称谓**永久返回
「我不知道」**，尽管地点边就在旁边。

> **判据：用户给这个人起了名字，不该让能力退化。**
> 合并的只是**人的分组**——占位不算独立的人、具名主体 ≥2 才是真歧义；
> 而「地点必须唯一，否则宁可问」那道安全闸**一个字不能动**：
> 两个具名孩子两所学校仍然是「问一句」。**放宽识别不等于放宽授权。**

#### 二、判据对**槽值**成立，不代表对**整句原话**成立

「目的地是不是只是个人称」的判据是「剥掉人称与填充词后还剩不剩实质内容」。
它对槽值是对的（「孩子的学校」→ 剩空 → 解析；「孩子学校旁边的星巴克」→ 剩内容
→ 不改写）。把同一条判据套到整句原话上就天然失效——**复合请求必然有剩余内容**，
于是「接爸妈去吃饭」「带我去接孩子放学，顺便找家麦当劳」这类句形永不触发。

> **修法不是放宽那条判据，是换挂点。** 放宽会连带毁掉它对槽值的正确性；
> 换挂点（走到「这个目的地我接不着」之后再回退人称）让给了具体地点的复合句
> 一个字都不受影响。**一条判据在 A 处对、在 B 处错时，先问它是不是被搬错了地方。**

#### 三、救济路径也要有判据面，否则它自己就是缺陷源

目的地接地有一条既有救济路径：就近候选的名字校验不过 → **去偏置全国重搜**
（为「虹桥机场」这类全国序靠前的地标而设）。校园族没进类目锚词表时，
这条救济路径会做一件很糟的事：拒掉 4km 外**官方名多了「教育集团」四个字**的正主，
然后从全国序里捞回一个**逐字同名**的外省学校交差。

三条判据由此收敛：

- **救济路径必须与它救济的那道校验共享判据面**（名字 + 类目），
  否则它捞回来的东西比被拒掉的还差。
- **top1 不能受一条比后面所有候选都严的判据**——集内双匹配从第二名开始扫，
  等于排第一的候选（就近序最靠前的那个）永远没机会用主干规则被接住。
- **来源查不清不等于不能防。** 修完前两条之后仍有低频复发，而全部容器日志里
  那个外省地名**零命中**、直连 provider 复测也复现不出来。此时该加的不是第四层
  判据面，而是一道**产品语义**的闸：接人是本地差事，命中结果远到不合常理就
  **问一句**——它不依赖那一跳从哪来。⚠ 这道闸只对接送句生效，且认不出（无定位）
  就不判、不回落成拒绝。

#### 四、同一件事的两份存储，谁赢决定你看见哪个 bug

同一条事实同时活在 `memory_relation`（带城市、正确）与 `memory_item`（无城市）里。
planner 读的是后者 ⇒ 下发无城市的槽值；一跳解析读的是前者 ⇒ 但它被①那个歧义
判据卡死。**两条路各自坏在不同的地方，症状却都是「接错人」**——只修一条，
另一条会在下一次采样里把同一个 bug 原样端回来。

> `memory_item` 的 supersede 按「新的取代旧的」，会让同一件事**越记越少**
> （实据：一条 `person.child` 链四跳从「用户的女儿在深圳市南山实验小学上学」
> 磨成「用户有一个女儿」）。关系边侧 2026-08-16 已定过相反的规则——
> **保留信息最全的那条，不是最新的**。两侧规则不一致本身就是账，
> 但不能直接搬：偏好类记忆（「以后不吃辣了」）就该新的赢。已单独立卡。

### 5.2.9 能力槽位的值域契约：声明了 ≠ 可达（v1.35，QA 卡 Q12 规格维 / B6 §4）

§5.2.7 讲能力面上**没有**那一维；这一节讲能力面上**有**那一维、planner 也填对了，
但**我们声明的值域本身是猜的**时会发生什么——真栈症状是用户说「少冰」，系统答
「这款饮品不支持"少冰"」，而 HMI 预览卡上**正画着一个「少冰」按钮**，商家也确实
提供这一档。

#### 一、猜出来的值域是一种不会报错的死亡

槽位声明齐全、planner 三次取样全部填对（`ice=少冰` / `ice=去冰` / `milk=燕麦奶`），
下游也确实在按商家权威数据校验——唯一的问题是**它查错了组**。写死在实现里的
「槽名→官方规格组名」映射是照常见叫法写的：`ice→{冰量,冰度,加冰}` 在瑞幸**一个
都不存在**（冰/少冰/去冰/热全是**「温度」组**的取值），`milk→{奶底,奶类,乳基底,
奶制品}` 同样全部落空（真名是 奶基/奶/奶油）。

⇒ 三个规格槽**结构性死亡两个多月**，全程零报错：每一层看起来都在正常工作，
拒绝话术也很得体（「我没有替你猜其他规格」）。**「诚实地拒绝」掩盖了「根本查不到」。**

> **判据：凡是「外部系统持有的值域」，我们这一侧的声明必须有一道机器闸对着真机。**
> 光把它写进契约不够——写进契约的仍然可以是猜的。

#### 二、一份声明，两个消费方，才算真收敛

映射表原本只有一个消费方时，它是「一处硬编码」；有了第二个（预览卡的可改规格
chip）之后，它是**一致的错误**：两处读同一张坏表，于是同时错、错得一模一样，
看起来毫无异常——卡上画出「少冰」按钮，点下去必然失败，而那段代码的注释
恰恰写着「把改不动的组做成按钮就是给用户一个必然失败的入口」。

收敛到唯一声明（`servers.yaml` 的 `input_schema`）之后，这种自相矛盾在结构上
不可能。**删掉那张表的理由不是「少一处硬编码」，是让两个消费方无法各自跑偏。**

#### 三、翻译可以，换档不行

用户说「不加糖」而官方项名是「不另外加糖」——这是**语义等价的翻译**，写进
`aliases` 是对的。用户说「半糖」而档位是 标准甜/少甜/少少甜/微甜/不另外加糖——
**没有哪一档等于半糖**，替他挑一个就是替他改了他说的话。正确行为是**诚实拒绝
并把商家的可选项说出来**：可选项本来就在手上（官方 `productAttrs`，权威且新鲜），
让用户再猜一次是没有理由的。

配套闸有两道：别名的**键必须是官方项名**（方向搞反会把用户说法当官方名去匹配，
症状与猜错组名完全一样）；别名的**值不得恰好等于另一个官方项名**（那会把用户
说的 A 悄悄换成 B，而两者都真实存在——这种错在真栈上完全看不出来）。

#### 四、同一个组被两个槽指向时，胜负要写在契约里

瑞幸没有独立的冰量组，于是 `temperature` 与 `ice` 必然同指「温度」。真栈实测
「来一杯冰美式去冰」planner 产的正是 `temperature=冰` + `ice=去冰`：两个槽都往
同一个组里写。**「两个槽都写了」不等于「用户自相矛盾」**——首版打算冲突即拒，
那会把一句意思毫不含糊的话拒掉。判据落成契约里的 `precedence`，让位的那一维
打日志不静默。若不写，最终落哪一项取决于遍历顺序——**那是巧合不是判据**。

#### 五、孪生形态：契约比原话少了一维

§5.2.3 管「**槽值**比原话少了什么」。同一批翻出它的另一半：planner 产出
`size: 大杯`，而那个能力**根本没有 `size` 槽**，于是这个值一路走到下发、被下游
当未知键忽略，**全程没有任何一处会报错**。判据只用能力自己的声明
（`declared_slots`，零领域词），契约为空时不判；**只观测不改值**——删掉它不会让
用户拿回那个规格，硬塞给下游反而是拿模型编的键去撞外部接口。它回答的是另一个
问题：**模型往契约外面塞过东西吗**——那是补能力的线索。

### 5.2.10 候选集的「哪一组」：指代要闭合到组这一维（v1.36，QA I-030）

§5.2.5 把「系统持有的事实绝不让 LLM 答」落到了候选集**里面的第 N 项**。
这一节讲它**外面**还剩的一维：手里有好几份候选时，这句话在说**哪一份**。

#### 一、答错组比编造更难被发现

真栈形态：两家菜单都在会话里，用户说「**麦当劳**的第二个多少钱」，系统绑到最新
那一组，**零方差地**答出「「生椰拿铁」16 元」——那是瑞幸的第二个。

**商品名是真的、价格是真的、语气是确定的，没有任何一处对不上。** I-052 那类编造
还能靠「这个商品根本不存在」抓出来；这一条只有知道用户问的是哪家的人才看得出错。
⇒ 按「哪条错得更严重」排序，它排在立卡时写的「跨组比较做不了」（答非所问）前面。

> 根因是同一句话的第三次兑现：**凡是「系统持有的事实」，判据面就得是闭合的。**
> 第 7.5 步那次是「聚合算子与零候选守卫之间留了一条缝，模型从缝里编了一个价格」；
> 这次判据面上**根本没有「哪一组」这一维**——于是编的不是模型，是短路自己。
> **多一份候选就是多一维，维度不闭合，确定性只是把错答得更笃定。**

#### 二、这一组该叫什么，只有产生方知道

编排看不出 `mcd.menu` 那一组该叫「麦当劳」；把「麦当劳→mcd」写进编排核心正是
R2.1 明令禁止的那类硬编码。所以组标签走保留键 `_candidate_label`，**判据与
`_fallback` 逐字同源**（「搜的和他说的是不是一回事，只有产生方知道」）。

而产生方其实早有这个词——`ui_card.merchant`=「麦当劳」、`ui_card.keyword`=「川菜馆」
——只是从没给过下游。**这与「菜单只进 `ui_card` 从没进过候选集」是同一个形状**：
`ui_card` 是给人看的，`data` 是给下游消费的结构化事实，**而用户恰恰是照着卡上
那个词点的名**。所以两处必须是同一个值（共用常量、契约测试断言两处相等），
不是各写一份字面量。

#### 三、新增一维的安全形态：零命中必须逐字退回旧行为

组指代的三条规则里，第一条才是它能安全上线的理由——**没声明标签的产生方、没点名
的句子，一个字都不变**。命中多组时主组在**命中集内**取，且 N5「兜底不得顶替点名
那份」原样继承：**多一维筛选不该把旧判据丢掉**。

跨组算子同理：它要求的条件比现状**更严**（≥2 个组标签 + 每组各点到恰好一项），
所以误伤面不因它扩大。**给一条看到全部流量的短路加能力，正确形态是「加一道更严的
入口」而不是「放宽既有的口子」。**

#### 四、编排知道这一步姓什么，但不知道用户嘴里的那个词姓什么

同一个「哪一组」，两个面的判据不一样，故意分开：

| 面 | 谁在问 | 判据 |
|---|---|---|
| 云侧确定性问答 | 用户这句话在说哪一组 | **组标签**（产生方声明，从候选集派生） |
| 下发给 Agent | 这一步该拿哪一组 | **结构、零领域词**：步的 intent 域 == 组的 `source_intent` 域 |

合成一条会逼编排去认识商户名。分开之后两边各自都不需要领域知识。

#### 五、纯函数绿 ≠ 那条路径会走到它（第四次）

八处反向验证里，第一处「把挂点改回旧口径」跑出来是 **0 个用例**——判据全都验过了，
**接线从来没验过**。而本仓早就把这句话写在那个测试文件的开头，我是在它下面又欠了
一次。⇒ 新增判据时，**「谁会红」要和「判据对不对」一起设计**。

同批第二条：那几条接线测试首版把 `capability_ref` 写死成 `cap_0001`，而编号按
字典序不是声明序 ⇒ 装置自己把两家配反了，读数指向一个**不存在的缺陷**。
**装置和被测系统要用同一份口径**（同「A/B 之前先证明两臂真的不同」）。

### 5.2.11 尾部方差闭环：确定事实不经过模型转述（v1.37，MiniMax QA 复验）

探索式 QA 已收过多轮后，剩余红灯不再是「系统完全没有这项能力」，而是同一句话
重复采样时偶发丢掉一个**系统本来就知道的确定事实**：明确说「解锁」，goal/slot 都对，
却选成 `door_lock.close`；说菜单「第一个」，模型把序数转成多项共有的展示名；一句
话里同一事项两个提醒时刻，被随机规划成两步、一步或零步；刚折叠后视镜说「再展开」，
对象与方向在执行历史里都有，仍被转成天窗或反向动作。

这些不是需要模型继续思考的开放语义。**模型可以发现候选意图，但不能改写原话已经
明确给出的极性、系统持有的候选身份、同一句业务提交的基数，以及执行账本里的焦点。**

#### 一、确定性纠偏不绕过安全流水线

门锁原话极性由 edge-vehicle 自己的窄 `route_hints` 闭合；后视镜省略动作产出普通
`Plan`。两者之后仍完整经过 capability 校验、Executor、Runtime Policy、VAL 与
`require_confirm`。这里收回的是**分类权**，不是执行权——危险动作仍只到确认边界，
LLM 仍不能直连车控。

#### 二、展示名不是身份，身份必须在权威域里重新成立

同一官方菜单允许重名时，「翻成规范名」已经不足以定位。候选下发只对 `*.menu`
携带有界商品 id；保留槽在 Agent 入口先剥掉，再由服务端候选项写回；商户工作流还要
重新读取当前门店菜单并按 code 精确匹配。这样既保住文本/按钮同路，又不把客户端输入、
陈旧候选或 POI id 提升成商户写路径的权威事实。

#### 三、一个用户提交只能对应一个原子业务提交

「明天下午四点提醒我开会，三点半再提醒一次」不是两个互不相干的 planner step，
而是一个含两个写入项的业务意图。`reminder.create_batch` 在 Agent 内重新解析并验证
两个不同的未来时刻，`add_many` 对 PostgreSQL 用同一事务、对内存态在全部校验后一次
更新；任一项无效时**一条也不落**。话术与落库数量因此不再可能分叉。

#### 四、尾部 route hint 只表达结构边界，不收编自然语言

本批仍有四类 MiniMax 重复采样残余需要硬落域：车辆告警后的继续驾驶追问、账号级
进行中任务查询、无品牌历史订单查询，以及「接/送亲属 + 明确顺路词 + 停靠类别」。
它们只由对应 Agent 在 manifest 声明整句/有界结构，命中后仍走既有能力；否定、疑问、
提醒、平台帮助、设备控制等反例逐条钉住。宽泛 paraphrase 继续由 exemplar/LLM 负责。

这类 hint 上线必须同时具备：**真实重复采样证据、正向结构、反向误伤集、命中归因**；
退役仍走 §5.1 的全命中语料双臂与跨 provider 交集，不把本次 MiniMax 证据外推成所有
模型永久需要这条规则。

### 5.2.12 验收证据也必须收口到同一事务（v1.38，MiniMax QA 闭环）

系统行为修到尾部后，最危险的假绿不再来自“完全没测”，而来自**证据只覆盖事务的一半**：
起跑时 release 正确，不代表 250+ 轮后仍是同一 SHA；collector 先到 turn、后到 agent/LLM，
不代表第一份非空 JSON 就是终态；车态键缺失时补一个语义默认值，不代表知道真实前态；页面
写了 MiniMax 设置，不代表服务端实际按请求级 pin 执行。

#### 一、相邻上下文必须有同源时序

`Focus.last_intent` 不再与“整个 history 里最近一个 action”抢同一格。云侧焦点记录
`origin_exchange_id`；现代历史只消费最新 exchange 的动作。端侧本地轮用一次性、入口防伪的
`previous_local_exchange + actions` 桥接 memory 异步落库窗口，并以 TTL/LRU 限界。于是旧车控
不能覆盖更新的股票/天气焦点，端侧电量查询也会切断信息追问；但紧邻本地 `sunroof.open`
仍能让“关掉”确定性续接。

#### 二、真栈报告必须绑定完整运行区间

长会话与 HMI C14 都在开始和结束调用统一 `dev_stack status`，同时要求 `target=cloud`、
exact 40 位 release SHA、5/5 healthy；任一端漂移则整份报告失效。每个业务帧显式携带
`llm_provider=minimax / llm_model=MiniMax-M3`，collector 还必须证明实际 LLM call
`pinned=true`、无 fallback。HMI 再向下证明 MiniMax TTS start/text/finish、PCM 非静音、
AudioBuffer 起播/自然结束和 barge-in cancel + source.stop，不能以“页面出现回复”替代。

#### 三、分布式观测要等连续稳定，不能抢第一份快照

Edge 的 local intent 与 cloud planning intent 按 trace 无序合并；agent 调用与 engine-only
lifecycle 都有明确 owner span。探针只接受 exact trace、终态 status、合法 route、非空 intent
及 agent/lifecycle owner，并对 turn/spans/llm_calls 指纹做两次连续稳定读取。这样晚到的
非 MiniMax、unpinned 或 fallback 调用不会因为第一拍 `llm_calls=[]` 被漏掉。

#### 四、测试产生的副作用必须可证明归零

所有 persona 开始前取得 VAL 发布的完整权威车态，不用默认值冒充；异常业务 session 立即关闭，
恢复动作走新的 cleanup session，终态按基线目标连续回读。商户预览即使 UI 卡丢失也无条件执行
owner/session 原子清理并要求 after=0；提醒、导航与挂起操作同样以服务端 closed id/真实卡 id
收口。**停止复用不确定 session 与清理已知副作用是两件事，前者不能成为放弃后者的理由。**

这套原则也约束验收工具自身：隐私 inventory 可以在 `os.walk(topdown=True)` 进入生成目录前
剪枝，但 source pattern 大小写不敏感、排除目录严格精确，通用 `build/dist/coverage` 只能在
已知生成前缀剪，不能造一个未来可藏真实 source 的全局命名空间。

### 5.2.13 安全事实的登记与执行闸：不能挂在路由上（v1.39 建立；v1.46 闭合 dispatch 边界）

「规划/执行分离」（§5.3）保证的是**谁有权产生副作用**。它有一条残余缝：
**当模型把一句提问规划成一个车控写步时，这条链上没有任何一处会说「这不是指令」。**
真栈实录——「红色机油灯亮了怎么办」被规划成 `warning_light.close` 并**真的执行了**：
`require_confirm` / `drive_restricted` / `voice_forbidden` 三闸对这个对象全 false，
可执行性判定是 shadow 不进主链，`Step` 也没有 effect 这一维，执行链全绿。

#### 一、判据要住在两边都够得着的地方

端侧对同一形态**早就有闸**（分类器出口：问句形态的写操作一律不产出、整句上云）。
所以正确的修法不是在云侧再写一份，而是把那份判据**下沉到共享运行时**——落点判据是
**镜像依赖闭包**（端侧镜像没有 `agents/`、云侧编排镜像既没有 `agents/` 也没有
`orchestrator/edge`，而它们都 `COPY runtime`）。这与时区墙钟、指令极性、中文时间词、
营业时间解析是同一条线：**同一件事只许一份实现，位置由「谁够得着」决定。**

> **判定抄两份，迟早有一份是错的**——而安全判定抄错的那一份，代价是执行一个
> 用户没下的指令。

#### 二、所有 build 出口共用同一终结器，且判据零领域词

**v1.39 的初始边界**挂在当时的常规计划出口，判据是：这一步在端侧执行
（manifest 的 deployment/kind）∧ 这一步是写操作（只看操作名）∧ 这句话是在问
（封闭虚词类，由源码级断言守着「不许出现领域词」）。这只是历史起点，不再是当前完整边界。

**v1.45 的当前唯一判据**为：

```text
非指令问句 ∧（端侧写步骤 ∨ Step.require_confirm=true）
```

所有 `build()` 出口都必须共用 `_apply_question_side_effect_guard` 终结器：常规出口收束
LLM 计划、降级语义路由与 route hints，focused deterministic early return 也在返回前经过
同一 helper。判据仍全部从声明派生、不含任何 agent_id / intent 字面量，因此它
**不违反「不改编排核心加硬编码」**：这是安全不变量，不是某个 Agent 的路由特判。

拦截后若仍有合法步骤，只删违规对象；若变成零步，只尝试经 manifest 装配且
`require_confirm=false` 的 talk fallback。有合格能力时可以回答；不存在合格能力时保持
空计划 fail closed，安全优先于强行生成话术。尤其 focused 路径被拦后**绝不再走 registry
fallback**，否则刚删除的确认写能力可能被语义检索重新引入。

> **代价要主动枚举并钉成断言**：礼貌请求（「把空调关了好吗」）也会被拦。
> 端侧本来就不执行它们，变的是云侧此前会真做。**不给「好吗/行吗」开口子**——
> 同一个口子会把「慢一点开可以吗」被执行成音量调低的旧洞放回去。
> 收窄面只写一边守不住，两边都要写成用例。

#### 三、登记不能是路由的副作用

安全告警这类**系统必须知道的事实**，此前唯一的写入通道是「某个 Agent 恰好在返回值里
声明了保留键」。于是被规划成车控步的那一轮里，「红色机油灯」这个事实**整个没进系统**，
后续几轮消费的还是更早那轮留下的黄灯——同一句话在四个 persona 上呈现三种错法。

⇒ 登记改挂在**输入的形态**上：编排在组装上下文时扫本轮原话（纯函数、零 LLM、
与走了哪条路由无关），与 Agent 声明经**同一条严重级比较**合流——原话是事实、
Agent 声明是补充，`critical` 不被 `amber` 覆盖（过期的除外），跨轮粘性接力同走这条比较。

> **路由是有方差的，事实不能跟着抖。** 这条同样适用于焦点与执行账本：
> 凡是「后面几轮要靠它做判断」的事实，写入要挂在输入或产出的形态上，
> 不能挂在「这一轮恰好走了哪条路由」上。
>
> 推论：**同一症状在多 persona 下呈现三种错法，本身就是「无确定性护栏」的读数**
> ——修方差先找该确定性的那一层，不是逐个 persona 调。

#### 四、确认边界也是问句写闸的一部分

云端 release `343934bab66c23f83575cee998eb6f64a9f45f3e` 的长会话里，
「红色机油灯亮了还能继续开吗」被规划成 `luckin.order` 并进入挂起态；同句在干净会话
`--repeat 3` 三次都正确。这不是一个稳定的单轮落域错误，而是**长上下文才暴露的高代价方差**。

只把现有端侧条件机械扩成“所有 cloud 步骤也调用 `is_write_intent`”不可行：当前操作名粒度
会把 `search/menu/talk/status` 等云侧读取或应答能力误判成写。问句写闸因此沿用
§二给出的 v1.45 当前唯一判据。

其中端侧写仍由 `deployment/kind` 与 `is_write_intent` 共同判定；云侧确认边界只认
`Step.require_confirm`。该字段来自 capability manifest/servers 的权威装配，Planner 的 LLM
输出协议不含它，模型无权补写、删减或降级。正常指令、`require_confirm=false` 的云侧步骤，
以及 mixed 计划里的合法步骤逐字保持；mixed 只丢违规对象。所有常规与 focused build 出口
共用 `_apply_question_side_effect_guard`；focused 被拦后不走 registry fallback。若过滤后零步，
仅在 `_talk_only_plan` 找到 `require_confirm=false` 的合格能力时补安全回答，否则保持空计划
fail closed；两种结果都保留 `question_write_blocked`。默认 chitchat 配置能否给出分级安全建议，
必须由部署验收实证，不能从本地 helper 行为外推。这条边界也明确**不声称覆盖**所有
`require_confirm=false` 的云侧副作用；扩面要等正式 effect 契约成立。

质量审查还补出一条同层旁路：计划主路径会经 `_validated_steps` 恢复 manifest 权威字段，
但 fallback 若手工构造 `Step`，就会把 `require_confirm` 丢成默认假值，守卫之后重新引入
副作用。因此所有 fallback `Step` 构造也必须经过 `_validated_steps`；`_talk_only_plan`
若选中的兜底 capability 本身 `require_confirm=true`，必须返回 `None`，不能把“安全回答兜底”
变成另一条需确认写路径。

#### 五、安全边界覆盖每个 dispatch-bound 出口，不只覆盖 build

v1.46 把守卫从“`build()` 返回前过滤一次”提升为“**任何新计划首次进入 dispatch 前都过滤**”：
`build`（含 focused/normal）、adaptive `replan` 的接收点、Agent `_escalate` 生成的 mini-plan，
以及 fallback 候选都复用同一份步骤过滤原语。mixed 计划只删除违规 `Step`；全部被删时零
dispatch、零挂起。legacy pending plan 若既没有 `safety_origin_text`，也没有可兼容回填的持久化
`raw_text`，则声明可知的副作用一律 fail closed，不能拿当前补槽答案或模型生成字段补授权。

为此新增服务端权威字段 `safety_origin_text`：新任务只由 engine 以最初 `request.text` 盖章，
并随 plan、adaptive replan、suspend/restore 与 pending 序列化保持不变。`ctx.raw_text` 仍然表示
**当前这一轮**的补槽/确认答案；LLM `goal`、replan goal、Agent escalate reason 都没有安全
授权权威。这样“深圳”“拿铁”“确认”不会在恢复轮被升级成最初用户下过副作用指令的证据。

#### 六、回答兜底用 capability 级 `response_only` 契约纵深兜住

“intent 名看起来像 talk”不是安全契约。唯一权威是 capability manifest 的
`response_only=true`，字段必须经 SDK manifest → registry 持久化 round-trip →
`Step.response_only` 装配到执行层；Planner wire 同名字段无权生效。缺声明与 legacy 记录默认
`false`。`response_only=true + require_confirm=true` 在 provider dispatch 前即判契约冲突；
direct output 只允许零动作 `OK`，或维持零动作 `FAILED`，`NEED_CONFIRM` / `NEED_SLOT` / 任意
action 均转成 `response_only_contract_violation` 且 `actions=[]`。Executor 在普通执行、重试前后，
D0 与 T2 流式出口都执行同一契约；流式 action 在 yield 前丢弃，并禁止再走 unary fallback。
因此 `_talk_only_plan()` 只扫描声明为 `response_only=true`、`require_confirm=false` 且通过同一
问句守卫的能力，找不到就保持空计划。

### 5.2.14 系统持有的会话事实要有读出口，且出口在落域之前（v1.40，MiniMax QA 修复批 C4）

§5.2.11 说的是「确定事实不经过模型转述」。它有一条更早的缝：**很多事实根本没有
被写下来，或者写下来了却没有一条通向用户的读路径。** 2026-08-26 长会话 QA 一次交来
五张症状卡，形态各不相同，根因只有这一个——

| 用户问的 | 系统答的 | 事实其实在哪 |
|---|---|---|
| 这个行情的数据源是什么 | 「东方财富实时行情、19:23 前后」 | 卡上的 `_prov`（真实 Tushare / 20260826） |
| 总结这五轮里执行了什么 | 「手册里没有查到」 | `AppendTurn.actions` 账本 |
| 现在还有待确认的操作吗 | 「嗯」 / 一个学校地址 | 挂起表 |
| 重新列出刚才可以选择的项目 | 另一个城市的另一批门店 | 候选台账 |

#### 一、写不下来的事实，后面再怎么防都是空的

`_prov`（数据真实性标记）此前**只活在卡上**：渲染完就丢，编排与记忆没有任何一处读它。
所以 chitchat 接住「数据源是什么」时，**它连想如实回答都没有材料**——4 轮纯文本历史里
既没有动作、也没有卡片、更没有来源章，**编造是结构性的，不是模型不老实**。

⇒ 账本必须与执行事实**同格扩维**（会话轮次上加一维，不是新表；字段与卡上那个章
逐字同名，两边不许各自演化出一套叫法）。这与 §5.2.13 第三节是同一条：
**凡是「后面几轮要靠它做判断」的事实，都要有一个与路由无关的写入点。**

#### 二、读出口必须在落域之前，且判据住在两边都够得着的地方

Q6 把「刚才执行了什么」的确定性闸建在**兜底 Agent 内部**。判据一直是对的，
可 2026-08-26 那句「刚才实际改了哪一条」被规划器接给了提醒域——**闸够不着**。

⇒ 两件事都要做，只做一件都不够：
① **判据下沉到共享运行时**（落点判据仍是镜像依赖闭包），兜底 Agent 与编排层共用一份；
② **挂点前移到计划构建之前**，与候选集那两条确定性短路同位——谁接走都不再影响。

> **判据搬家会改变误伤代价。** 同一张词表在兜底位上判宽一格是「答得不对」，
> 在编排层短路位上是「整轮不进 Planner」。搬家时词表必须重看一遍并补否决面。

#### 三、有账才答，无账明说；「读不到」与「读到了、是空的」永远分开报

读出口只念账本、零 LLM、零网络，同一份账逐字同一个答案。两条边界：

- **账本空时是否仍然劫持，取决于「有没有第二个能答的人」**：挂起状态与执行史没有，
  所以空账也答；数据源有（域内直答），所以空账放行给规划器。
- 存储读失败必须与「读到了、是空的」分开报——两者都答「当前没有待确认的操作」，
  就是让一次存储故障说出一句听起来很确定的假话。

> 通用推论：**凡是「系统持有的事实」，判据面就得是闭合的**——写得下来、读得出来、
> 而且读的那条路不能依赖模型先把它路由对。

### 5.2.15 会话状态机的归属判定：默认方向、参照系与准入（v1.41，MiniMax QA 修复批 C3/C10）

§5.2.14 管的是「事实读不出来」。它旁边还有一条：**事实读得出来，但系统把「这句话
属于谁、这个序号指谁」判错了。** 2026-08-26 长会话 QA 的两张卡是同一类病的两个面。

#### 一、自由文本槽的默认方向本身是错的

`wait_slot` 续接的旧默认是「**除非证明是换话题，否则当槽值**」。于是判据每漏一种
说法，那句话就被整句塞进槽里——真栈一条 `item_query` 挂起连吞三轮，每一轮都答
「在售餐单里没查到"<用户刚说的那句话>"」，用户越说越远，挂起一直不放。

补词表救不了它：**规则的边界比说法的边界窄**，这是提醒域那条 replace 路由提示
退役时就写下的判据。方向要反转成「**槽值必须长得像这个槽**」——而这个反转的先例
就在被它取代的那段代码里：订单号槽只接受两种显式形状、其余一律换题。

⇒ 把那个特例升成**声明式契约**：哪个槽是什么形状由 Agent 在 manifest 声明，
形状怎么判是编排侧的通用判据（零领域词）。与执行后对账（`verification`）同一条分工。

> 判据取**三值**而不是 bool：`是槽值 / 不像 / 形状没意见`。写路径身份匹配上就是权威，
> 而餐品名匹配上什么都不证明（「点一杯拿铁」完全长得像餐品名，它是一句完整新指令）。
> **压成两值必然要牺牲其中一条。**

同一节还有一条更硬的兜底：**判据之外**再加一条止损线——同一条挂起连续问同一件事
到上限还接不上就放弃它（并说一句）。判据再准也有漏网的说法，这条保证黑洞只能吞
有限轮。**不是判得更准，是吞不了太多轮。**

#### 二、序数指代的参照系不许被后台动作静默替换

「第N条」在提醒域有三个互不相同的参照系：用户刚看到的列表、澄清候选、以及
**一次成功操作之后的后台刷新**。最后那个取的是整表最老 10 条——库里沉着 80 条
过期垃圾时，取消成功的那一刻参照系就被换成一份用户从来没看见过的考古清单，
下一句「取消第一条」于是取消了一条八月初的探针垃圾，还把它的标题念了出来。

⇒ **「第N条」只许指向用户最后一眼看到的那份列表**（与候选集下发面同一条判据）。
任何后台刷新参照系的动作都是在给序数指代埋雷，所以刷新也得刷成用户看得见的那份。

配套两条同族：按标题定位要有**精确度阶梯**（逐字相等优先于子串——转述放宽一个字
就可能命中另一条并真的把它取消掉）；按 id 回读要与按标题查同一条状态过滤
（两条读路径一条认 status 一条不认，缓存落后时就能选中一条已经终态的条目）。

#### 三、写入闸要判「这是不是一件事」，判据取形态

提醒的写入闸此前只判「触发时刻是不是有效」。于是**问句**（「刚才那个提醒现在几点」）
与**第三人称事实陈述**（「用户计划…4天行程」）都建成了提醒，还进了序数参照系。

⇒ 补一条任务性准入，**判据取句法形态、不取关键词**（关键词排除换个转述就绕过去）：
疑问收尾、第三人称主语开头。两条都只覆盖观测到的那两类，**宁可漏不误杀**——
漏了顶多多一条垃圾提醒，误杀的是用户真的要做的事。

> 通用推论：**归属判定的默认值要选「代价小的那一侧」。** 补槽的默认从「当槽值」翻成
> 「必须像」，是因为判错的代价不对称：判成换题只是重新规划一次，判成槽值会把
> 用户的新请求整句吃掉、还连吃好几轮。准入与参照系两条同理，只是方向相反——
> 那里宁可漏，因为误杀的代价更大。

<a id="section-5-2-16"></a>

### 5.2.16 复合句：每个诉求都要被单独看见一次（v1.42，MiniMax QA 修复批 C5/C6/C7/C8）

§5.2.14 管「事实读不出来」，§5.2.15 管「这句话属于谁判错了」。这一条管第三种：
**一句话里说了两件事，系统只回应了其中一件——而且每次少的那件还不一样。**

2026-08-26 长会话 QA 的一整族症状都长这个样子：「先查瑞幸，再点生椰拿铁不加糖」
只执行了搜索、下单意图消失（同一句在另一个 persona 却出对了两步）；「接爸妈去吃饭」
答出一串川菜、接人那半零动作；「接孩子放学，顺便找麦当劳」的 nearby 一反问，
同轮的导航一次都没发出去。**同形态两态就是零护栏的读数**（§4.3 那条「方差本身是
能力缺席的签名」的复合句版）。

#### 一、锚定范围与守卫范围是两件事

确定性路由（R2.1 的 `route_hints`）此前只能**整句锚定**：一条 hint 要生效，整句话
都得长得像它。于是接送 hint 只敢锚两种整句形态，注释里当时明写「带后续目的地的
复合句均不命中」——**那是刻意的裁定，把复合句留给了 LLM**。真栈把这笔账收了。

修法是给引擎加一维**匹配范围**（`RouteHint.scope`）：`clause` 档按分句表逐句试，
于是「接X + 任意后续」里的接人那一半总能被单独看见一次，另一半仍交给正常规划
（所以 policy 是 `append` 不是 `replace`——它只负责「别把这半丢了」）。

> ⚠ **放宽锚定不等于放宽守卫。** `guard` 必须留在整句面：分句档首版把守卫也收进
> 分句，当场撞红三条既有负向锁——「接女儿放学，路上买杯咖啡，然后播放音乐」这类
> **另一个域的诉求**靠的正是整句 guard。误伤一条正向句，比放开一整面守卫便宜。

> ⚠ **补步的去重判据要跟着一起换。** 整句档问「这个 intent 在不在计划里」；分句档
> 要问的是「**我这一分句的诉求**在不在」——「接孩子后去万象城」的计划里
> `navigate_to(destination=万象城)` 确实在，可它回答的是另一半。按 intent 去重
> 会把接人那半再丢一次。

#### 二、一个补槽问题不许劫持整轮

复合句的第二种死法在**执行**这一层：一个步 `NEED_SLOT` 反问，整轮就挂住了，
无依赖的兄弟步连跑的机会都没有。修法把挂起语义拆成两档——`NEED_CONFIRM` 是对
**整轮**说「先别做」，维持当场停；`NEED_SLOT` 只挂起**该步及其下游**（下游由
「依赖必须 OK」天然拦住，不需要第二份判据）。

> ⚠ 还有一半更隐蔽：同一层的步是一次并发跑完的，**它们的结果早就算出来了**，
> 挂起那条却把后面的整段丢掉。那不是「没执行」，是「执行了但不报」（§4.3
> 「读不到与读到了但不对分开报」的执行面）。同族的第二处在挂起话术里：挂起事件
> 此前只带挂起那一步的动作，兄弟步跑完了动作发不出去——**话说了事没做**。

#### 三、值得跨轮留住 ≠ 这一轮该注入

长会话里第三种死法是**旧焦点把新诉求解释掉**：三轮前的「万象城」「上海」还挂在
焦点里，模型读到后把「先去接我妈」整个丢了，抓住「川菜馆」+旧「万象城」反问
「哪个城市的万象城？」。

判据分离与 §9.28 候选集那次同形：**「值得跨轮留住」与「这一轮该不该注入」是两个
问题，两张表分开**。本轮有一个确定性的、自带完整语义的诉求时（判据声明式：命中了
`scope: clause` 的 hint），粘性的地点/候选焦点让路；安全告警、车控对象焦点与活动
路线**不在让路名单里**——前者是这轮回答的前提，后两者是「这句话在说哪台设备/哪条路」
的必要输入，让掉会制造新的洞。

#### 四、没被点名的维度要守恒，改了要说出来

复合句族的孪生形态在**修改类**请求上：用户只说了一条顺序约束（「不要把珠海排到广州
前面」），系统整程重规划，3 天「合法地」变成 4 天、还跨城混排。三条修法各管一段：
① 约束**已经满足**时零重规划直答（判据零领域词，城市名只从行程自己的城市表解析）；
② 重规划必须把用户此前给过的上下文**整套带过去**（丢上下文是纯 bug，不是取舍）；
③ 天数这类**没被提及的维度**要守恒——回炉一次仍不等就把它变成一次**显式选择**，
而不是静默扩天。

> 通用推论：**复合句里每一个诉求都得有一个「谁保证它被看见」的答案。**
> 靠 prompt 里一句软约束不算答案——它在长上下文里会输给旧焦点，而且失败时无声无息。
> 答案有三种形态，本节各占一段：**声明式锚定**（谁把它变成一步）、
> **执行调度**（一步挂起时其余怎么办）、**注入门控**（哪些跨轮事实这一轮该闭嘴）。
> 判不出来的那些先落**观测列**而不是判据——覆盖度信号本批只发 obs 不进决策，
> 误报面写在源码里等真实分布（B6 shadow 的纪律）。

### 5.2.17 说出口的每一句话都要对得上账（v1.44，MiniMax QA 修复批 C9/C11/C12/C13/C14）

§5.2.14–16 各管一族「系统没做到」。这一条管的是另一件事：**系统做到了什么与它说了
什么之间的落差**。2026-08-26 长会话 QA 里，四类话术在同一轮 QA 中同时出现，
它们的共同点不是「答错了」，是**每一句听起来都像有依据**：

| 说了什么 | 账上是什么 | 卡 |
|---|---|---|
| 「**上海**当前有1条天气预警」（前三轮全在问深圳） | 「上海」逐字来自 `memory/store.py` 的 **mock 车辆位置** | C9 |
| 「已经为您重新计算路线…全程约1.6公里」 | 零 navigation 调用、零动作（chitchat 兜底轮） | C11 |
| 「按您的口味优先川菜」+「不合口味的已排后」+「记得您说过不吃辣」 | **同一轮确定性拼出来的三句**，互相打脸 | C12 |
| 「比您要求的5:00早约**593分钟**」 | 「5点」被滚成次日凌晨，聚合 LLM 在同一句里自我吐槽 | C13 |

#### 一、拿不到就说拿不到，别让 mock 顶上

运行期 mock 回退是本仓的老盘点盲区（history：LLM 运行时那次）。这次它出现在**数据面**：
info 与 navigation 早就显式移除了 `vehicle.location` 回退并各留了注释，
road-safety 的天气预警是**全仓最后一条**还留着的——它把一个演示用的坐标当成
「当前位置」念了出来，下一轮模型又从这句答案里**学会了上海**（污染自我延续）。

> 判据：**诚实降级的顺序里没有 mock 这一档。** 本轮定位 → 诚实问一句，就这两级。
> 同族的第二条：署名摘要不是时间（`updateTime or tag` 让空气质量卡的
> 「更新时间」变成一串 64 位 hex）——**认不出就留空，宁缺勿假**。
> 第三条：外源数据卡必须盖 `_prov`（同一个文件里 5 个 handler 两个盖三个漏，
> 而契约的必带清单也少了同样三张——**契约与实现一起漏，等于没人在看**）。

#### 二、防编造要用类别否定，不要禁语清单

chitchat 的防编造条款此前是**禁语清单**（「已为您找到/已选定/已下单」+「请确认」
开头 + 四个能力名）。它被绕过了两轮：上一轮从交易话术、这一轮从**导航**
（清单里没有「重新计算路线」），而「请确认是否发起导航？」出现在句尾、连位置都躲开了。

> 判据：**清单挡不住换个说法，类别能。** 换成「凡是描述『系统已经做了什么／正在
> 做什么／接下来会做什么』的句子一律不许说」，并补一条「不许虚构自己此前犯过的
> 错误来道歉」（真栈出现过模型为一个**没发生过的错**道歉）。
> 配套两件：① 聚合器**不再吞掉 Agent 自己的失败话术**——单步 FAILED 出口原来
> 无条件查一张 `error → 友好话术` 表，而 `AgentResult` 根本没有 error 字段，
> 于是每一条失败都被换成裸「抱歉，处理失败。」，恢复指引连同「失败在哪一步」一起没了；
> ② 出口加一位**观测列**（执行完成形态 ∧ 本轮零动作），判据零领域词、
> 只写观测不进决策——直接拦的误伤面（信息类能力的合法完成语、转述历史）没量过。

#### 三、前景赢过背景，但前景要有载体

「记忆是背景，当轮说的是前景」这条判据 2026-08-15 就写下了，**一直没有载体**：
用户在第 28 轮说「我不吃辣，也不想排长队」（落 chitchat），第 29 轮问「推荐附近
适合晚饭的地方」拿到 10 家川菜——nearby 只读得到**当轮原话**，那句话在上一轮；
唯一的跨轮通道是异步记忆抽取绕 PG 一圈，几秒之内未必落库。

修法给焦点加一格 `session_constraints`：**登记挂在输入的形态上，不挂在路由上**
（同 §5.2.13 安全告警那条），抽取判据与词表落 `runtime/`（两个消费方够不着彼此——
抽取在云侧编排、消费在 Agent），下发走 manifest `context_scopes` 门控（**不广播**：
忌口是个人数据，与安全告警那次的取舍正相反）。合并语义是「**后说的覆盖先说的**」
——一个解除不了的忌口会让系统跟改主意的用户犟嘴。

> 同一张卡的另一半是**判据用错了变量**：挡「拿爱吃的辣菜系当检索词」的那块板问的是
> 「本轮原话有没有说不要辣」，而不是合并后的忌口事实 ⇒ 记忆里两条偏好并存时，
> 三句自相矛盾的话是**同一轮确定性拼出来的**。判据：**限制性偏好赢过扩张性偏好。**

#### 四、解析器没把握的分支，把疑点交还用户

「5点我要到学校」在 18:53 说出口时，两个候选（05:00/17:00）都已过时，旧实现滚到
**次日同数字小时**——一个精确、可播报、且完全错误的时限。

> 判据：**滚日不该改变小时语义。** 滚到明天该算 17:00 还是 05:00 本身无解，
> 说明这一支不该猜：返回今天那个**已经过去**的时刻，由上层如实说「已经过了」。
> 话术层再加一道**荒谬余量闸**（>6h 不播精确分钟数）——两道闸的分工是
> 「时限已经过去」与「时限在未来但远得不合常理」，成因同一个，
> 而**精确数字是有害的确定感**。

> 通用推论：**每一句话都要能回答「这个说法的依据在账上是哪一条」。**
> 四种断法各对应一种依据缺失：依据是假的（mock）、依据不存在（编造）、
> 依据互相矛盾（前景/背景没有仲裁）、依据是猜的却报成精确值（解析疑点）。
> 落点判据也一致：**能确定性给出的事实不进 LLM，给不出的就诚实说给不出**，
> 中间那一档（拿一个像样的值顶上）在任何一面都是最坏的选择。
> 第五张卡 C14 是它在**声明面**的同一件事：`charging.plan` 本来就只出建议卡、
> 不发导航，可这个性质只写在代码注释里 ⇒ planner 无从知道「先不要启动导航」
> 与它相容——**能力的性质写不进 manifest，就等于不存在**（R2.1 的老判据）。
