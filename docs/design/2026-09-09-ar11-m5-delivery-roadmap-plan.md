# AR11：Android M5 生产化交付规划方案

> 状态：**规划草案，未启动生产化实现**；日期：2026-09-09。
> 交付对象：产品负责人、mobile、身份/后端、平台运维、安全隐私与 QA 角色；具体人员待项目分派，不在本计划编造。
> 对应 R14 生产化部分；身份/能力摘要已有 AR05，本批消费其结果。当前核对基线见[接续路线](2026-09-09-android-ar06-ar11-execution-roadmap.md)，正式交付基线待 AR10 报告。
> **命名消歧：本文的 Android M5 是移动端对外交付阶段，不是项目已落地的 M5 数据飞轮。** 后续工作包统一使用 `AM5-*`，避免台账与 Goal 混淆。

## 1. AR11 本批的完成结果

将账号、可靠连接/投递、签名/更新、隐私/系统交互、观测/性能分成五个可独立安排、验收与回退的工作包。本文已经提供首版拆解；后续 AR11 应核对 AR10 实际结果并定稿，而不是再次从零列方向。

AR11 完成只说明计划可执行，不代表登录、厂商推送、正式签名或上架已经实现。建议第一交付目标为**限定支持设备、受控邀请的小范围试用**，待准入证据齐全再扩大发布；本建议不构成对外发布授权。

## 3. 五个独立工作包

### AM5-01：账号、设备身份与可信权限

**责任**：身份/后端主责；mobile 接入；安全复核鉴权覆盖；QA 做跨身份反例。

建议复用标准身份服务，原生端使用系统浏览器的授权码 + PKCE 登录，避免自建密码体系或将登录放入可读密码的 WebView。此路线依据 [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)，身份供应方与登录方式仍需结合项目账号来源确定。

实施拆解：

1. 冻结 `account_id/user_id/device_id/vehicle_binding` 关系、会话授权来源、token 期限/续期/吊销、权限更新传播时限。手机默认最小 scope，车控需可信车辆绑定及服务端授权；声纹、布局角色、客户端 meta 无授权权威。
2. 接入服务端鉴权适配层，保留现有 `stampScopes` 和确定性权限检查；盘点主 WS、会话 HTTP、ASR/TTS/S2S、视觉与业务恢复入口，不能只给 `/api/session` 加登录。
3. mobile 登录/退出/续期/离线恢复，续期失败明确提示。账号/服务器切换必须终止旧音频、挂起回复/队列、异步准备和摘要，不把上一个账号的数据带进新会话。
4. 连接中权限吊销或车辆解绑，服务端规定失效界限并主动阻止后续写；客户端关闭可执行入口只作体验，服务端再次校验。
5. 迁移内部长效 token 用户采用受控过渡，不静默改 `.env` 或批量切换生产权限。

**代码面**：`mobile/src/core/config/`、`core/api/`、`core/session/`、应用宿主与引导；`gateway/edge/`、`gateway/cloud/`、`llm-gateway/`、`security/`；必要的身份服务为拟新增，先冻结 API/数据设计。

**DoD**：登录/取消/续期/过期/吊销/设备解绑/账号切换均有真链路用例；受限账号在所有执行出口零越权；旧会话和音频不复活；两端同 user_id 共享记忆但会话隔离；日志/URL 不泄凭证；凭证与 schema 变更取得具体授权。

**产物**：身份合同、入口鉴权覆盖表、状态机、迁移/回退方案、正反例报告。AM5-02/03 不得各自另造设备身份。

### AM5-02：公网连接、设备投递与恢复

**责任**：平台/网关主责；提醒/主动服务和 mobile 协作；QA 负责离线、多端和去重。

建议前台沿用 WS，后台采用目标市场可达的系统/厂商推送唤起通知；保留 Tailscale 作为内部环境，不要求外部用户手动维护 Tailnet。具体推送供应商以渠道和设备覆盖决定，不预设 GMS 在所有目标设备可用，也不把前台常驻服务作为通用保活方案。

实施拆解：

1. 冻结公开域名/TLS、主链与音频入口、认证、限流、超时、健康检查及降级。先准备运维变更与验证/回退步骤，再申请基础设施授权。
2. 设备注册绑定 AM5-01 身份；推送 token 更新/失效/退出登录与设备注销可追溯，不直接把 provider token 当用户 ID。
3. 投递合同明确 `delivery_id`、设备维 attempt、TTL、去重/重试上限与清理；通知 payload 默认只带不敏感的索引/摘要，正文按当前身份拉取。
4. 区分 accepted、provider_delivered（可用时）、App received、notification_posted、presented、handled。AR04 的 `proactive_ack` 不可因 SDK 返回成功提前发送；“锁屏通知已展示是否满足某任务触达”需要新的明确产品合同，默认保持既有 App presented 语义。
5. 双端在线/离线、重复投递、token 轮换、重装、应用被系统终止、过 TTL 后进入等逐项验证；不能承诺所有 OEM 强停后都可靠自启。

**代码面**：`gateway/edge/` 的主动投递、`agents/reminder/`、`proactive/`、mobile 会话/呈现与拟新增通知桥，注册/重试存储如需 schema 变更先给迁移方案。

**DoD**：目标设备分别取得前台/后台/锁屏/离线回归报告；同一 delivery 不重复业务/播报；过期通知不复活旧操作；未呈现不销账；观测可分清供应商接受与用户触达；公开入口可用性/恢复指标及测试窗口事前冻结。

**产物**：连接与投递合同、设备/供应商矩阵、部署/回退清单、端到端逐 delivery 证据。首次试用可先限定渠道，但范围必须由产品采用。

### AM5-03：正式签名、版本与更新

**责任**：发布/平台主责；mobile 负责 CNG/兼容；产品决定分发渠道；QA 验升级与回退。

建议先建立可靠的完整 APK 更新链，再决定是否引入自托管 Expo Updates。正式签名与 OTA 是两项工作，不能以“能下发 JS”代替签名和原生兼容。Android 对更新签名的要求见[官方签名指南](https://developer.android.com/studio/publish/app-signing)；Expo 的更新与原生 runtime 必须匹配，见 [runtime version 文档](https://docs.expo.dev/eas-update/runtime-versions/)。

实施拆解：

1. 定正式 applicationId、签名所有权/保管/恢复、分发渠道、versionCode 单调递增与版本命名；敏感签名材料不进仓库/日志。开发/灰度/正式包是否分 package 明确决定，不能破坏现有高德绑定。
2. 审核 debug 签名转正式的安装路径。默认视为不能直接覆盖，先核实际签名/系统支持；给出保留旧内部包或新包迁入的具体选择，以及账号/设置/本地资料安排。不得自动卸载或清数据。
3. 通过 CNG 配置、构建脚本和验包输出形成可重复产物；正式指纹在高德后台登记，装机验证地图可用。不复制维护生成的 `android/`。
4. 更新包校验、分批放量、网络中断/低存储/下载失败/安装取消恢复；数据格式前后兼容需明确。回退通常是发布更高 versionCode 的已知好实现，而非默认 Android 可安装低版本。
5. 若引入 OTA，再定义 runtimeVersion/原生指纹、更新签名、渠道、启动失败恢复、缓存策略、服务端契约兼容；新原生依赖必须新 APK，不能热更推给缺模块旧包。

**代码面**：`mobile/app.config.ts`、config plugins、版本/引导/更新 UI、`scripts/build_mobile.ps1` 及获准的发布流水线；更新服务属于拟新增依赖。

**DoD**：签名/版本/ABI/build/原生模块验证全齐；安装/升级/中断/回退/配置保留逐项完成；旧签名切换方案实际验证；地图指纹有效；至少一轮灰度发布及回退演练完成后才扩范围。

**产物**：发布清单、密钥保管责任与恢复规程（无密钥正文）、兼容矩阵、升级/回退实证。不得借 AR06 内部 prod 包验收声称正式签名已完成。

### AM5-04：隐私、SDK 初始化与系统交互

**责任**：产品/隐私角色定义承诺，mobile/后端落实；安全与 QA 验撤销和数据路径。正式法律文本与渠道要求由相应责任人审核，本方案不宣称合规认证。

实施拆解：

1. 建数据清单：麦克风原始音频、ASR 文本、S2S 音频、单帧图像、位置、记忆/画像、诊断、推送地址；逐项写采集目的、触发、处理方、存储/TTL、用户关闭/导出/删除方式及失败恢复。
2. 审核高德等 SDK 初始化时间；真正同意前不初始化需同意的 SDK，拒绝仍有可用的非地图流程。不能只加声明 UI，却继续调用库内硬编码同意初始化。
3. 沿用 AR02 内存视觉/在途作废、AR04 后台/锁屏撤回；撤销权限与功能关闭后新上传为零。若需调整留存承诺，先给具体数据路径、时间与理由，不能无声改“零落盘”。
4. 锁屏内容默认脱敏；解锁/换账号后重新鉴权取数据，不能让过期通知打开他人内容。通知权限按具体任务申请，不强制开通知才能用所有前台功能。
5. 系统入口按下表单独立项；后台录音、悬浮窗不作为 M5 默认范围。账号删除/数据删除需要覆盖服务端与本地并提供可审查过程，不先在生产执行删除验证。

**代码面**：mobile 设置/引导/地图/视觉/音频/通知桥、`llm-gateway/`、`memory/`、诊断及所有第三方 SDK 接入点。

**DoD**：每项数据承诺有实际链路与失败/撤销证据；SDK 同意状态与初始化一致；锁屏/账号隔离、视觉缓存与后台边界合格；所需声明和渠道物料经责任角色审核；未采用能力从承诺中明确移除。

| 系统入口 | 首版建议 | 单独启动条件 |
|---|---|---|
| 静态 Shortcuts | 保留现有入口，复验只打开正确页面 | URI/权限/账号恢复可靠 |
| QS Tile | 暂不作为首发必要项 | 已证实用户需要快速进入，点击后按前台交互规则，不自动开麦 |
| Live Updates | 暂不用于通用助手常驻 | 有用户发起、可跟踪且有明确结束的任务；符合[官方使用范围](https://developer.android.com/design/ui/mobile/guides/home-screen/live-updates) |
| Widgets | 按只读任务后排 | 数据陈旧提示、刷新预算、账号隔离与点击恢复有具体需求 |
| 默认助理角色 | 保留既有不启用判断 | 新设备/系统证据和真实入口收益足以推翻原结论时再立项 |

### AM5-05：观测、性能准入与试用反馈

**责任**：平台观测/QA 主责，mobile 提供崩溃和性能信号，产品负责问题优先级与支持承诺。

实施拆解：

1. 复用 AR09 字段与现有 collector，接崩溃/ANR、启动、语音、网络失败、采集/播放生命周期等指标；具体采集 SDK 根据隐私/成本决定，不预定必须 Sentry 或上传所有日志。
2. 版本、设备/Android、网络、主链与语音 provider 分组；上传只用允许的摘要，原始音视频/凭证/完整敏感请求不进遥测。
3. 将 AR07/08/09 与 AR10 采用指标转成放量准入；另冻结真实内存/耗电/长期前后台要求。短期 0 crash 不能冒充低事故率，必须记录会话数/用户时长/观察窗口。
4. 建 badcase 入口、trace 关联、脱敏、问题分派/复现/修复/回归记录；用户授权的反馈资料和自动指标分开。
5. 写异常响应与回退条件，例如确认/权限/隐私破坏立即停止扩大试用；普通性能指标连续超目标按预定窗口处理。执行暂停/回退仍走实际发布责任与授权。

**代码面**：`mobile/src/core/obs/`、AR09 诊断、平台采集适配、`observability/collector/`、dashboard 与发布报告。

**DoD**：至少一条可控崩溃/错误在非生产环境贯通到符号化/版本/设备；不敏感的 trace 可定位全链；告警与问题闭环演练成功；灰度用户量/时长/设备分母齐全；指标和成本有负责人及明确阈值。

**产物**：遥测字段合同、SLO/性能准入表、报警/响应规程、试用报告与反馈台账。

## 4. 依赖、顺序与并行边界

| 阶段 | 必要产物 | 后续可启动 |
|---|---|---|
| D0 产品边界 | AR10 结论、试用人群/渠道/设备、后台触达承诺、数据范围 | 各包合同与技术验证 |
| D1 身份与隐私合同 | AM5-01 身份/设备/scopes、AM5-04 同意与数据路径 | 公网/推送注册、SDK/登录 UI、观测采集 |
| D2 发布骨架 | AM5-03 正式签名/版本/构建身份与兼容规则 | 真实设备灰度候选；高德/推送身份配置 |
| D3 端到端集成 | AM5-01/02/04 的鉴权、投递、撤销；AM5-05 可观测 | 限定用户试用与准入报告 |
| D4 放量裁决 | 所有必选 DoD、实际支持矩阵、回退演练 | 由用户决定分发/上线；未采用系统入口留独立待办 |

合同设计、测试材料与本地实现可按独立文件分工；共享 schema/网关、CI、云端发布、构建镜像与手机使用必须有一个集成负责人串行裁决。只有真正独立工作流才委派，不能让五个 Agent 同时改身份和配置源。

工作量不编日历承诺：AR11 定稿时按每包“合同/客户端/后端/原生/QA/外部等待”估算有效工作量，并写依据；账号供应商、渠道和真实设备未确定前，不能给一个伪精确总天数。外部等待与编码工作量分栏。

## 5. 必须在开工前落实的决策

| 决策 | 本方案建议默认 | 未定的影响/责任角色 |
|---|---|---|
| 首发范围 | 受控邀请，采用 AR10 已证设备/系统范围 | 产品负责，决定设备与推送投入，不自行宣布公开可用 |
| 身份来源 | 复用已有/标准 IdP，浏览器 PKCE | 身份/产品决定租户与账号来源，影响登录和 user_id 映射 |
| 后台触达 | 通知+按需恢复，前台 WS | 产品明确哪些提醒必须通知；平台选择目标厂商渠道 |
| 签名/包名/渠道 | 正式签名，明确内部包过渡；先 APK 更新 | 发布角色提供受控签名方案；不能假设原包可覆盖升级 |
| OTA | 在 APK 更新可靠后独立评估 | mobile/平台评估 runtime/托管与维护成本；不设成所有包的前置 |
| 数据/遥测 | 最小摘要、用户控制、限定留存 | 隐私/产品定保留期、反馈授权和数据权利流程 |
| 系统入口 | 除 Shortcuts 外按具体任务后排 | 产品定优先级，不打包强制做 Tile/Live Updates/Widgets |

这些是后续实施前要关闭的决策点，本轮无需为了写计划先要真实密钥、开云资源或向他人发消息。AR11 可以先形成带明确前置的完整计划；定稿必须标出哪些包已可开工，哪些仍等待具体外部条件。

|---|---|---|
| A11-0 | 工程规划先核当前代码/发布与未达项；定稿再读取 AR10 最终报告 | 冻结实际规划基线；分清 UX 与生产化问题 |
| A11-1 | 五包源码/依赖盘点与默认方案对比 | 每包真实差距、接口/数据草案、可复用模块及替代方案 |
| A11-2 | 收集本节关键决策、角色与外部条件 | 不虚构人员或供应商；每个未决点有责任角色与影响 |
| A11-3 | 将五包拆为可执行任务 | 每项输入、输出、前置、代码面、DoD、测试和授权边界；给出工作量估算依据 |
| A11-4 | 完成发布/迁移/回退与试用准入设计 | 可审查步骤；环境/密钥/schema/CI/生产操作单列，仍未执行 |
| A11-5 | 定稿与入口交接 | 拟新增执行日期的 `android-m5-delivery-plan`，或在本文件完成定稿；状态表能定位下一包 |

AR11 签收条件：五个包都具备责任角色、明确范围、依赖、实现落点、验收产物和发布边界；外部缺口有具体行动/负责角色；实施顺序无循环依赖；采用 AR10 真结论；系统入口逐项裁决；工程工作量与外部等待分开；没有将“计划已完成”写成“生产功能已上线”。

## 7. Goal 文本

执行方式以[工程交付与集中验收安排](2026-09-10-android-goal-delivery-and-acceptance-plan.md)为准。下面两种目标在启动时选择；默认采用工程交付目标，本文完整验收矩阵仍保留。

### 工程交付 Goal（默认）

> 按 AR11 方案完成 Android M5 技术规划主体：基于当前核实的代码与验收状态，把 AM5-01～05 的范围、接口/数据草案、代码面、角色、依赖、DoD、测试、工作量依据、发布/回退和具体授权材料写全。AR10 最终结论和供应商/人员条件作为明确待校准项，不阻塞其他规划内容；不编造商业条件、不实现未决定的生产能力。交付可分工计划及最小决策清单，最终采用 AR10 基线时再完成定稿签收。

### 规划定稿 Goal（采用 AR10 最终基线）

> 接手 AR11，基于本方案的 AM5-01～05 草案和 AR10 实际验收结果，完成 Android M5 可分工交付计划定稿。核对账号/设备、连接/推送、签名/更新、隐私/系统入口、观测/性能的真实差距，逐包落实责任角色、接口/数据方案、依赖、任务、DoD、验证、工作量依据和发布/回退边界；明确已可开工与待外部条件的包。只交付规划与可审查材料，不把本 Goal 解释为授权实现全部生产能力或对外上线。

定稿后每个 AM5 包另设目标，先合同与本地可验证实现，再到真实账号/设备/基础设施验收。生产签名、token、数据库、系统配置、CI/CD、push 与部署按项目规则逐项处理；不因已批准总规划而自动执行红线操作。
