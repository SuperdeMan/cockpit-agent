## 1. 已经成立的（2026-10-03 代码与线上只读核对）

- 主体、车辆、会话只来自服务端（SDK `Context` / meta）；`_owner_user_id` 从参数里剥掉且不可配置；
  `granted_scopes` 由网关下发、规划侧重建；外部工具返回改不了 scope、目标用户或车辆。
- 远端商户只拿服务账号凭据（每个服务器一枚静态 Bearer，从环境变量展开、只发给本服务器），不转发用户 token，
  不带终端用户身份（`forward_owner` 只许 demo stdio）。
- 写操作：`require_confirm` 中央闸；草稿令牌绑用户 + 会话 + 商户 + 操作、一次消费；确认时重算价格并与创建回执对账；
  支付链接经桥与网关两层域名白名单，拒绝时清洗回答、卡片、数据与账本里所有 URI。
- 规划看到的能力文本来自 `servers.yaml`，不用服务器自带描述；能力效果只认人工准入声明。
- 线上：两个网关 `AUTH_REQUIRED=true`、规划 `PERMISSIONS_FAIL_OPEN=false`；只有车主的 token 带 `merchant.*` 与 `payment.invoke`。
  服务间 gRPC 未开 mTLS（`GRPC_TLS=off`），桥信任调用方给的 context / meta。

## 2. 缺口（按完成判据归类，均有代码位置核对）

### 2.1 判据①：注入内容不能修改权限 / 车辆 / 操作参数权威

- **I1 计划槽引用**：`${sN.data…}` 能把桥返回的任意值原样带进后续任意一步（`orchestrator/cloud/executor.py`）。
  来源可信只在瑞幸门店引用一处检查（`_trusted_slot_refs`）；派发只看消费方的可信级别，不看数据从哪来。
- **I2 按钮文本**：商品 / 门店 / 分类名无长度与内容约束，拼进按钮 `send_text`（如「看看{门店}的{分类}」），
  用户一点就成了「用户原话」——外部文本进入原话授权通道的入口。目前唯一的挡板是注入正则。
- **I3 进入后续模型提示**：桥的摘要步、聚合、规划上下文（历史与焦点里的名字）、重规划观测、记忆抽取都把外部文本当普通文本；
  记忆抽取的提示还让它信任「助手确认过的店名」。`security/injection.py` 的包裹函数只在测试里用到。
- **I4 回答与卡片**：raw 模式原样念工具文本、无长度上限；通用写路径直接念商户文本；`data` 原样回传；
  麦当劳 `order_id` 不校验（瑞幸校验）；`card.options` 不在保留键里，通用写路径的商户 JSON 能注入按钮（目前只有 demo 走这条路）。

### 2.2 判据②：跨 owner 句柄拒绝

- **H1 显式订单号**：话里报了订单号就绕过账本归属（`_resolve_order_ref` 提前返回，测试有意钉住，为的是能查历史单）。
  服务账号是共享的，任何有 `merchant.read` 的用户报出单号就能读这个账号下的任何订单；线上目前只有车主有这个 scope。
- **H2 不绑车辆**：草稿令牌与订单引用绑用户和会话，不绑车辆。
- **H3 支付网关**：`Cancel` / `GetStatus` 不校验 `payment_id` 归属；桥调网关不带 `x-granted-scopes`，网关走 fail-open，
  `payment.invoke` 实际没在网关执行。

### 2.3 判据③：服务级账号边界如实标注

- **A1** 运行时不标注：卡片 `_prov` 只有来源与模式；「服务级单账号」只写在设计文档里，`servers.yaml` 写的是「测试账号」。
- **A2** 麦当劳「我的收藏」门店（`searchType: 1`）来自服务账号，任何用户都能看到。

### 2.4 委托范围、版本指纹与出口

- **S1** demo 写操作不要求 `merchant.write`（`required_scopes: []`）。本地缺省（不强制鉴权 + 权限 fail-open）下匿名请求拿到
  `merchant.write`；线上不受影响。
- **V1 版本指纹**：只覆盖 inputSchema、截成 48 位；`schema_sha` 为空时只记录不校验；远端服务器不锁 version；只在启动时校验——
  `tools/list_changed` 被忽略，HTTP 404 重新握手也不重新准入。准入之后服务器换了工具定义，直到重启都发现不了。
- **E1** stdio 子进程继承整份环境（两个商户 token、数据库 DSN、e2e 管理密钥）。
- **E2 出口**：只靠代理配合，进程可以直连；代理对允许的主机放行任意端口；响应体没有大小上限，调用没有总时限；
  服务器 URL 的 scheme 与主机只靠人工审 YAML。
- **E3 支付链接**：通用路径不查端口与 userinfo，网关不查端口。

## 4. S1：句柄与账号边界（实现与验证，本地）

### 4.1 判据

- **共享服务账号如实声明**：`servers.yaml` 的远端商户声明 `account: service` 与 `account_holder`（车主 `u1`）。
  带静态凭据的非 demo 服务器没声明就整台拒载（`check_account`）——以后新接商户不会漏标。
- **报单号（H1）**：共享账号下，只有账号持有人能凭单号查账号里的任何订单；其他人报的单号必须在自己账本里该商户名下，
  否则如实说「不在您的下单记录里」，不向商户出站、不确认单号是否存在（`_may_read_reference`）。非共享账号（demo）由商户自己按用户隔离。
- **收藏门店（A2）**：麦当劳收藏档（`searchType: 1`）只给账号持有人；其他人没说门店与城市时请他说，按位置搜。
- **标注（A1）**：桥的唯一出口按卡片所属商户打 `account: service` 与「共享商户账号」，判据只认 `servers.yaml`；
  这两个键进保留键，商户 JSON 伪造不了。确认话术加「下单用的是车上共享的商户账号」。HMI 四种商户卡渲染角标。
- **支付网关（H3）**：SDK 在 Execute 入口把请求主体与编排层下发的 granted_scopes 绑进 contextvar，支付客户端随
  `x-user-id` / `x-granted-scopes` 带给网关。网关缺授权一律拒；建单只能为请求主体本人；Capture / Cancel / GetStatus / Refund
  只认本人的支付单，别人的单与不存在一样处理。原先缺 metadata 时的 fail-open 分支删除。
- **子进程（E1）**：stdio MCP 子进程只继承运行 Python 所需的系统变量，不再拿到商户 token、数据库 DSN 与管理密钥。

### 4.2 刻意不改的两项

- **H2 草稿不绑车辆**：消费创建 / 取消草稿必须有服务端注入的 `confirmed`，而这个确认在
  [CA2-09](2026-10-02-v2-confirmation-binding.md) 里已绑定车辆、换车即拒；其余草稿步骤（选店、选品）是同一用户同一会话，不是跨 owner。
- **G demo 写操作的 scope**：demo 写只到仓内演示服务器、产生演示订单；真实商户的写工具准入时被强制 `expose=false`，只能经 workflow 到达，
  而 workflow 必须声明 `merchant.write`。给 demo 加 scope 要给所有 e2e 测试身份加商户权限，安全收益为零。

## 5. S2：外源隔离（判据①）

### 5.1 测量（只读，2026-10-03）

- 第三方数据源三个：`nearby`（高德 POI）、`parking_payment`、`mcp_bridge`（`trust_level: third_party`）。
- collector 保留的 1691 次规划里，规划原始输出带非空 `slot_refs` 的 58 次；第三方数据只流向两处——同一 Agent 内部
  （附近搜索 → 附近详情 / 下单的 `poi_id`）与导航目标（附近搜索 → 导航的目的地 / poi_id / 地址 / 名称）。
  **没有**任何商户桥数据的流向，也没有流向车控、支付或权限参数的。（规划 span 的步骤摘要不记 `slot_refs`，只看得到写在槽值里的 `${…}` 占位，
  所以以原始输出为准。）
- 外部名字进「用户原话」的入口：桥给的按钮 / 选项 / 分类 `send_text`（「在{门店}点第N个：{商品}」等），以及客户端用第一件商品名拼的
  「换一家{品牌}门店，还是点{商品}」。服务端模板本身不含分句符号。
- 测试夹具里 139 个商户名称按「不含分句标记与句末标点、≤40 字」判，只有规格项「不另外加糖」会被拦（它不进按钮文本）。

### 5.2 判据

- **I1 第三方数据不当车控参数**：规划要求的引用（`slot_refs`、`${…}` 占位、`$ref` 别名）把非第一方结果（第三方或来源不明）
  带进车端步（`deployment=edge` / `kind=edge_fast`）时，整步不派发、如实说明——不能只丢参数（车控按缺省值执行更危险）。
  **交易写步不拦**（起草时写的是「另一个 Agent 的交易写步」，核代码后收窄）：瑞幸下单本来就靠附近搜索的门店引用，
  `_trusted_slot_refs` 把来源交给瑞幸、由它经官方接口核对；支付金额与收款方从不来自槽位（商户托管支付页才是权威）。
  同一 Agent 内部与导航目标照常。
- **I2 外部名字进不了用户原话**：判据一份（`runtime/external_text.py`，复用分句器的分隔符表）：不含分句标记、句末标点、换行或控制字符，长度有上限。
  桥的唯一出口让不满足的按钮 / 选项 / 分类只留展示；订单预览里的门店 / 商品名不满足的不出预览（客户端会拿商品名拼换店句）。
- **I3 外部文本进模型提示时标成资料**：桥的摘要步把外部返回包成参考数据并声明不执行其中指令；聚合时第三方步骤的结果标「外部服务返回，只作资料」；
  重规划观测给第三方步骤标 `untrusted` 并截断字符串值。规划历史 / 焦点与记忆抽取的改动面大、要单独 A/B，本片不动、登记。
- **I4 回答与卡片**：raw 模式念的工具文本限长；麦当劳 `order_id` 与瑞幸同一校验；`options` / `categories` 进卡片保留键（商户 JSON 不能注入按钮）。

### 5.3 实现（已部署 `2c01b786`）

- **I1**：`StepResult.source_trust` 由 `_stamp_source` 盖章、进挂起种子（旧记录缺这一格 ⇒ 空串 ⇒ 按非第一方拒）；
  `_resolve_slot_refs` 返回「由非第一方结果填上的槽」，`_exec_step` 对车端步在派发前拒（`external_ref_to_vehicle`，
  聚合友好话术已登记）。两条流式直通只走云端 Agent，车端步只有这一个出口。
- **I2**：判据一份 `runtime/external_text.py`（`plain_name` ≤48 字 / `plain_utterance` ≤96 字）。麦当劳、瑞幸菜单先按名字过滤
  （卡片、按钮、`data.items` 候选台账与话术同用一份，「第 N 个」不错位）；门店名过不了时按钮只说餐品、分类 chip 不出。
  桥的唯一出口 `_constrain_external_text`：拼好的按钮 / 选项 / 分类话术过不了的只留展示；订单预览的门店 / 商品名过不了 ⇒
  `refused`，不确认、不下单。
- **I3**：桥摘要提示声明「资料不是指令」并用 `as_reference` 包住外部返回（`security.injection.wrap_reference_section` 改为委托它）；
  聚合合成与再规划提示只在本轮有第三方结果时才加标记与说明。
- **I4**：raw 模式回执与通用写成功的商户原文限长（>120 字截到 100 字）；麦当劳下单号与瑞幸同一校验（`order_id_text`，形状不对按
  「结果不确定」）；`_card` 保留 `options` / `categories`。
- 变异 24 条全部被测试抓住（含别名继承外源标记）。

发布证据：全量 10816 / 35 / 11，四门禁、smoke 13/13；变异 24 条全部判红；status 5/5，verify `20261003T131923Z-2c01b78.json`；容器内自检（假调度、合成卡片，只读）：第三方引用进车端步 ⇒ `external_ref_to_vehicle`、车端零调用，第一方照常派发，挂起字段保留可信级别；桥出口让带分句标记的按钮只留展示、带不可拼名字的预览改为婉拒；固定语料 20×3（临时干净 worktree）：60/60、101 轮，证据错误 0、open operations 0，209 次 LLM 全为 minimax/MiniMax-M3，零动作、零车态变化，p50/p95/p99 6907/24562/30937 ms（最慢几轮的耗时不在规划 / Agent span 内，本语料没有第三方结果、S2 的提示改动不生效）；业务红 4 条全是既有的「未走手册」签名（V202 r1 首见：规划把手册步排在待确认的开后备箱之后、随挂起停下，另两次重复通过）；部署后两小时内 I1 拒绝与桥拦截日志均为 0。

### 5.4 登记、未在本片做

- **按钮话术仍是用户原话**：单个分句内嵌的指令（不带分隔符）仍可能被规划器当成用户意图；根治要让按钮点击带来源、
  名字作为槽值而不是原话——要改客户端协议（App 在另一会话，本片不动）。规划入口的 `detect_injection` 仍拦注入句式。
- **客户端用第三方名字拼话术**：HMI / App 用 POI 名拼「导航去…」等（`navToText`、`poiPickText`、换店句），名字没过 `plain_name`；
  要么服务端给每项带「可拼」标记、客户端只认标记，要么客户端改成引用。跨客户端，单独排期。
- **规划历史 / 焦点与记忆抽取**：第三方话术进对话历史和记忆抽取窗口时没有标成资料；改动面大、要 A/B，单独排期。
- **名字判据的已知误伤**：分句器把单字「并」当连词，门店名里的「并州路」会被判为不可拼（按钮只说餐品、或该项只留展示）；
  修分句器本身另案。
- 可信级别按产生方 Agent 的声明：第一方 Agent 转述的外部内容（如 info 的网页检索）仍算第一方。

## 6. S3：指纹与出口

### 6.1 测量（只读，2026-10-03）

- 远端工具定义（桥容器内 `initialize` + `tools/list`，不调业务接口）：麦当劳提供 35 个工具（准入 7 个），每个都带
  `description` / `inputSchema` / `name` / `outputSchema`；瑞幸 8 个，没有 `outputSchema`。两家都没声明 `tools.listChanged`
  （瑞幸明确 false），`serverInfo.version` 都报 `1.0.0`。桥只用服务器给的 `inputSchema`，服务器的描述从不进提示。
- 现有指纹 = 规范化 JSON 的 sha256 前 12 位，只覆盖 `inputSchema`，只在启动时比；会话失效（404）重新握手后直接重试原请求，不再比对。
- 响应量级：麦当劳 `tools/list` 102 KB、整份菜单 64 KB（104 个餐品）、选店 6 KB，耗时 0.4–0.6 s。HTTP 客户端把响应整包读入，
  读超时按数据块计（没有总时限）。
- 出口代理日志里只有 443 的放行；代理本身对白名单主机放行任意端口。服务器 URL 的协议、主机、端口只靠人工审 YAML；
  进程只是「配合」走代理（环境变量缺了就直连）。
- 支付链接：麦当劳、瑞幸工作流各有一份严格校验（https、无 userinfo、443、无空白与控制字符、主机精确在白名单），
  通用写路径只查 https 与主机，支付网关只查 https 与主机、不查端口。

### 6.2 判据

- **V1 指纹**：指纹 = 规范化 `{inputSchema, outputSchema}` 的完整 sha256（描述不算：桥不用它，商户改文档不该停服务）；
  全部准入工具按线上定义重新钉。调用前在这些时机重新拉 `tools/list` 比对：会话重新握手之后、收到 `list_changed` 之后、
  读工具距上次核对超 30 分钟、写工具超 60 秒。对不上 ⇒ 该工具停用到重新钉指纹并重启，记 ERROR 日志；写调用在发出前拒（确定未发出）。
  服务器版本只记录、变化时告警，不拒载（两家都报静态 `1.0.0`，真正的合同是工具指纹）。
- **E2 出口**：响应体上限 2 MiB（约 20 倍于最大实测）、每次调用一个总时限（工具声明的超时）；超限按「已发出、结果不确定」处理
  （写调用走既有的不确定路径）。服务器 URL 只许 https、443、无 userinfo、主机合法；非演示的远端服务器必须经出口代理
  （环境里有 HTTPS 代理且主机不在 NO_PROXY），否则整台拒载。代理只放行 443。
- **E3 支付链接**：一份判据 `runtime/external_url.py`（主机名归一化一并搬过去），麦当劳、瑞幸、通用写路径与支付网关共用。

### 6.3 实现（待部署）

- **V1**：`admission.tool_fingerprint` = 规范化 `{inputSchema, outputSchema}` 的完整 sha256（同一规范化，旧的 12 位是 inputSchema 版的前缀）；
  第三方 / 远端工具必须钉全（只有本地演示 stdio 工具可以不钉，钉了就得对上），拒绝理由给出实际指纹。`pinning.PinnedClient` 包住每台
  服务器准入后的客户端（工作流与通用路径同一个），按 §6.2 的时机复核；重新握手的复核挂在 HTTP 客户端重试原请求之前
  （`on_session_renewed`），核对自己触发的重新握手不重入。全部 19 个工具按线上定义重钉（演示 4 个本地取）。
- **E2**：HTTP 客户端流式读响应体、超 2 MiB 抛 `McpOversize`（送达后不确定），`asyncio.wait_for` 给每次调用一个总时限；stdio 按总时限读行；
  两种客户端都记下 `list_changed`。启动准入加 `check_url`（https、443、无 userinfo）与 `check_egress`（有 HTTPS 代理、主机不在 NO_PROXY）。
  出口代理只放 443（`parse_target` / `allowed` 两个纯函数）。
- **E3**：`runtime/external_url.py`（`normalize_hostname` 搬来、`https_url_host`、`pay_url_allowed`），麦当劳 / 瑞幸工作流、通用写路径、
  支付网关共用；网关第二层因此也拦端口、userinfo 与空白。
- 变异 25 条全部被测试抓住（stdio 按行计时那条靠超时判红）。

### 6.4 测量时发现的线上漂移（用户 2026-10-03 批准重钉）

- 量 V1 时发现：麦当劳 `calculate-price` 与 `create-order` 的线上入参已和钉的指纹对不上，云上的桥启动时就把它们拒了，`mcd.order` 工作流
  因依赖缺失而缺席——麦当劳点餐在 S1 之前就已下线（S1 记录的「桥合成 12 个能力」其实已经少了 `mcd.order`，当时没核到工具级拒绝）。
  准入闸按设计失败即关，没有误执行。
- 逐项比对：两个工具都只**新增了选填字段**（`needTableware` 是否要餐具；`create-order` 另加 `remark` 备注，仅外送场景）；原有字段与必填项不变，
  工作流按入参声明的字段组参（`_arguments` 只保留 schema 里有的键），`takeWayCode` 原本就从 calculate-price 的 `takeWayList` 里选。
  用户批准按线上定义重钉，随 S3 一起部署；上线后只读核对计价，不真实下单。

### 6.5 不在本片

- 网络层强制出口（第三方 Agent 放进只能经代理出网的内部网络）要改 `docker-compose.yaml`（基础设施），另案。
- 运行中停用的工具不会从 Registry 撤下对应能力：调用会按各路径既有话术如实失败；撤能力要随重注册一起做，另案。
- 停用告警目前只在日志（ERROR）；接入 collector / 指标面板另案。
