名字**包含**「滴水湖」的更近 POI（酒店）顶上 top1 → `_dest_matches` 包含式校验**放行**
（「滴水湖」⊆「滴水湖雅悦酒店(上海老芦公路店)」，:1024 归一后任一方向包含即真）→
去偏置重搜（:1102）**永远不触发**（它只在校验失败时触发）。

## 2. 根因一句话

R1 第一期的包含式校验解决的是「**名字对不上**的就近垃圾」（广州塔 vs 广州仄仄科技），
它的隐含假设是「名字包含查询词 ⇒ 是本体」。本家族证伪了这个假设：
**包含是必要条件不是充分条件**——酒店/停车场/门店借地标之名命名（「XX 机场店」「外滩 XX 馆」），
在就近偏置的距离序里天然排在本体前面。校验通过 ⇒ 现有的两条救济（去偏置重搜、地标 LLM）
全部短路。

## 3. 为什么不能顺手修（R1 第一期的既得绿灯是硬约束）

`_find_destination` 是三个月里被四批 badcase 打磨出来的窄门，动它之前这些必须保持绿：
- 「广州塔」不被「广州仄仄科技」顶掉（包含**拒绝**面，方向不能反）；
- 「导航去惠州」走行政级判定直达市中心，不给 0.3km 的「惠州出口」机会（:1080 段）；
- 「最近的粤菜馆」就近类目路径 `strict=False` 刻意绕过本校验（:516 注释），不能被新逻辑误伤；
- 地标 LLM 候选的 `name_matches` 宽松匹配（俗称→官方名，2 字公共子串）是另一把尺子，别混用；
- 高德对非官方名返回「挂羊头」邻近 POI 的老坑（华润春笋大厦→V东滨店）。

## 4. 候选修法方向（评估序即建议序，可组合）

| # | 方向 | 判据 | 风险 |
|---|---|---|---|
| D1 | **短名/精确优先重排**：候选集内先找 `name == query` 或「name 长度 ≤ query 长度×k」的项（k≈2.5），有则顶替距离序 top1 | 零额外 API 调用（候选集已在手）；「虹桥机场」vs「如家…停车场(21字)」长度比一目了然 | k 阈值要用对抗集扫出来，不拍脑袋；「滴水湖(地铁站)」这类短名亲戚要处理 |
| D2 | **类目感知降权**：查询含 机场/火车站/高铁站/湖/山/景区 等类目锚词而候选 `category` 是 酒店/停车场/商铺 时降权（高德 type 字段已随 POI 返回，零额外调用） | 语义最准；交通枢纽与自然地物正是三例全部命中的两类 | 锚词表是新的维护面（B4 纪律：声明要有消费方且防漂移）；类目词表别长成第二个 fast_intent |
| D3 | **去偏置对照裁决**：短查询（≤6 字）恒做一次 near=None 对照搜索，两个 top1 里选名字更精确的 | 把「对照例为什么对」直接机制化；救济面最广 | 每次短名导航多一次高德调用（QPS 面）；两个都错时无裁决依据 |
| D4 | **「上次去过」独立小刀**：episodic 轨迹 value_json 里**坐标本来就有**（批 C 落的），历史指代场景直接用坐标不重搜 | 与本家族解耦、可单独先做；顺带消掉「召回对了最后一跳歪」的整类 | 只救历史指代一个场景；需要 planner→agent 的坐标传递面设计（防模型编坐标——`last_places` 不进 prompt 的老纪律） |

## 5. 接手取证清单（先做这个，再写代码）

2. 对红例逐个记录 `_direct(near)` 返回的**完整候选列表**（名字/类目/距离）——D1 的 k 阈值

3. 按 D1→D2 顺序单独开臂评估（一次只开一个），红例修复数 / 绿例回归数 双指标；
   D3 只有在 D1+D2 仍有残留时才评估（它有 QPS 代价）。
4. D4 独立做，不与 D1-D3 混在一个 commit（消费面不同、回归面不同）。
5. 验收：迷你集全绿 + `agents/navigation/tests` 全绿 + `eval_route_hints` 无回归 +
   真栈复跑本卡 §1 的四条 trace 输入。

## 6. 明确不做

- 不放宽/收紧 `landmark.name_matches`（那是俗称→官方名的尺子，本家族不经过它）；
- 不把修法做成 route_hint 或正则（这是接地质量问题不是路由问题）；
- 不改 `search_poi` 视觉地标分支（它是本卡的对照组，动它就没有基准了）。
