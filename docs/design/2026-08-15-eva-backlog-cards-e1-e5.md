## E1 事件时刻反推用餐/出发窗（G1 余项）

**缺口**（指令集三§1#3「晚7点电影，先吃个饭…」）：`arrive_by`（到达时限判定）与出发提醒反向环
已在 B 批落地（`_deadline_note`、`_route_plan_to` 的 `depart_ts = arrive_by - 路程`），但**镜像
半边没有**——用户说出的是**事件时刻**（7 点的电影）而不是到达时限，系统既不反推「几点该入座、
几点该吃完」，也不据此约束餐厅检索。真栈读数是诚实澄清（「想让我怎么安排？」），不编造，
但也没有 constraint solving。

**方案**：
1. **时刻解析下沉共享**——`_parse_arrive_by` 目前是 navigation 的私有函数，nearby 要用同一套
   语义。提取 `agents/_sdk/timewindow.py` 作**唯一实现**（判定抄两份正是 B1 那个 bug 的成因），
   navigation 改为 import（对外名字与行为逐字不变）。
2. **事件时刻解析**（新）：`parse_event_time`——只认「时刻 + 事件名词」形态
   （电影/演出/话剧/球赛/演唱会/航班/火车/会议…），**不认**「X 点前到」（那是 `arrive_by`，
   归 navigation）。两者互斥，避免同一句被两条链抢。
3. **用餐窗反推**（新）：`dining_window(event_ts, *, dwell_min=60, buffer_min=30)` →
   `(入座, 离席, 出发)`；`离席 = 事件时刻 − buffer`、`入座 = 离席 − dwell`。
   **buffer 是明说的假设不是伪造的数据**——话术里逐字说出「预留 30 分钟路上时间」。
4. **nearby 消费**：命中「事件时刻 + 餐饮类目」→ ① 话术给出窗口；② 按 `open_today` 过滤
   **入座时刻不营业**的候选（复用 `providers/base.is_open_now(now_min=)`，真实数据不是近似）；
   ③ 结构化落 `data.dining_window`。窗口已过（事件太近）→ 诚实说来不及，不硬凑。

**不做**：不替用户订位（G10 搁置）、不自动创建提醒（主动路径零执行权）、不猜事件地点的路程
（未知地点的路程只能编，改用明说的 buffer）。

**实施记录**：`agents/_sdk/timewindow.py` 落四件（`parse_clock_time` 由 navigation
`_parse_arrive_by` 原样迁入 + `parse_event_time` + `dining_window` + `fmt_clock`/`clock_minutes`）；
navigation 改 import 且对外名字不变（`_parse_arrive_by = parse_clock_time`，既有 132 条零改动通过）；
nearby `_search` 在餐饮类目下消费，`data.dining_window` 落结构化。
**刻意不进卡片**——HMI 没有渲染这块，落进卡片就是无消费方的死字段（B4 那条判据）。
`_now_ts()` 留成可替换的时间锚：不给注入口，用例就只能写成「在某些真实时刻会红」的样子。
单测 **13 条**（sdk 8 + nearby 5）。

**真栈**：「晚上7点的电影，先找个地方吃饭」→
> 19:00的电影——建议17:30入座、18:30前吃完，预留30分钟路上时间。为您找到 10 家川菜…

四轮命中 4 次（另有**首轮一次落 chitchat**「晚饭想吃什么类型的？」，obs 读数
`intents=chitchat.talk / plan_mode=toolcall_degraded` ⇒ 输出通道方差族，非本卡缺陷）。
按「修落域 badcase 的默认产物是范例」投 `skills/exemplars/nearby.yaml` 一条（307 条 / 22 域，
域错配率 2.4% 不涨）。

**顺带修**（同一轮真栈话术里看见的）：planner 把「吃饭」填进 keyword 时，它被当成检索词
——高德搜「吃饭」、话术念成「为您找到 10 家**吃饭**」。剥壳后若正好是类目别名就换成
canonical 检索词（`吃饭/餐厅 → 美食`），具体词（火锅/川菜）不受影响。

## E2 停车便利 / 无障碍 / 不排队属性维（G5 余项）

**缺口**（指令集六#6「爸妈腿脚不便→带爸妈吃饭」、三§1#3「停车方便」、六#3「不排队」）：
`Place` 无停车/无障碍字段；「不排队」无检索维度。存储面有（`person.parent`「用户的父母腿脚
不太方便」真栈在库），消费面零——**存得下用不上第 N 例**。

**方案**（缺口分析 §2-G5 的方向：目的地半径停车场计数近似 + tag 软重排）：
1. **触发两路**：① 原话显式（腿脚不便/走不动/轮椅/无障碍/少走路/停车方便…）；
   ② **记忆驱动**——话里点名家人/老人时召回 `profile.person` 事实。
2. **停车便利度近似**：对前 K=4 个候选各查一次「停车场」，取 300m 内计数与最近距离 → 软重排。
   **串行**（高德免费档 QPS 紧，并发扇出会 CUQPS 超限——既有纪律）；探测面有界，重排面就不超出它。
3. **诚实边界**：话术逐字说「地图没有无障碍/台阶数据，已按周边停车便利度排序」——同「安静度」
   那条既有形态。「不排队」同理：**没有实时排队数据就说没有**，不拿评分冒充。
4. `data.access` 落 `{reason, parking:[{name,count,nearest_km}]}`。

**实施记录**：nearby 落 `_ACCESS_RE`/`_MOBILITY_MEM_RE`/`_NO_QUEUE_RE` + `_kin_words`
+ `_mobility_reason` + `_parking_rerank`；`_taste_profile` 增 `no_queue` 维。
「不排队」的原话与记忆文本**共用一条正则**——两处各写一条迟早只改一处。
单测 **9 条**。

**真栈 3/3**：
- 「带爸妈去吃饭，他们腿脚不太方便，找个停车方便的餐厅」→「您提到出行不太方便——地图没有
  无障碍/台阶数据，已按周边停车便利度排序」
- 「带爸妈去吃个饭」（**一个属性词都没有**）→「记得您提到过家人行动不太方便——…」（记忆驱动）
- 「找个不排队的粤菜馆」/「晚上和老婆找地方吃饭」→「地图没有实时排队数据，这条我按不上」

**过程抓修：假个性化一枚**（真栈发现，单测跟不上）。首版触发条件是「话里提到了人」，于是
**「和老婆吃饭」命中了「父母腿脚不便」那条记忆**——系统声称考虑了一件根本不适用的事，
与缺口分析 §5① 那条「nearby 假个性化」是同一种错、只换了个维度。修法：记忆必须**确实关于
话里那个人**——`subject` 命中，或文本提到该称谓的同义词；泛指「老人/长辈」才放宽到祖辈族。
对照断言双向锁（老婆不触发 / 爸妈仍触发）。

## E3 多城归城校正 + 主题接地可观测（LLM 软层观察双面）

**缺口**（P2 实施记录自记的两条软层噪声）：跨天归城排错（点在行程里但落在别的城市那天）；
主题接地命中率没有读数（分不出「正常降级」与「链坏了」）。

**方案**：`correct_stop_cities(trip, pool_by_city)` 按坐标把排错城那天的 stop 搬回归属城首日
（双阈值保守：比当前城近 ≥1.5 倍**且**绝对差 ≥30km，城际交界不来回搬；未接地的没有坐标不动；
单城零影响），在 `ground()` 之后、`solve()` 之前跑（衔接 leg 依赖最终分天）。
`build_theme_pool` 改返回 `(pool, stats)`，`data.theme_grounding = {proposed, grounded}`。

**实施记录 + 真栈：这卡真正的收获是「校正够不着」的三层原因**。六城长句
（「从苏州出发看大秋裤→无锡灵山大佛→南京长江大桥→济南趵突泉→潍坊风筝博物馆→北京天安门」）
连跑四轮，每轮都换出一个新的上游障碍：

| 轮 | 现象 | 定性与修法 |
|---|---|---|
| 1 | 城市序 = 苏州、**东方之门**、无锡、南京、济南、潍坊、北京；第 2–5 天全标「东方之门」 | planner 把「大秋裤→东方之门」**同时**填进 `destination` 城市串和 `must_visit`。修：`_drop_named_pois_from_cities`——点名 POI 不是城市，判据是**归一后精确相等**不是包含（「苏州园林」不等于「苏州」） |
| 2 | 城市序对了，但 6 城只排 3 天，南京/济南/潍坊/北京**一天都没分到** | planner 填 `days=「用户未指定」`。修：`_days_for_cities`——多城且用户没说天数 → 天数取城数。⚠ 判「说没说」不能用 `_norm_days`（它把非数字剥掉，「三天」会被读成 0，那就成了替用户改需求） |
| 3 | 每城有天了，可无锡那天溢出的三个点被塞进**南京那天**（且都在队首） | `solve` 的日上限顺延 `insert(0, moved)` 只认「下一天」，不认「下一天是别的城」。修：下一天是别城就**原地插一天、城市跟着走**；单城 city 全空、判据短路，行为逐字照旧 |
| 4 | 五城全部归位（东方之门→苏州、灵山胜境→无锡、长江大桥→南京、趵突泉→济南、天安门→北京）；**潍坊风筝博物馆仍留在济南那天** | 日志实锤：`pool search '潍坊 景点' / '潍坊 美食' failed: CUQPS_HAS_EXCEEDED_THE_LIMIT` ——**潍坊池两次检索都被高德限流 ⇒ 该城没有质心 ⇒ 不参与归城判定**。这是本机制的**已知边界**（判据是各城池质心），不是静默失败 |

单测 **10 条**（归城校正 7 + 顺延跨城 2 + 单城行为不变 1）+ 城市序/天数守卫 **5 条**。

**主题接地命中率（③ 的另半边）真实读数**：「跟着《太平年》游杭州」→
`theme pool《太平年》: **6/7** candidates grounded`，唯一漏掉的「凤凰山」是
`CUQPS_HAS_EXCEEDED_THE_LIMIT`（限流），**不是主题知识缺**——这正是这个读数的用处：
它一眼分开「正常降级」「链坏了」「被限流」三种长得一样的结果。复跑话术兑现
「已按《太平年》主题…规划杭州 3 天行程」。⚠ 首轮该请求**网关超时**（高德连续限流
拖慢整条链），复跑 32.4s 正常——归既有高德 QPS 一族，与本卡改动无关
（`correct_stop_cities` 是纯函数、不打 provider）。

> 判据沉淀：**「校正没生效」有四种完全不同的原因**——没有城市序、没有天、被下游打乱、
> 判据的输入为空。四轮里每轮都只暴露一个，上一个不修就永远看不见下一个。
> 这与「诊断出一个洞不等于这个洞就是病因」互补：**修好一个洞才看得见下一个洞**。

## E5 抽取谓词别名散置老账（消费方误伤**已命中**）

**取证先行**（本卡最重要的一段）：§4.2 写的启动条件是「出现消费方误伤再启动数据清洗」。
实测 u1 真栈库（38 组 predicate）：

| predicate | scope | n | 样本 | 后果 |
|---|---|---|---|---|
| `place.avoid` | profile.taste | 1 | 以后不要推荐三立方(南山创维店)，觉得咖啡太酸 | **召不回** |
| `poi.dislike` | profile.taste | 1 | 用户不喜欢三立方(南山创维店)这家咖啡店 | **召不回** |
| `restaurant.no_queue` | profile.taste | 1 | 老婆不喜欢排队 | **召不回** |
| `beverage.coffee`/`brand.coffee`/`coffee.brand`/`coffee.order`/`consume.coffee`/`drink.coffee`/`food.coffee`/`taste.beverage`/`taste.americano_iced` 等 | profile.taste | 11 | 同一件事（瑞幸美式中杯）散成 6 个谓词 | supersede 失效、并存 |

nearby 口味召回是 `recall(scopes=["profile.taste"], predicate_prefix="taste.")`，而
`pg_store._score` 里 scope 与谓词前缀是 **AND**（`pg_store.py:429-432`）——前三行**永远进不了
口味消费面**。P5 的降权之所以在真栈兑现，是因为恰好另有一条 `taste.coffee` 也带了店名；
**同一件事的另外两条证据一直是死的**。这是「存了没用上」与「记录一个缺陷不等于修它」的合流。

**方案与实施**（三半，缺一不可）：
1. **写入侧**：`_PRED_CANON` 扩 7 个 canonical / 18 个别名（`taste.coffee` / `taste.coffee_brand`
   / `taste.cuisine` / `taste.spicy` / `taste.dislike_place` / `taste.no_queue` / `order.pickup`）。
   别名**全部来自真栈实测谓词**，不发明未观测形态。**刻意不合并语义不同的维度**——品牌偏好
   与口味偏好各自 canonical，压成一条会让新口味 supersede 掉品牌偏好。抽取 prompt 同步把口味族
   前缀写死（源头收敛，归一表只治已知别名）。
2. **消费侧**（防再犯）：nearby `_recall_taste` 改**两路并集**——`scope=profile.taste` 一路 +
   `predicate_prefix=taste.` 一路，按 text 去重。谓词与 scope 都是 LLM 写的、都会漂，
   任何一路单独当门禁都会重演今天这一幕（同 P4「三类并集」先例）。
3. **存量**：`scripts/memory_predicate_cleanup.py`（dry-run 默认；`--apply` 归一、
   `--supersede-dups` 去重，两者分别授权）。归一表**只从 `memory/extract.py` 导入**，不留第二份声明。

单测 **9 条**（memory 5 + nearby 4）。
