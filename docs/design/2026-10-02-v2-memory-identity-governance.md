## 5. S1a：端点按 token 解析主体（已部署 `e7766e98`）

### 5.1 判据

`llm-gateway/http_server.py::_owner_query` 是这 9 个端点的唯一入口判据：

- 主体只来自 `Authorization: Bearer`：`AUTH_TOKENS` 四段条目（与车端网关同一解析口径）；`e2e.v1.` 前缀的签名测试身份
  只在 `E2E_IDENTITY_ENABLED=true` 且签名、有效期都通过时成立（与 S2S、车端网关同一开关与密钥）；
- 查询串里的 `user_id` 可以不带；带了就必须逐字节等于主体，否则 403 `owner_mismatch`；没有可用 token → 401 `unauthorized`；
- **拒绝发生在读请求体与调 Memory 之前**：注册 / 识别不读音频，删除不触达 Memory；识别的拒绝仍回 `occupant_id=primary`
  （识别面的既有契约：任何失败都回落到 primary）。

`/api/memory/forget` 的既有判据（body 里的 `user_id` 只能等于主体）不变，签名测试身份对它同样生效。

### 5.2 客户端

- HMI：`audio.ts::memoryAuth()` 给全部记忆 / 声纹请求带同一个 `VITE_WS_TOKEN`；免唤醒的说话人识别经
  `postIdentify(audioApi, userId, token)` 带上（`handsFreeController` 传入 `memoryAuthToken()`）。
  云端 HMI 的 token 主体是 `u1`，与 HMI 写死的 `USER_ID` 一致（只读核对，未改 `.env`）。
- E2E：`e2e_voiceprint` / `e2e_memory_graph` / `e2e_s2s` 改用运行器签发的测试身份 token 调这些端点。

### 5.3 本批发现、不在本批修的同类缺口

S2S 的 `session.start` 在生产里同样直接信客户端帧里的 `user_id`：会话用它读该会话近几轮对话做上下文，并把对话回流写进
该用户的记忆（只有开了 E2E 签名身份的测试命名空间才验签）。HMI 与 Android 都走这条路，收紧要重新出 Android 包，
所以并入 S2（S2 本来就要改 Android 的身份上送）。

## 6. S1b：删除与在途写入同代际失效（已部署 `910fd572`）

### 6.1 复核到的复活路径（2026-10-02）

| 路径 | 窗口 | 现状 |
|---|---|---|
| Memory 内部抽取（每 4 轮或「记住」类语句触发） | 读最近 12 轮 → LLM 抽取（秒级）→ 写条目 / 关系 / routine → 发主动建议 | forget 落在中间时，抽取结果在删除之后写回 |
| 云端回合 | **回合结束后**才写 user / assistant 两条轮次（复杂任务几十秒） | 全量 forget 会取消本进程在途请求；单乘员 / 单条删除不会 |
| Agent 写记忆 / 画像（`remember`、`save_profile`、`save_shared_state`） | Agent 执行期间 | 无任何复核 |
| 车端 `AppendTurn`、S2S 回流 | 回合内 | 无任何复核 |
| **单条删除后的再抽取** | 下一次抽取重读窗口里的旧轮次 | 删掉的条目会从仍在窗口里的原话被重新抽出来——这不是竞态，是必现 |

### 6.2 判据

- **代际** `memory_epoch` = `<代数>.<随机 128 位>`，按用户存在 Redis（`mem_epoch:{user}`，无 TTL；Redis 不可用时与会话轮次同样退回进程内存），
  首次读取惰性创建（代数 0）。ForgetUser（全量 / 乘员 / scope）、DeleteVoiceprint、DeleteMemoryItem **在删除之前**推进代际。
  Redis 丢数据后重建出的代际与在途写入带来的旧值不相等 ⇒ 拒绝，失败方向是少写而不是复活。
- **串行点**：Memory 是记忆数据的唯一写入口，且是单副本（compose 单实例、无副本配置）；同一用户的「复核代际 + 写入」与
  「推进代际 + 删除」在 Memory 进程内互斥，所以复核与写入之间没有窗口，不需要跨存储事务或事后补偿。
  **前提**：Memory 扩成多副本之前，这把锁必须换成跨进程的。
- **写入方带观测时的代际**：`AppendTurn` / `Remember` / `UpsertProfile` 新增 `memory_epoch`；带了且不等于当前值 ⇒ 拒绝
  `stale_memory_epoch`，不写。不带 = 旧调用方，照旧写；生产写入方全部带（源码对账测试）。
  代际在**读记忆之前**取（新 RPC `GetMemoryEpoch`）：云端每回合开始、车端每个请求开始、S2S 会话开始与每次重取上下文时；
  Agent 用云端经 meta 下发的 `memory_epoch`（服务端自有键，客户端 prefs 里同名键一律剔除）。
- **抽取**：Memory 在读轮次之前取代际 e0；写入前持锁复核，不等则整批丢弃；routine 派生与主动建议同样复核。
- **抽取水位**：轮次落库时盖上当时的代际，抽取只用代际等于 e0 的轮次（修前落库、没有代际字段的轮次只在代数 0 时有效）。
  于是单条删除推进代际后，删除前的轮次不再进入抽取窗口——被删的条目不会再从旧原话里抽出来；会话历史本身（规划上下文、记忆页）不受影响。

### 6.3 代价与不做

- 删除时刻在途的写入一律丢弃，包括与被删内容无关的（同用户其他乘员同一时刻的轮次、Agent 临时态）；删除前尚未抽取的轮次（最多 3 轮）不再抽取。
- **删除总线不扩展到单乘员 / 单条删除**（方案稿 ② 的「撤销在途」；2026-10-03 用户接受，连同下一条单副本前提）：总线负责删 MCP 草稿与云端挂起，这两种删除都不涉及；
  若为它们取消云端在途请求，删一条「爱吃辣」就会打断正在跑的天气查询。所以这两种删除只做栅栏：在途请求可能用删除前读到的
  数据完成当前这一句回答，但写不回 Memory。全量 forget 维持现有总线（删除 + 撤销在途视图）。
- 会话中途删过记忆的 S2S 会话：模型手里的摘要读于删除之前，此后回流一律被拒，直到断线重建摘要——这段时间的语音对话不进记忆。

### 6.4 验证（本地）

  轮次盖章；正在进行的写入与删除串行（删除等写完再删掉它）；抽取进行中删除 ⇒ 整批丢弃；单条删除后不从删除前的原话里再抽出来、

### 7.2 判据

1. **声音证明**：llm-gateway `/api/voiceprint/identify` 在 `decision=accept` 时签发短期证明 `voice.v1.<payload>.<sig>`，载荷为
   token 主体、乘员、称呼、签发与过期时间（10 分钟）。HMAC-SHA256，密钥由各服务已挂载的网格私钥按独立上下文派生（与删除总线同一做法，
   不新增密钥、不改 `.env`）。签发与校验只有一份实现（`runtime/voice_attestation.py`）。
2. **乘员只认证明**：meta 里的 `occupant_id` / `occupant_name` 不再被信任。证明有效（签名对、未过期、主体等于本请求的 token 主体）
   ⇒ 该乘员与称呼；否则乘员按 `primary`（存量语义）。云端与车端本地轮次同一判据。
3. **没认出 ⇒ 投影**：HMI 在声纹开启、免唤醒语音这一轮没有拿到 accept 证明时声明 `voice_identity=unrecognized`；云端据此把本轮的记忆读取
   投影为「只读普通偏好」——条目须 `kind=semantic`、`privacy_level=normal`、谓词不在 `identity.` / `person.` / `place.`、
   scope 不在身份 / 人物 / 地点、且不是关于别人的（`subject` 为空）；人称地点解析与关系查询返回空；称呼不下发。

4. **执行面在 Memory**：`GetContext` / `Recall` / `ResolvePersonPlace` / `QueryRelations` 新增 `projection` 字段，Memory 用同一个判据
   （`runtime/memory_projection.py`）过滤定向读与非定向召回；云端读时带上，Agent 经服务端自有 meta `memory_projection` 拿到、SDK 读时带上，

5. **S2S 绑定主体**：`session.start` 必须带 token（帧字段 `auth_token`，浏览器的 WebSocket 不能设请求头；E2E 签名身份照旧），

6. **不变**：声纹仍不参与权限、确认、VAL 与支付（`test_voiceprint_not_auth.py` 的红线不动）——投影只决定「这一轮能读到哪些个性化记忆」，

- 衰减两次：加强时存的是按 valid_from 衰减过的强度，召回时再衰减一次（推断档半衰期 90 天）。
- 同一个人两个主体：「女儿」与她的名字各存一条「不吃辣」（§8.6）；称谓的同义写法（妻子 / 老婆）按原样存的条目也各算一个主体。

### 9.2 判据

- 证据数 = 场合数（会话）：新条目 1 次；同一维度在**新的会话**里再被观测到才 +1（加强与取代时的继承同一规则，`weighting.next_evidence`）；
  同一会话里窗口重叠的重复抽取不加分。证据轮次只作溯源。Agent 写入带自己的会话。
- 强度存未衰减值：写入与加强都按 age=0 算，衰减只在召回时按 valid_from 算一次。
- 主体归一：`relation.normalize_subject`（称谓 → canonical，「用户 / 我 / 本人 / 自己」→ 本人）。名字与称谓只在**没有歧义**时算同一个人
  （`revision.aliases_from_family`：亲属关系边里一个称谓只对应一个具名的人、这个名字也只对应一个称谓；两个女儿各有名字就不合并）。
  写入时找维度的现行条目、召回按 subject 过滤、读取折叠，三处用同一组写法（`revision.subject_group`）；Agent 写入的 subject 先归一。
- 泛称不归到具体称谓：「孩子」不等于「女儿」（有两个孩子时会记到另一个人头上）。

### 9.3 存量

- 主体别名不改数据，读取时即生效。
- 存量的证据数是按旧口径写的，读取时分不出新旧，只能改数据：`scripts/memory_evidence_recount.py`（默认 dry-run，写库要 `--apply`）。
  场合数 = 同一维度里说同一件事的条目（现行 + 已被取代，与取代时继承证据同一口径）来自几个不同的会话；单值维度按来源类别分开数，
  多值维度按 `revision.equivalent` 判同值。旧的加强不记会话，所以是下限。只改现行带权条目的 evidence_count 与 weight，不删行，只打印计数。
- 只处理新口径上线之前写入的条目（`--created-before` 取 memory 容器启动时刻）与取代了它们的条目；写入前比对条目当前的证据数，
  并发的加强不会被覆盖。上线到重算之间被加强过的旧条目会少算至多一次（加强覆盖了来源会话）。
- 写库是生产数据修改，单独授权。

### 9.4 实现与验证（本地）

- 规则：`memory/weighting.py::next_evidence`；`memory/relation.py`（`normalize_subject` / `kinship_spellings` / `is_kinship_word`）；
  `memory/revision.py`（`aliases_from_family` / `subject_group`，维度与折叠带别名）。`pg_store`：插入不再按轮次数计、加强记会话、
  维度查询与召回按一组写法过滤；`store`：加强不再衰减、Agent 写入先归一主体、事实与偏好都按一组写法找现行条目。
  删掉不再有调用方的 `weighting.evidence_count`。
